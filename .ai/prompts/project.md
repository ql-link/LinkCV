# LinkCV

LinkCV 是 React/TypeScript + FastAPI 前后端分离 Monorepo。原型 Express 运行链已经移除；SQL-first Alembic 根 revision `0001` 已为 FastAPI 鉴权和简历模块建立正式 MySQL schema。

本文是项目使用与开发入口，只保留所有任务都需要知道的仓库事实、真实命令和长期约束。当前模块知识见 [docs/README.md](docs/README.md)，详细交付流程见 [.ai/skills/README.md](.ai/skills/README.md)，Spec 状态规则见 [.specs/README.md](.specs/README.md)。`AGENTS.md` 与 `CLAUDE.md` 统一链接到本文件。

> 临时改造分支提示：在 `refactor/local-ai-workflow-redesign` 上改造 AI 工作流时，先读取 [施工记录入口](plans/ai-workflow-redesign/README.md)。该目录只保存本分支的分析、决定、计划和进度，不覆盖本文、现有 Skill、脚本或测试所表达的当前规则；改造完成后删除该目录和本提示。

## 1. 沟通与决策

- 默认使用中文沟通、总结和撰写 PR 说明；代码、命令、日志与技术标识保留原文。
- 先核实仓库事实再给结论。不要为了迎合用户跳过风险、证据或尚未确认的假设。
- 不过分夸赞。用户和 Agent 的判断都可能有误；出现矛盾时优先补证据和说明取舍。
- 只在缺少的选择会实质改变结果时提问；低风险细节可采用明确写出的合理假设。

## 2. 仓库结构与架构边界

```text
apps/web       React 19、TypeScript、Vite 前端
apps/extension WXT、React、TypeScript 浏览器岗位采集插件
apps/backend   Python 3.13、FastAPI 后端
deploy         Compose 与部署资料
docs           供开发者和 AI 按需调阅的长期项目知识
.ai            项目规则与交付 Skill 的唯一来源
.specs         方案先行任务的本地阶段快照；产物模板跟随对应项目技能保存
scripts        初始化、质量与阶段门禁脚本
```

- 开发期全部 `/api` 请求由 Vite 代理到 FastAPI；FastAPI 已提供健康检查、鉴权、简历和图片路由。仓库中不再存在 `server/` 或 Express 启动入口。
- SQLAlchemy 模型、Alembic 环境和 SQL-first revision 生成入口已经建立；根 revision `0001` 创建 `users`、`resumes`，但仍须区分仓库 head 与目标环境实际 current revision。
- 后端集成测试使用隔离 SQLite 和假 MinIO，这只是测试替身，不是运行时持久化或回滚拓扑。
- FastAPI、前端 API client、Vite Proxy、环境变量和部署配置属于同一跨端契约；修改其中一处时检查其他位置。
- 鉴权、数据库、对象存储、资源归属和数据完整性改动一律按高风险跨模块改动处理。

## 3. 初始化与验证命令

```bash
npm run setup       # 新环境安装依赖并修复缺失的安全链接
npm run dev         # 启动 Web 和 FastAPI
npm run check:ai    # 校验 AI 链接和项目 Skill
npm run check:docs  # 校验长期文档及代码到文档同步关系
npm run check:contracts # 校验确定性的运行时契约值
npm test            # 运行 Web、浏览器插件和后端自动化测试
npm run check:app   # 三个应用的测试、类型检查和构建
npm run check       # 完整本地质量入口
npm run spec -- ... # 管理方案先行任务的本地阶段状态
```

- Python 命令统一通过 `uv run --directory apps/backend` 执行，不依赖系统 `python`。
- 不得宣称测试通过，除非实际运行了与改动范围匹配的命令并看到了成功结果。
- 当前任务完成只要求通过与改动范围和风险匹配的检查；准备创建 PR 时再运行完整 `npm run check`，共享 CI 继续执行同一完整入口。
- 前端使用 Vitest + React Testing Library，后端使用 pytest；跨端 E2E 当前采用人工验证。不得把 Gherkin 场景、组件测试或后端接口测试描述成已完成自动化端到端验收。

## 4. 交付流程入口

- 默认情况下，改代码请求先由 `flow-router` 分开判断准备程度、任务复杂度、风险和记录需要，再建议走直接实现还是方案先行；用户没有显式指定交付方式时，才按该建议和对应 Skill 推进。
- 用户可以在当前请求中显式指定是否走完整工作流以及走哪条交付路径。用户指定优先于 Agent 的自动分流，不得以“按规则风险更高”为由拒绝、静默升级或反复要求确认；Agent 最多简短说明一次风险，然后按用户选择执行。

### 4.1 用户放行通道

推荐使用以下任一写法；含义等价的自然语言指令同样有效：

```text
工作流：自动 | 开启 | 关闭
路径：自动 | 直接实现 | 方案先行
后续：自动 | 直接施工 | 契约验收
```

共有三条端到端路径：`直接实现`、`方案 → 实现`、`方案 → 验收契约 → 实现`。前一个岔口在用户未指定时由 `flow-router` 判；后一个岔口已有用户选择时直接记录并复用，尚未选择时才由 `solution-generator` 随方案确认。

- `工作流：自动`：默认行为，由 `flow-router` 判断路径并进入对应阶段。
- `工作流：开启`：执行分阶段交付；用户指定路径时直接采用，未指定时由 `flow-router` 判断。
- `工作流：关闭`：进入直接执行模式，不创建或更新方案文档、Acceptance 和 Spec 状态，不运行阶段门禁；完成真实代码核实、实现、必要测试和结果说明后直接交付。
- `路径：直接实现`：直接实现和按改动范围验证，不创建 Spec。
- `路径：方案先行`：生成并冻结方案文档后再实现，是否额外产出 Acceptance 由 `后续` 决定。
- `后续：直接施工`：方案文档冻结后直接实现，不产出 `acceptance.feature`；方案文档“验证与验收”中的结果、测试落点和人工步骤即验证契约。
- `后续：契约验收`：方案文档冻结后先产出并冻结 `acceptance.feature`，再实现。
- 方案文档各章节写多细不再由用户选档位，而由文档实际涉及的内容触发：涉及数据表就必须写到定稿 DDL，涉及跨端契约或部署就必须写到兼容窗口、回滚顺序和不可逆点。
- 用户说“直接执行”“不要走工作流”“跳过 Spec”等明确表达时，视为 `工作流：关闭`；用户说“先出方案”“要方案文档”但未说明工作流时，视为 `工作流：开启` 并采用 `路径：方案先行`。
- 同一请求同时出现冲突指令时，以更具体、更新的用户指令为准；若仍无法判断，则 `工作流：关闭` 优先，避免用流程阻塞已明确授权的实现。
- 用户在任务进行中切换工作流或路径时，从当前进度立即采用新选择。改为直接实现或关闭工作流后，不伪造、降级或手改已有 `.specs` 状态，只停止使用该 Spec 推进本次任务；已有文件作为历史快照保留。改为方案先行时再按所选路径补齐后续必要产物。切换 `后续` 使用 `npm run spec -- route <KEY> <路径>`，该命令会重置已有的验证与质量审查记录。

直接执行模式只跳过项目交付流程，不跳过以下底线：

- 仍须核实真实代码并保护用户已有修改；
- 仍须遵守权限范围、敏感信息保护和破坏性操作安全要求；
- 未实际运行的测试、构建、迁移或部署不得宣称通过；
- 创建提交、推送、PR、合并和远端变更仍需遵守本文的 Git 与授权边界；
- 发现会导致数据丢失、越权、密钥泄露或目标不明确的操作时，必须停止并说明具体阻塞，不能把“关闭工作流”解释为授权破坏性操作。

### 4.2 默认分流流程

- `flow-router` 使用七个维度：准备程度；影响面与相互牵连；规则与状态关系；实现确定程度；验证难度；风险与可回退性；持续性与协作。只有中间四项决定复杂度，不计算数字总分：四项都简单才是简单，任一项命中明确复杂信号就是复杂，其余为中等。准备程度是开工门槛；风险独立分为常规和严格；持续性只决定会话内还是需要持久记录。
- 七个维度始终在内部完整判断，但默认只向用户展示路径、一个主导原因和额外检查。准备不足、风险严格、需要持久记录或用户主动要求解释时，才展开完整七维依据。
- 准备不足时先澄清或只读调查，不伪装成复杂任务。复杂任务进入方案先行；简单和中等任务在目标已收敛、消费方已找全、实现有界可逆、无需分阶段兼容且当前会话可完成时可以直接实现。严格风险本身不自动升级为方案，但必须增加对应确认、失败结果、回退或不可逆说明、验证和审阅。预计跨会话、正式交接、并行协作或多个检查点时，现有 Spec 精简完成前保守走方案先行；这不改变任务本身的复杂度结论。
- 方案先行任务的需求与方案在同一阶段由 `solution-generator` 定稿：模板保留完整章节库，每份方案始终收敛需求描述、现状问题、一张主要流程图、真实文件、编号实施步骤和验证映射；状态机和数据模型是高优先条件章节，命中生命周期、状态关系或持久数据读写时不得省略，其他章节按任务复杂度与真实涉及面选择。它是与用户交互确认的核心阶段，业务规则和重要技术取舍的不确定点都在此直接提问，一次一个问题并给出推荐答案，结论写入方案文档的决策记录。
- 方案文档第一部分面向决策者，用白话写业务，不出现类名、方法名、表名、字段名、框架名和文件路径；通用技术术语直接使用不作解释，只有自创说法才在首次出现处就地说清。第二部分面向实现者，必须落到真实文件路径和按步骤编号的实现方案。没有待决选择的短方案整份只确认一次；长方案或存在独立决策时才分段确认。用户已经指定直接施工或契约验收时，冻结阶段直接复用，不重复询问；未指定时把后续路径与方案放在同一次确认中，并随 `--next` 记入状态。
- `solution.template.md` 保留原有完整章节和独立的“验证与验收”，但不要求逐章填写。实际方案按触发条件选择章节，未命中的章节直接删除，不写“无”“不涉及”或空表；任何选择都不能省略可观察结果到业务规则、真实文件、实施步骤和验证证据的对应关系。
- 整个模块的目标或商业前提尚未成形，或需要把结论沉淀到飞书供他人协作时，才使用 `module-planning` 完成事实调查、草稿确认、写入和读回；它按需调用 `decision-grilling`，每轮只处理一个需要用户取舍的决策。已有经确认并读回的飞书详情文档时，其结论优先于本地推断，冲突时回 `module-planning` 更新后再修订本地产物。用户原请求已经明确授权规划后继续开发时，读回一致后直接进入已授权的下一站，不再要求用户重复发送继续指令。
- 判为直接实现的任务直接实现和验证；方案先行任务必须冻结方案文档，选定契约验收路径时还要冻结 Acceptance。技术设计不再是独立阶段，已并入方案文档第二部分。
- 自动分流时，数据库 schema 或数据迁移默认判为方案先行，因为通常同时需要处理存量数据、兼容、迁移顺序和回退，不是因为“数据库”标签天然等于复杂。设计 MySQL 表结构使用 `mysql-ddl-conventions`，由方案文档阶段调用以定稿数据模型；编写、校验或排查 SQLAlchemy/Alembic 迁移使用 `alembic-migration`，在实现阶段按已冻结的定稿 DDL 落成配对 SQL。用户显式关闭工作流或指定其他路径时采用用户选择，但仍需执行与数据库风险相匹配的目标校验、迁移验证和回滚检查。
- 用户要求判断“功能是否真正做完、还缺什么”时使用 `feature-completion-audit`；当前会话刚完成的实现必须由独立子 Agent 取证，避免实现者自评。
- 用户要求根据报错、日志或异常现象查原因时使用 `incident-triage`，默认只诊断；没有修复授权时不修改代码、配置、外部系统或数据。
- 用户当前请求、可读取的 Issue、飞书文档及用户明确指定的其他材料都可以作为需求来源。当前请求已经讲清目标、边界、授权和可观察结果时，没有 Issue 不阻止分流、方案、实现或 PR，也不要求关闭工作流；有 Issue 时必须完整读取正文和关联材料，并把它作为可选追踪信息保存。工作流自身不要求补建 Issue；外部团队另有显式追踪规则时按其规则处理，但不能把本地 Issue 字段变成开工许可证。
- 飞书周开发文档及其中引用的详情材料负责补充和确认会改变范围、验收、权限、数据或兼容策略的决定。有效来源材料互相冲突时转 `module-planning` 确认当前结论，不静默选择；它只在完整草稿获得用户确认后调用 `lark-doc` 写入，并通过读回完成交接。项目流程不捕获外部 Issue 需求指纹，不核验评论链，不自动写评论，也不把实施差异回写任何 Issue 系统。
- `.specs/<KEY>/` 是当前工作区的本地执行快照，不承诺跨设备或跨 worktree 自动同步。冻结产物后由 `state.yaml` 记录哈希；任务范围验证由工具亲自执行所选命令并自动绑定代码内容快照，验证后必须经过同一快照上的质量审查才能进入 `release_ready`。这里的 `release_ready` 不代表 PR 全量检查已完成；开发者不手填哈希、退出码或阶段字段。适用的人工端到端结果记录在同目录 `manual_acceptance.md`。
- 实现阶段出现无法预见但不改变核心产品目标的偏差时，记录原因、影响、验证和遗留风险，并在 PR 中明确提出；不得为此自动修改来源 Issue。只有已允许的实际方案偏差、已接受限制，或必须跨会话交接的遗留风险或下一步事项才创建 `implementation_report.md`，数据库、跨端、权限、部署、多模块或严格风险本身不触发报告。会改变核心范围、验收、权限、数据安全或兼容承诺的事项先回 `flow-router` 重评并在方案先行时由 `solution-generator` 重新确认、冻结；相关结论已写入飞书详情文档时，才先更新并读回该文档。
- 方案先行任务开始实现前运行阶段检查；直接实现不创建 `.specs`。只在任务触发时读取对应 Skill。
- 搭建或修订这套 AI 工作流框架本身时允许采用自举例外，不要求先用尚未稳定的流程生成 Spec；框架用于正式业务开发后，再按上述路径强制执行。自举例外不免除真实代码核实、测试和审查。

## 5. 实现约束

- 改动前先读取最接近目标文件的现有实现、测试和文档，不凭框架惯例猜测项目结构。
- 保持改动聚焦；不顺带重构无关模块，不覆盖用户已有修改。
- API、持久化模型、迁移、权限和失败路径必须同步设计与验证。
- Alembic 版本默认采用 SQL-first：每个 revision 必须配对同 ID 的 `.up.sql`、`.down.sql`，DDL、索引、约束和可表达的数据变更优先写入 SQL；Python revision 只执行 SQL 文件。仅当 SQL 无法安全表达受控迁移时才允许 Python 逻辑，并在 revision 注释中说明原因；禁止使用自动生成的 `op.create_table`、`op.add_column` 等作为最终版本内容。
- FastAPI 已建立 SQLAlchemy 模型、Alembic 环境、SQL-first revision 模板和迁移执行入口，根 revision `0001` 创建 `users`、`resumes`。后续 schema 变化必须核对模型真值源，创建顺序编号及配对 SQL 文件，完成空库与往返迁移验证、文档同步和部署回滚；原型 SQLite 数据默认不迁移到 MySQL。
- `docs/` 只描述当前已实现的长期项目事实；方案文档、Acceptance、实施报告和人工验收记录继续放在 `.specs/<KEY>/`。
- 修改 FastAPI 路由归属、Vite Proxy、HTTP 契约或部署入口时，明确兼容窗口、回滚方式和数据处理策略。
- 新依赖必须说明必要性，并更新对应 lockfile。
- 默认示例和测试数据使用虚构信息，不得写入用户真实简历、联系方式或密钥。

## 6. Git 与 PR

- 禁止直接向远端 `dev`、`master`、`main` 推送、合并或改写历史。
- 创建分支、提交、推送或 PR 时必须使用 `branch-pr-workflow`；分支命名、规范化中文提交和中文 PR 模板只在该 Skill 中维护，不在本入口重复。
- 默认使用独立类型分支并创建以 `dev` 为 base 的 PR；发布前确认 base/head、完整 diff 和验证结果，不带入无关改动。
- 创建 PR 前必须在当前可提交内容上运行并通过完整 `npm run check`；任务阶段的范围检查不能替代该门槛，远端 CI 也不能反向证明本地未执行的检查。
- PR 创建后交由用户或远端审核，不代替用户合并，除非用户再次明确授权。

## 7. 完成定义

- 实现与确认的范围一致，未解决的偏差已明确记录。
- 新增或修改行为有与当前测试基础相匹配的验证。
- 与改动范围和风险匹配的自动化检查通过；只有当前任务准备创建 PR 时才要求完整 `npm run check`。若环境阻塞，准确报告未执行项和原因。
- 受影响的 API、配置、部署和文档同步完成。
- 没有真实用户数据、凭据、构建产物或无关文件进入提交。

## 8. 原型与简历产品约束

- 可自行运行本地服务时，由 Agent 启动并打开预览，不把启动步骤转交给用户。
- 大幅视觉修改前，如果视觉来源不清楚或与当前目标不一致，先获取产品设计上下文。
- 从选定效果图实现时，以效果图的布局、组件结构、密度、间距、色彩、字体、可见内容和层级为准。
- 用户给出可长期复用的原型设计反馈、偏好或决策时，更新本文。
- 默认简历模板使用虚构示例内容，当前姓名为“张三”，不得包含用户真实简历或联系方式。
- 默认简历使用精致的中文衬线字体栈，不使用已移除的 Google CJK serif 字体族。
- 暴露在 UI 中的霞鹜文楷等可选字体必须作为 Web Font 打包，不能依赖系统安装。
- 左右结构的简历行不得自动加粗左侧内容；只有 `**text**` 等显式 Markdown 强调才加粗。
- Markdown 标题不自动加粗；默认通过字号、间距和分隔线建立层级。
- 显式 Markdown 粗体必须在网页预览和 PDF 中清晰可见；中文衬线字体需要时允许合成粗体。
- 显式粗体使用中等字重和略浅于正文的墨色，保持清晰但不过重。
- 所见即所得编辑器工具栏不展示固定字号快捷项；全局字号统一通过页面设置调整，避免重复入口。
- 左右布局以旧版 `::: left` / `::: right` 的渲染语义为准：转换当前正文行时保留原内容到左栏，右栏立即显示可输入状态并获得光标；聚焦时必须有清晰但不进入导出效果的分栏提示。
- 登录、简历主页和简历编辑器使用可恢复的独立 URL：`/login`、`/resumes`、`/resumes/:resumeId/edit`；编辑页刷新、收藏及浏览器前进后退必须保持当前简历定位。
- 管理端页面以 `dev` 的黑白中性设计系统为视觉基线，并采用可打断弹簧、按下即时反馈、半透明材质和完整无障碍降级；管理端登录应保持克制、可信的内部工具气质，避免巨型营销口号和宣传式数据堆叠。
- 所见即所得编辑器聚焦时不显示包围整张 A4 内容区的浏览器默认外框；保留光标、文本选区和左右分栏等局部编辑提示。
- “智能一页”必须在简历编辑器中保留清晰、可直接操作的入口和选中状态，并继续控制连续单页与标准 A4 分页两种 PDF 导出模式。
- 简历编辑工作台必须支持 `Command/Ctrl + 滚轮` 缩放纸张预览；普通滚轮仍只负责滚动，缩放比例不得影响 PDF 的实际页面尺寸。
