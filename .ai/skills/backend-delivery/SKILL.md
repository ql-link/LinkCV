# 后端七维判断与分层交付

## 1. 定位

本技能是纯后端和前后端混合任务的唯一领域编排入口。当前对话的 Sol（主 Agent）拥有七维判断、后端路径选择、工作包规划与拆分、Luna 调度、最终整合和复核，但复用现有专项 Skill，不重新定义方案文档、代码实施、测试或质量规则。

```text
flow-router
  → Sol（当前对话主 Agent）完成七维判断、方案与工作包拆分
      ├── 澄清 / 调查 / module-planning
      ├── 直接实现 → Sol 按工作包调度一个或多个 Luna 使用 implementation-execution
      └── 方案先行 → 主 Agent 使用 solution-generator
                         → 用户确认 solution.md 与后续路径
                         → acceptance-generator（按需）
                         → Sol 按工作包调度一个或多个 Luna 使用 implementation-execution
  → frontend-delivery（混合任务的 UI）
  → Sol 整合、验证与质量审查
```

Sol（主 Agent）始终拥有用户沟通、授权边界、七维判断、方案、工作包拆分、Luna 调度、工作区协调、实施整合复核和最终结论。不要为了满足工作流形式启动同级 Sol，也不要把同一后端任务交给多个同级 Sol 重复读取和规划。确认后的实施可以交给一个或多个 Luna；Luna 不能创建分支、提交、推送、PR 或修改外部系统。

## 2. 进入条件与用户选择

适用于：

- `flow-router` 已判为纯后端或前后端混合任务；
- 用户明确调用本技能；
- 已有匹配的 `solution.md`，需要恢复后端或混合交付。

纯前端页面、组件、布局或视觉任务使用 `frontend-delivery`。解释、只读调查或审查请求不因为涉及后端就自动进入代码交付；纯故障定位先用 `incident-triage`。

来源可以是用户当前请求、可读取的 Issue、飞书文档或其他明确材料；存在 Issue 时完整读取，没有 Issue 不阻止七维判断或交付。

用户明确给出的 `工作流`、`路径` 和 `后续` 选择优先并立即生效：

- `路径：直接实现`：七维判断只识别阻塞事实、严格检查和实施边界，不静默升级为方案先行；确实缺少会改变结果的决定时停止并指出缺口；
- `路径：方案先行`：七维判断不降级为直接实现，继续生成或修订 `solution.md`；
- `路径：自动`：由第 5 节映射路径；
- `工作流：关闭`：不创建 Spec、不展示七维路径，由主 Agent 给出最小实施边界后交 Luna 使用 `implementation-execution` 施工；七维判断不作为形式门禁，但安全、数据和授权底线仍适用。

已有 `solution.md` 时不重复决定是否需要方案；重新读取当前请求、Spec、Git 差异和真实代码，只有新证据使领域或核心路径失效时才重新判断。

## 3. Sol（主 Agent）七维判断

自动或开启工作流时，由当前对话的 Sol（主 Agent）完成判断。不得仅因为需要七维判断、方案先行、严格风险或任务复杂而创建同级 Sol Agent。

Sol 读取 `AGENTS.md`、真实入口、直接消费方、配置、邻近测试、来源材料、授权边界和需要保护的工作区差异，然后：

1. 完成第 4 节全部七维判断，区分事实、未知和用户选择；
2. 得到准备、复杂度、风险、记录、主导原因、严格检查、路径和唯一下一站；
3. 直接实现时形成会话内的目标、边界、真实文件和最小验证，不创建 Spec；
4. 方案先行时直接使用 `solution-generator` 创建或修订唯一的 `.specs/<KEY>/solution.md`，并以它为拆分和调度依据；
5. 用户回答问题后继续复用当前对话与已经核实的代码上下文，不通过同级 Sol 交接重建上下文。

## 4. 七个判断维度

准备程度、复杂度、风险和记录需要必须分开表达。文件数量、预估工时、业务优先级和风险高低都不能单独代表任务复杂度。七个维度仍必须在内部完整判断，但默认只向用户展示路径、主导原因和额外检查。

### 4.1 准备程度

- `可实施`：能识别稳定目标并选择路径。直接实现还要求边界、授权和可观察结果足够清楚；方案先行允许把已识别的业务或技术选择交给方案阶段确认；
- `需澄清`：缺少的用户选择会改变任务目标、是否开发或后端路径；
- `需调查`：目标清楚，但根因、真实影响面或可行性需要只读证据。

整个模块服务谁、解决什么问题或商业前提尚未成形时转 `module-planning`。普通单需求选择由本技能或 `solution-generator` 收敛，不把方案内部问题误判为模块规划。

### 4.2 影响面与相互牵连

- 简单：局部职责、单一消费方、一次修改且容易回退；
- 中等：多个已知文件或模块需要同步，消费方已找全，可以一次实施和验证；
- 复杂：跨独立应用或外部消费方、消费方未知、兼容窗口、分步迁移、部署顺序或多个相互依赖的交付单元。

### 4.3 规则与状态关系

- 简单：一个主要结果和少量独立校验，没有状态或角色相互作用；
- 中等：几条明确分支可以用短清单表达，失败结果相互独立；
- 复杂：多角色、多状态、并发、重试、恢复、跨端一致性或失败副作用相互影响。

### 4.4 实现确定程度

- 简单：沿用已核实的实现和测试模式；
- 中等：存在有界、可逆的实现选择，不引入新架构、基础设施或长期兼容负担；
- 复杂：可行性未知，需要新架构、新依赖、外部服务、技术试验、数据迁移或复杂回退设计。

### 4.5 验证难度

- 简单：邻近测试或一次明确观察即可覆盖；
- 中等：需要多个测试层或一次真实环境检查，但环境稳定、结果明确；
- 复杂：依赖多个真实服务、生产式数据、长时间观察、难稳定复现的并发或外部系统协作。

### 4.6 风险与可回退性

- `常规`：影响局部、可逆，不涉及关键权限、数据和外部承诺；
- `严格`：涉及权限、安全、隐私、凭据、数据迁移或丢失、公开接口消费者、生产切换、计费或不可逆操作。

严格风险本身不自动升级为方案先行，也不自动启动独立 Agent；只增加命中的确认、失败结果、回退或不可逆说明和针对性验证。权限语义未确认时由准备程度阻止直接实施；兼容窗口、迁移顺序或复杂回退由对应复杂度维度决定路径。

### 4.7 持续性与协作

- `会话内`：当前会话可以由一个协调者完成，来源、Git 差异和最终摘要足以恢复；
- `持久记录`：预计跨会话、正式交接、并行协作、多个检查点，或用户明确要求保留当前计划。

记录需要不改变复杂度或风险，记录需要不改变交付路径。方案任务由 `solution.md` 承担持久上下文；直接实现从当前请求、来源、七维简报、Git 差异和真实代码恢复，不为了记录倒写方案。

## 5. 复杂度和路径映射

复杂度只使用 4.2 至 4.5 四个维度，不做加权总分：四项全部简单才是`简单`；任一项命中明确复杂信号就是`复杂`；其余是`中等`。

自动路径按顺序选择：

1. 模块目标或商业前提尚未形成：`module-planning`；
2. 准备为`需澄清`或`需调查`：提出一个会改变结果的关键问题，或完成一次最小只读调查后重评；
3. 复杂任务：`方案先行`；
4. 简单任务：`直接实现`；
5. 中等任务只有目标和结果已收敛、消费方找全、实现可逆、不需要分阶段兼容或迁移、验收可用短清单表达时才`直接实现`，否则`方案先行`。

数据库 schema 或数据迁移通常命中迁移顺序、存量数据、兼容和回退，因此默认方案先行；不是因为数据库标签本身是一票升级条件。记录为持久记录也不自动升级方案。

## 6. 七维输出和方案门禁

默认只向用户展示三行：

```text
路径：直接实现 | 方案先行 | 模块规划 | 暂不进入开发路径
原因：<只写一个决定当前路径的主导事实>
额外检查：无 | <权限、数据、兼容、人工验收或回退检查>
```

只有准备不足、风险严格、需要持久记录或用户主动要求查看判断依据时展开：

```text
准备：可实施 | 需澄清 | 需调查
领域：纯后端 | 前后端混合
复杂度：简单 | 中等 | 复杂 | 暂不判定（主导原因）
风险：常规 | 严格（具体触发项）
记录：会话内 | 持久记录（原因）
路径：直接实现 | 方案先行 | 模块规划 | 暂不进入开发路径
维度依据：影响面=<事实>；规则关系=<事实>；实现确定=<事实>；验证难度=<事实>
预计影响：<模块、消费方、契约、数据、权限或部署范围>
未确认项：<没有则写“无”>
下一站：<澄清、调查、module-planning、implementation-execution 或 solution-generator>
```

路径为方案先行时，Sol 完整使用 `solution-generator`。没有用户对当前 `solution.md` 和后续路径的明确确认，不得施工。选择契约验收时，先使用 `acceptance-generator` 创建或修订 `acceptance.feature` 并取得确认；选择直接施工时不创建该附件。

混合任务的 `solution.md` 固定业务结果、API、权限、数据、状态与失败语义，并列出前端可观察结果；前端只消费用户提供的原型或 Figma 输入，由 `frontend-delivery` 做原型映射和工作包交接，不得让视觉材料改写业务契约。

## 7. Sol 调度 Luna 实施与复核

直接实现使用七维简报，方案任务使用已确认的 `solution.md` 和适用 Acceptance。Sol 先把实现拆成边界清楚的工作包，再决定由多少个 Luna 承担；不固定 Luna 数量，也不为了并行而拆分本来紧密耦合的任务。

实施前每个工作包必须明确：

1. 目标、可观察结果、契约和安全边界；
2. 允许与禁止文件、文件所有权、依赖、严格检查和最小验证；
3. 仍会改变权限、数据、兼容、迁移或失败语义的选择已经由 Sol 收敛；
4. Luna 只执行确认范围，不重新规划任务或替其他工作包改写契约。

Sol 根据 `solution.md`、依赖、写冲突和工作包边界调度：可独立、边界清楚、文件所有权不重叠且没有未满足前置依赖的工作包可以并行交给多个 Luna；共享契约、迁移链、同一核心文件或存在前后依赖的工作包必须串行。并行时每个 Luna 只能写自己的所有权范围，不能借并行修改共享契约或其他工作包的文件。

每个工作包的实施 Agent 使用：

- `model`: `gpt-5.6-luna`
- `reasoning_effort`: `max`
- `fork_turns`: `none` 或必要的有限轮次。

每个 Luna 必须完整使用 `implementation-execution`，读取当前实施依据、允许和禁止文件、严格检查、依赖与最小验证。Sol 汇总多个 Luna 的实际差异和测试证据并复核整合结果；发现实现问题时给出具体失败证据和修正边界。失败后由 Sol 判断继续原 Luna，还是把未完成工作重新分派给另一个 Luna；不得引入同级 Sol，也不能由 Sol 静默改写代码来掩盖问题。

严格风险由 Sol 完成判断和方案约束，再由 Luna 按明确工作包实施；不因权限、迁移、生产切换、凭据、数据丢失、并发或事务自动启动同级 Sol。用户明确要求第二模型审查时，才按该次授权执行独立审查，不把它写入默认交付主链。

混合任务的后端、契约和配置工作包完成并稳定后，把前端结果与不可改写契约交给 `frontend-delivery`；若前后端工作包无共享写入且依赖已满足，Sol 可以分别调度，但共享契约仍按串行规则处理。

## 8. 回流与完成

- 发现任务其实是纯前端，或领域边界改变：返回 `flow-router`；
- 准备、复杂度、风险、记录或后端路径变化：留在本技能，只重评受影响维度；
- 方案中的业务、权限、数据、兼容或发布决定变化：由主 Agent 使用 `solution-generator` 修订并确认；
- 整个模块目标或商业前提失效：转 `module-planning`；
- 普通文件组织、命名、测试落点或不改变外部结果的差异继续实施，按重要性在 PR 说明。

Sol 最后检查完整差异，对照七维简报或方案核实结果，进入 `run-all-tests`、适用的 `manual-acceptance` 和 `code-review-and-quality`。用户另行授权 Git 交付时才进入 `branch-pr-workflow`。最终说明七维路径、工作包拆分与 Luna 实施范围、完成结果、真实验证、未覆盖区域和遗留项。
