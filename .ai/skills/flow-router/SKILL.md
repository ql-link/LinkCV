# 交付路径分流

## 1. 职责

本技能是代码交付链的入口，只回答一个问题：**这次改动进实现之前，需要先产出什么。**

三个可能的答案，互斥且穷尽：

| 结论 | 含义 | 下一站 |
| --- | --- | --- |
| `直接实现` | 不建 `.specs`，直接改代码并按改动范围验证 | `implementation-execution` |
| `方案先行` | 先产出并冻结方案文档，再按方案文档选定的后续路径推进 | `solution-generator` |
| `模块规划` | 模块目标或商业前提尚未成形，先把它谈清楚 | `module-planning` |

本技能只负责这一次判断，不负责：

- 创建或修改 `.specs` 产物；
- 决定方案文档冻结之后走哪条路径（那是 `solution-generator` 在方案定稿时和用户一起决定的）；
- 判断方案文档各章节要写到多细（由文档实际涉及的内容触发，见 `solution-generator`）；
- 主持模块方案讨论或撰写飞书详情文档；
- 编写实现代码；
- 修改任意平台的 Issue；
- 创建分支、提交或 PR。

## 2. 使用边界

适合使用：

- 用户提出新增功能、缺陷修复、重构、迁移或配置改动，但尚未确定走哪条路径；
- 用户询问某个改动是否需要方案文档；
- 已经开始的实现暴露出更大的影响面，需要重新分流。

不必使用：

- 已经存在有效的 `.specs/<KEY>/state.yaml`；改用 `npm run spec -- status <KEY>` 恢复下一站；
- 用户在当前请求中已经明确指定路径或关闭工作流；采用用户选择，最多说明一次风险，不重新分流；
- 用户明确要求先讨论模块或撰写飞书模块详情；直接进入 `module-planning`，即使请求中同时指定了路径；
- 用户只要求解释、审查、排障或报告状态，没有要求改代码；
- 用户已经明确进入某个下游阶段，且没有出现影响面扩大的新证据。

## 3. 分流前必须核实

1. 读取 `AGENTS.md`、来源 Issue 的完整正文和关联材料。Issue 可以来自 Multica、Linear、GitHub 或其他系统，平台不得影响分流结论；普通团队任务没有 Issue 时先报告缺失，用户明确关闭工作流、自举或本地维护请求除外。
2. 已有飞书周开发文档或详情文档时完整读取，并把它与 Issue 正文一起作为产品输入。两者冲突、详情文档尚未确认或存在阻塞性决策时，只识别缺口并转 `module-planning`，不在本技能内盘问或改写文档。
3. 检查最小必要代码面，至少确认预计修改的入口、相邻模块和现有测试。
4. 不根据预估代码行数分流。以契约、数据、权限、跨端和回滚风险为主要依据。
5. 信息不足时，只提出会改变分流结论的关键问题；路径可以判定但产品细节仍未收敛时，保持分流结论并把内容问题留给 `solution-generator`。

## 4. 分流判据

### 直接实现

**同时满足**以下全部条件才能判为直接实现：

- 改动局限于单个局部实现、文案、样式、测试或低风险配置；
- 不改变用户可感知的完整业务流程；
- 不改变 HTTP 接口、共享类型、错误语义或环境变量契约；
- 不涉及鉴权、资源归属、数据库、迁移、对象存储或数据完整性；
- 不涉及 React、FastAPI、Vite 代理和部署配置之间的联动。

有一条不满足就不是直接实现。这条路径不产出任何文档，也不进入 `.specs` 状态机，因此它的准入必须严格；"看起来不复杂"不是依据。

Issue 正文已经清楚说明目标、边界和可观察结果时，直接据此实现；已有详情文档时仍必须一并读取。

### 方案先行

不满足直接实现的全部条件，且模块目标本身是清楚的，就判为方案先行。典型信号：

- 改变一个前端或后端模块中的完整行为，或新增有明确边界的用户能力、校验规则、失败路径；
- 同时改动前端和后端，或改变两端共享的接口、类型、错误或状态语义；
- 新增或修改鉴权、权限、资源所有权或敏感信息处理；
- 修改数据库模型、迁移、事务、唯一性、关联关系或数据修复逻辑；
- 修改对象存储、文件访问、持久化边界或数据完整性规则；
- 改变 FastAPI 路由归属、Vite Proxy、HTTP 兼容窗口或切换方式；
- 环境变量、Vite 代理、部署配置和运行时行为需要同步改变；
- 需要灰度、数据迁移、兼容旧版本或明确回滚顺序；
- 影响面仍不确定，判错可能导致数据、安全或发布风险。

存在待确认的业务规则或技术取舍**不构成**转 `module-planning` 的理由——这类问题由 `solution-generator` 在写方案文档时逐个向用户确认。

### 模块规划

只在整个模块的**目标或商业前提本身尚未成形**时使用：不是若干个可以逐一回答的具体问题，而是还说不清这个模块要解决谁的什么问题。用户要求先把结论沉淀到飞书供他人协作时同样走这条。

## 5. 判定步骤

1. 列出预计受影响的文件、模块和外部契约。
2. 先判断模块目标是否成形；不成形直接转 `模块规划`，不进入后两步。
3. 再逐条核对直接实现的五个条件；**任意一条不满足即判方案先行**，不做加权、不做折中。
4. 只有五条全部满足才判直接实现。
5. 区分"影响分流的事实"和"内容缺口"：前者由本技能查证，后者交给下一站。
6. 实现过程中发现新的高风险影响时，立即改判方案先行并回到 `solution-generator`，不得以"已经开始编码"为理由维持直接实现。

数据库改动一律走方案先行。物理表结构在方案文档的数据模型章节使用 `mysql-ddl-conventions` 定稿，迁移在实施阶段使用 `alembic-migration` 落地和验证；这两个专项技能不替代方案文档。纯故障排查不进入分流，先转 `incident-triage`；确认需要改代码或配置后再回本站。

## 6. 输出格式

每次分流至少给出：

```text
路径：直接实现 | 方案先行 | 模块规划
判定依据：<对应本技能中的具体判据和仓库证据>
预计影响：<模块、契约、数据、权限或部署范围>
未确认项：<会改变分流结论的假设；没有则写“无”>
下一站：<implementation-execution、solution-generator 或 module-planning，以及进入条件>
```

判为方案先行时，不要顺带预测方案文档之后走哪条路径，也不要预设文档要写多细——这两件事都在方案定稿时才有足够信息决定。

不要只输出路径名称，也不要在证据不足时用"看起来不复杂"作为走直接实现的理由。
