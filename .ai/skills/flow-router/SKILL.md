# 后端七维判断与分层交付

## 1. 定位

本技能是后端交付范围的唯一入口。它先用最小代码证据确认当前请求是否存在后端范围，再在同一上下文中继续七维判断和交付，不产生中间路由结果。纯后端任务处理完整范围；前后端混合任务只处理其中的 FastAPI、数据、公共契约、配置、迁移、部署和必要消费方契约同步。当前 Codex 拥有范围判断、七维判断、后端路径选择、实施顺序、代码修改、验证、整合和复核，但复用现有专项 Skill，不重新定义方案文档、代码实施、测试或质量规则。

本技能可以识别前端消费方并约束后端必须提供的可观察契约，但不负责决定、实施或验收前端页面，也不调用前端能力。混合需求中的前端工作由当前任务在本技能之外独立处理，不是后端交付链的下一阶段。

```text
当前请求（明确或可能涉及后端）
  → 当前 Codex 完成七维判断并确定实施边界
      ├── 澄清 / 调查 / 暂不进入开发路径
      ├── 直接实现 → 当前 Codex 使用 implementation-execution
      └── 方案先行 → 当前 Codex 使用 solution-generator
                         → 用户确认 solution.md 与后续路径
                         → acceptance-generator（按需）
                         → 当前 Codex 使用 implementation-execution
  → 当前 Codex 验证与质量审查
```

当前 Codex 始终拥有用户沟通、授权边界、七维判断、方案、实施、工作区协调、验证、复核和最终结论。不要为了满足工作流形式创建实施子 Agent、重复读取上下文或等待另一模型执行命令；只有用户明确要求独立审查或并行 Agent 工作时，才按该次授权使用子 Agent，且不把它加入默认交付主链。

## 2. 进入条件与用户选择

适用于：

- 请求直接修改或可能修改 FastAPI、服务、持久化、数据库、公共 API、权限、后端配置或部署行为；
- 前端开发中发现必须新增或改变请求、响应、共享类型、权限、数据、错误语义、代理或部署契约；
- 用户明确调用本技能；
- 已有匹配的 `solution.md`，需要恢复后端或混合交付。

进入后只读取当前请求、预计修改入口、直接消费方和判断公共契约所需的最小代码。确认没有后端交付范围时立即退出，由当前 Codex 按普通前端任务处理；确认存在后端范围时，标记为纯后端或前后端混合并直接继续第 3 节，不再调用另一层入口。文件位置不能单独决定范围：前端 API Client 跟随后端契约变化属于混合任务，仅调整页面并复用现有接口仍是纯前端。

解释、只读调查或审查请求不因为涉及后端就自动进入代码交付；纯故障定位先用 `incident-triage`。

来源可以是用户当前请求、可读取的 Issue 或用户明确指定的外部材料；存在 Issue 时完整读取，没有 Issue 不阻止七维判断或交付。项目工作流不负责创建或回写外部规划文档。

用户明确给出的 `工作流`、`路径` 和 `后续` 选择优先并立即生效：

- `路径：直接实现`：七维判断只识别阻塞事实、严格检查和实施边界，不静默升级为方案先行；确实缺少会改变结果的决定时停止并指出缺口；
- `路径：方案先行`：七维判断不降级为直接实现，继续生成或修订 `solution.md`；
- `路径：自动`：由第 5 节映射路径；
- `工作流：关闭`：不创建 Spec、不展示七维路径，由当前 Codex 给出最小实施边界并使用 `implementation-execution` 直接施工；七维判断不作为形式门禁，但安全、数据和授权底线仍适用。

已有 `solution.md` 时不重复决定是否需要方案；重新读取当前请求、Spec、Git 差异和真实代码，只有新证据使领域或核心路径失效时才重新判断。

## 3. 当前 Codex 七维判断

自动或开启工作流时，由当前 Codex 完成判断。不得仅因为需要七维判断、方案先行、严格风险或任务复杂而创建额外 Agent。

当前 Codex 读取 `AGENTS.md`、真实入口、直接消费方、配置、邻近测试、来源材料、授权边界和需要保护的工作区差异，然后：

1. 完成第 4 节全部七维判断，区分事实、未知和用户选择；
2. 得到准备、复杂度、风险、记录、主导原因、严格检查、路径和唯一下一站；
3. 直接实现时形成会话内的目标、边界、真实文件和最小验证，不创建 Spec；
4. 方案先行时直接使用 `solution-generator` 创建或修订唯一的 `.specs/<KEY>/solution.md`，并以它为实施依据；
5. 用户回答问题后继续复用当前对话与已经核实的代码上下文，不通过 Agent 交接重建上下文。

## 4. 七个判断维度

准备程度、复杂度、风险和记录需要必须分开表达。文件数量、预估工时、业务优先级和风险高低都不能单独代表任务复杂度。七个维度仍必须在内部完整判断，但默认只向用户展示路径、主导原因和额外检查。

### 4.1 准备程度

- `可实施`：能识别稳定目标并选择路径。直接实现还要求边界、授权和可观察结果足够清楚；方案先行允许把已识别的业务或技术选择交给方案阶段确认；
- `需澄清`：缺少的用户选择会改变任务目标、是否开发或后端路径；
- `需调查`：目标清楚，但根因、真实影响面或可行性需要只读证据。

整个模块服务谁、解决什么问题或商业前提尚未成形时，暂停开发路径并直接在当前对话中与用户收敛目标，不转入另一个规划 Skill。普通单需求选择由本技能或 `solution-generator` 收敛，不把方案内部问题升级成新的规划阶段。

### 4.2 影响面与相互牵连

- 简单：局部职责、单一消费方、一次修改且容易回退；
- 中等：多个已知文件或模块需要同步，消费方已找全，可以一次实施和验证；
- 复杂：跨独立应用或外部消费方、消费方未知、兼容窗口、分步迁移、部署顺序或多个相互依赖的交付单元。

### 4.3 规则与状态关系

- 简单：一个主要结果和少量独立校验，没有状态或角色相互作用；
- 中等：几条明确分支可以用短清单表达，失败结果相互独立；
- 复杂：多角色、多状态、并发、重试、恢复、跨端一致性或失败副作用相互影响。

### 4.4 实现确定程度

- 简单：沿用已核实的实现和测试模式；
- 中等：存在有界、可逆的实现选择，不引入新架构、基础设施或长期兼容负担；
- 复杂：可行性未知，需要新架构、新依赖、外部服务、技术试验、数据迁移或复杂回退设计。

### 4.5 验证难度

- 简单：邻近测试或一次明确观察即可覆盖；
- 中等：需要多个测试层或一次真实环境检查，但环境稳定、结果明确；
- 复杂：依赖多个真实服务、生产式数据、长时间观察、难稳定复现的并发或外部系统协作。

### 4.6 风险与可回退性

- `常规`：影响局部、可逆，不涉及关键权限、数据和外部承诺；
- `严格`：涉及权限、安全、隐私、凭据、数据迁移或丢失、公开接口消费者、生产切换、计费或不可逆操作。

严格风险本身不自动升级为方案先行，也不自动启动独立 Agent；只增加命中的确认、失败结果、回退或不可逆说明和针对性验证。权限语义未确认时由准备程度阻止直接实施；兼容窗口、迁移顺序或复杂回退由对应复杂度维度决定路径。

### 4.7 持续性与协作

- `会话内`：当前会话可以由一个协调者完成，来源、Git 差异和最终摘要足以恢复；
- `持久记录`：预计跨会话、正式交接、并行协作、多个检查点，或用户明确要求保留当前计划。

记录需要不改变复杂度或风险，记录需要不改变交付路径。方案任务由 `solution.md` 承担持久上下文；直接实现从当前请求、来源、七维简报、Git 差异和真实代码恢复，不为了记录倒写方案。

## 5. 复杂度和路径映射

复杂度只使用 4.2 至 4.5 四个维度，不做加权总分：四项全部简单才是`简单`；任一项命中明确复杂信号就是`复杂`；其余是`中等`。

自动路径按顺序选择：

1. 模块目标或商业前提尚未形成：暂不进入开发路径，在当前对话中确认会改变目标的关键问题；
2. 准备为`需澄清`或`需调查`：提出一个会改变结果的关键问题，或完成一次最小只读调查后重评；
3. 复杂任务：`方案先行`；
4. 简单任务：`直接实现`；
5. 中等任务只有目标和结果已收敛、消费方找全、实现可逆、不需要分阶段兼容或迁移、验收可用短清单表达时才`直接实现`，否则`方案先行`。

数据库 schema 或数据迁移通常命中迁移顺序、存量数据、兼容和回退，因此默认方案先行；不是因为数据库标签本身是一票升级条件。记录为持久记录也不自动升级方案。

## 6. 七维输出和方案门禁

默认只向用户展示三行：

```text
路径：直接实现 | 方案先行 | 暂不进入开发路径
原因：<只写一个决定当前路径的主导事实>
额外检查：无 | <权限、数据、兼容、人工验收或回退检查>
```

只有准备不足、风险严格、需要持久记录或用户主动要求查看判断依据时展开：

```text
准备：可实施 | 需澄清 | 需调查
领域：纯后端 | 前后端混合
复杂度：简单 | 中等 | 复杂 | 暂不判定（主导原因）
风险：常规 | 严格（具体触发项）
记录：会话内 | 持久记录（原因）
路径：直接实现 | 方案先行 | 暂不进入开发路径
维度依据：影响面=<事实>；规则关系=<事实>；实现确定=<事实>；验证难度=<事实>
预计影响：<模块、消费方、契约、数据、权限或部署范围>
未确认项：<没有则写“无”>
下一站：<当前对话澄清、调查、implementation-execution 或 solution-generator>
```

路径为方案先行时，当前 Codex 完整使用 `solution-generator`。没有用户对当前 `solution.md` 和后续路径的明确确认，不得施工。选择契约验收时，先使用 `acceptance-generator` 创建或修订 `acceptance.feature` 并取得确认；选择直接施工时不创建该附件。

混合任务的 `solution.md` 固定业务结果、API、权限、数据、状态与失败语义，并列出后端需要向消费方保证的可观察契约。它不记录 UI 实现步骤，也不编排前端设计、开发或检查；如果前端期望要求改变上述契约，先返回 `solution-generator` 修订并确认受影响决定。

## 7. 当前 Codex 直接实施与复核

直接实现使用七维简报，方案任务使用已确认的 `solution.md` 和适用 Acceptance。当前 Codex 在同一上下文中完整使用 `implementation-execution`，直接修改代码、配置、迁移和测试，不创建默认实施子 Agent，也不为实施指定其他模型或推理强度。

实施前必须明确：

1. 目标、可观察结果、契约和安全边界；
2. 允许与禁止文件、依赖、严格检查和最小验证；
3. 仍会改变权限、数据、兼容、迁移或失败语义的选择已经收敛。

当前 Codex 根据 `solution.md`、依赖关系和共享文件确定实施顺序。共享契约、迁移链、同一核心文件或存在前后依赖的改动按依赖顺序完成；其他改动也留在当前上下文连续实施，不为了并行拆成 Agent 工作包。实现问题在确认范围内直接修正；如果证据表明目标、权限、数据、兼容、迁移或失败语义需要改变，则按第 8 节回流，不通过重新派发来重建上下文。

实施中只在能为下一步提供有效反馈的稳定节点运行最窄检查，不按文件或步骤机械重跑。完整差异稳定后，只执行一次与任务范围匹配的自动化验证、适用的人工验收和质量审查；仍对应当前代码快照的充分结果可以复用。用户明确要求第二模型审查时，才按该次授权执行独立审查，不把它写入默认交付主链。

混合任务中的后端、契约、配置、迁移和部署范围完成并稳定后，本技能的实施阶段结束。前端是否继续实现或检查由当前任务独立决定，不纳入本技能的步骤或完成门禁；共享契约变更仍按依赖顺序处理。

## 8. 回流与完成

- 发现任务没有后端交付范围：退出本技能，按普通前端任务处理；范围仍不明确时留在本技能完成一次最小只读调查后重评；
- 准备、复杂度、风险、记录或后端路径变化：留在本技能，只重评受影响维度；
- 方案中的业务、权限、数据、兼容或发布决定变化：由当前 Codex 使用 `solution-generator` 修订并确认；
- 整个模块目标或商业前提失效：暂停开发路径，在当前对话中重新确认目标；
- 普通文件组织、命名、测试落点或不改变外部结果的差异继续实施，按重要性在 PR 说明。

当前 Codex 最后检查本技能负责范围内的完整差异，对照七维简报或方案核实结果，只进入一次任务级 `run-all-tests`、适用的 `manual-acceptance` 和 `code-review-and-quality`。选择命令时复用仍对应当前代码快照的验证证据，只补尚未覆盖的检查，不重复执行相同范围。用户另行授权 Git 交付时才进入 `branch-pr-workflow`。最终说明七维路径、实施范围、完成结果、真实验证、未覆盖区域和遗留项；混合任务不得把尚未核实的前端结果计入后端完成结论。
