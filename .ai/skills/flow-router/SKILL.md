# 交付流程分级

## 1. 职责

本技能是代码交付链的入口。先判断改动需要多少前置设计和审核，再把任务交给对应技能，避免小改动套用完整流程，也避免高风险改动绕过规格约束。

本技能只负责分级，不负责：

- 创建或修改 `.specs` 产物；
- 编写实现代码；
- 修改任意平台的 Issue；
- 创建分支、提交或 PR。

## 2. 使用边界

适合使用：

- 用户提出新增功能、缺陷修复、重构、迁移或配置改动，但尚未确定车道；
- 用户询问某个改动是否需要需求简报、验收契约或技术设计；
- 初步判断与真实代码影响面不一致，需要重新分级。

不必使用：

- 已经存在明确车道和有效的 `.specs/<KEY>/state.yaml`；
- 用户只要求解释、审查、排障或报告状态，没有要求改代码；
- 用户已经明确进入某个下游阶段，且没有出现影响面扩大的新证据。

## 3. 分级前必须核实

1. 读取 `AGENTS.md`、来源 Issue 的完整正文和关联材料。Issue 可以来自 Multica、Linear、GitHub 或其他系统，平台不得影响分级结论；普通团队任务没有 Issue 时先报告缺失，用户明确关闭工作流、自举或本地维护请求除外。
2. 已有飞书周开发文档或详情文档时完整读取，并把它与 Issue 正文一起作为产品输入。两者冲突时先确认哪份是较新的有效结论，不静默取舍。
3. 检查最小必要代码面，至少确认预计修改的入口、相邻模块和现有测试。
4. 不根据预估代码行数分级。以契约、数据、权限、跨端和回滚风险为主要依据。
5. 信息不足时，只提出会改变车道结论的关键问题；能够通过 Issue、详情文档或仓库事实确认的，不询问用户。

## 4. 车道判据

### L1：局部快车道

同时满足以下条件才能判为 L1：

- 改动局限于单个局部实现、文案、样式、测试或低风险配置；
- 不改变用户可感知的完整业务流程；
- 不改变 HTTP 接口、共享类型、错误语义或环境变量契约；
- 不涉及鉴权、资源归属、数据库、迁移、对象存储或数据完整性；
- 不涉及 React、FastAPI、Express、Vite 代理和部署配置之间的联动。

典型下一站：`implementation-execution`。

Issue 正文已经清楚说明目标、边界和可观察结果时，L1 可以直接据此实现；已有详情文档时仍必须一并读取。不能因为 Issue 来自某个平台而升级或降级。

### L2：单模块标准车道

符合以下特征，且没有命中 L3 强信号时，判为 L2：

- 改变一个前端或后端模块中的完整行为；
- 新增有明确边界的用户能力、校验规则或失败路径；
- 存在局部契约调整，但影响方单一、兼容和回滚路径清楚；
- 需要先冻结范围与可观察验收标准，但不需要独立的跨模块技术设计。

范围已经清楚时进入 `brief-generator`，由它从来源 Issue 和相关详情文档生成本地需求简报；Issue 信息不足或存在会改变范围或行为的阻塞性选择时，先补齐飞书详情材料并使用 `decision-grilling` 收敛，再生成需求简报。

### L3：跨模块或高风险车道

命中任一项即判为 L3：

- 同时改动前端和后端，或改变两端共享的接口、类型、错误或状态语义；
- 新增或修改鉴权、权限、资源所有权或敏感信息处理；
- 修改数据库模型、迁移、事务、唯一性、关联关系或数据修复逻辑；
- 修改对象存储、文件访问、持久化边界或数据完整性规则；
- 改变 Express 与 FastAPI 的路由归属、兼容窗口或切换方式；
- 环境变量、Vite 代理、部署配置和运行时行为需要同步改变；
- 需要灰度、数据迁移、兼容旧版本或明确回滚顺序；
- 影响面仍不确定，但错误分级可能导致数据、安全或发布风险。

范围已经清楚时进入 `brief-generator`；Issue 信息不足或存在阻塞性选择时，先补齐飞书详情材料并使用 `decision-grilling`。完整链路随后为 `brief-generator` → `acceptance-generator` → `technical-design` → `implementation-execution`。

## 5. 判定步骤

1. 列出预计受影响的文件、模块和外部契约。
2. 先检查 L3 强信号；命中后不再向下压级。
3. 未命中 L3 时，判断是否形成完整的模块行为变化；是则判 L2。
4. 只有同时满足全部 L1 条件时才判 L1。
5. 区分事实缺口和决策分歧：事实通过仓库探索解决；会改变范围、行为、契约、数据或兼容策略的选择转 `decision-grilling`。
6. 实现过程中发现新的高风险影响时，立即升级车道并回到相应上游阶段，不得以“已经开始编码”为理由维持低车道。

数据库任务判为 L3 后仍先走完整规格链。在技术设计中使用 `mysql-ddl-conventions` 确认物理 schema，在实施时使用 `alembic-migration` 落地和验证；这两个专项技能不替代 Brief、Acceptance 或 Technical Design。纯故障排查不进入车道分级，先转 `incident-triage`；确认需要修改代码或配置后再回本站分级。

## 6. 输出格式

每次分级至少给出：

```text
车道：L1 | L2 | L3
判定依据：<对应本技能中的具体判据和仓库证据>
预计影响：<模块、契约、数据、权限或部署范围>
未确认项：<会改变分级的假设；没有则写“无”>
下一站：<decision-grilling、brief-generator 或 implementation-execution，以及进入条件>
```

不要只输出车道字母，也不要在证据不足时用“看起来不复杂”作为降级理由。
