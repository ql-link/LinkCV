# 交付路径分流

## 1. 职责

本技能在实现前回答六个问题：

1. 任务属于纯前端、纯后端还是前后端混合；
2. 当前信息是否已经足够开工；
3. 任务本身是简单、中等还是复杂；
4. 做错后的风险是常规还是严格；
5. 当前会话是否足以承载任务，还是需要本地持久记录；
6. 在现有交付能力下，下一站应当是什么。

准备程度、复杂度、风险和记录需要必须分开表达。文件数量、预估工时、业务优先级和风险高低都不能单独代表任务复杂度。

七个维度仍必须在内部完整判断，但不要求把内部检查表每次都展示给用户。默认只交付路径、一个主导原因和真正需要追加的检查。

当前仍保留三种分流结果：

| 路径 | 含义 | 下一站 |
| --- | --- | --- |
| `直接实现` | 不建 `.specs`，按领域直接改代码并验证 | 纯前端转 `frontend-delivery` 轻量或标准路径；纯后端转 `implementation-execution` |
| `方案先行` | 后端或混合任务先确认 `solution.md`；纯前端完整任务先确认 `ui-design.md` | 后端或混合转 `solution-delegated-delivery`；纯前端转 `frontend-delivery` |
| `模块规划` | 整个模块的目标或商业前提尚未成形，或需要先形成供多人协作的飞书详情文档 | `module-planning` |

准备不足时可以暂不进入任何开发路径：缺少一个会改变结果的选择时先澄清；问题原因或可行性未知时先做只读调查。它们不是新的分流结果。

本技能不负责：

- 创建或修改 `.specs` 产物；
- 决定方案文档确认后走直接施工还是契约验收；
- 判断方案文档各章节写多细；
- 主持模块讨论或撰写飞书详情文档；
- 编写实现代码；
- 修改任意平台的 Issue；
- 创建分支、提交或 PR。

## 2. 使用边界

适合使用：

- 用户提出新增功能、缺陷修复、重构、迁移或配置改动，但尚未确定路径；
- 用户询问某个改动是否需要方案文档；
- 实现中出现新证据，需要重新判断复杂度、风险或记录方式。

不必使用：

- 已经存在与当前任务匹配的中心文档：后端或混合任务的 `solution.md`，或纯前端任务的 `ui-design.md`；直接读取 Spec、Git 差异和真实代码判断下一步，只有新证据改变分流结论时才重新使用本技能；
- 用户在当前请求中已经明确指定路径或关闭工作流；采用用户选择，最多说明一次风险；
- 用户明确要求先讨论模块或撰写飞书模块详情；直接进入 `module-planning`；
- 用户只要求解释、审查、排障或报告状态，没有要求改代码；
- 用户已经进入下游工作，且没有影响判断的新证据。

## 3. 分流前必须核实

1. 读取 `AGENTS.md`、用户当前请求和明确指定的材料。有 Issue 时完整读取正文和关联材料；没有 Issue 不阻止分流，也不改变复杂度、风险或路径。
2. 尚未形成 `solution.md` 且已有飞书周开发文档或详情文档时完整读取，并核对初始来源是否冲突；已存在匹配方案时按上一节直接读取方案，不重新把飞书提升为平级依据。
3. 检查最小必要代码面，至少确认预计修改的入口、相邻职责边界、真实消费方和现有测试。
4. 区分能从仓库核实的事实、需要只读调查的未知，以及必须由用户决定的选择。
5. 不根据代码行数、文件数、预估工时或“看起来很大”判断复杂度。

### 3.1 先确定任务领域

- `纯前端`：只改变 `apps/web` 的页面、组件、交互呈现、布局、样式或前端内部状态，并沿用既有 API、权限、数据和错误语义；
- `纯后端`：只改变 FastAPI、服务、持久化、任务处理、后端配置或其他不含用户界面实施的行为；
- `前后端混合`：新增或改变请求、响应、共享类型、权限、数据、错误语义、代理或部署契约，同时需要前端呈现或消费。

文件位置不能单独决定领域：前端 API client 跟随后端契约变化属于混合任务；后端仅提供既有接口而页面独立调整仍是纯前端。扩展、小程序和 PDF 按实际应用边界单独判断，不自动并入 Web 前端流程。

## 4. 七个判断维度

### 4.1 准备程度

准备程度是开工门槛，不参与复杂度分级：

- `可实施`：已经能确认这是一个边界清楚的开发任务，并能选择下一条路径。直接实现还要求目标、明确不做的内容、修改授权和可观察完成结果足够清楚；方案先行允许把已经识别出的业务规则或技术取舍交给方案编写过程继续确认；
- `需澄清`：缺少的选择使任务目标本身无法成立，或会改变是否进入开发、进入哪条路径；
- `需调查`：问题目标清楚，但根因、真实影响面或可行性需要先用只读证据确认。

整个模块服务谁、解决什么问题或商业前提都尚未成形时，输出 `需澄清` 并转 `模块规划`。普通的单个业务选择不需要模块规划：如果它会阻止直接实现，就提出一个最关键问题；如果任务已经明确属于方案先行，就把问题列入 `未确认项` 并交给 `solution-generator`，不要由分流阶段提前主持方案讨论。

### 4.2 影响面与相互牵连

只判断职责边界、消费方以及实施顺序，不按文件数量判断：

- 简单信号：局部职责边界、消费方单一、可以一次修改和直接回退；
- 中等信号：多个已知文件或模块需要同步，所有消费方都已找全，可以一次实施、一次验证；
- 复杂信号：跨多个独立应用或外部消费方，消费方仍不确定，需要兼容窗口、分步迁移、部署顺序或多个相互依赖的交付单元。

### 4.3 规则与状态关系

只判断业务规则之间是否相互影响，不机械计算分支数量：

- 简单信号：一个主要结果和少量独立校验，没有状态或角色相互作用；
- 中等信号：存在几条明确分支，但可以用短清单表达，失败结果相互独立；
- 复杂信号：多角色、多状态、并发、重试、恢复、跨端一致性或失败副作用相互影响，需要一组可独立确认的验收规则。

### 4.4 实现确定程度

判断仓库中是否已有可靠实现路径：

- 简单信号：沿用已经核实的实现和测试模式；
- 中等信号：存在有界、可逆的实现选择，不引入新架构、基础设施或长期兼容负担；
- 复杂信号：可行性未知，需要新架构、新依赖、外部服务、技术试验、数据迁移或复杂回退设计。

### 4.5 验证难度

判断如何证明结果正确，不把“需要测试”本身视为复杂：

- 简单信号：现有邻近测试或一次明确观察即可覆盖；
- 中等信号：需要多个测试层或一次真实浏览器、设备检查，但环境稳定、结果明确；
- 复杂信号：依赖多个真实服务、生产式数据、长时间观察、难稳定复现的并发条件或外部系统协作。

### 4.6 风险与可回退性

风险衡量做错后的后果，不参与简单、中等、复杂的计算：

- `常规`：影响局部、可逆，不涉及关键权限、数据和外部承诺；
- `严格`：涉及权限、安全、隐私、凭据、数据迁移或丢失、公开接口已有消费者、生产切换、计费、不可逆操作。

严格风险只增加命中的必要确认、失败结果、回退或不可逆说明、针对性验证和责任审阅。严格风险本身不自动升级为方案先行；一行权限修复可以是“简单 + 严格”。如果权限语义尚未确认，由准备程度或规则复杂度阻止直接实施；如果存在兼容窗口、迁移顺序或复杂回退，则由相应复杂度维度进入方案。

### 4.7 持续性与协作

只判断是否需要持久记录，不参与复杂度分级：

- `会话内`：预计当前会话完成，由一个协调者推进，来源、Git 差异和最终摘要足以恢复；
- `持久记录`：预计跨会话、正式交接、并行协作、多个检查点，或用户明确要求保留当前计划。

记录需要不改变复杂度或风险，记录需要不改变交付路径。后端与混合方案任务由 `solution.md` 承担持久上下文；纯前端标准或完整任务按 `frontend-delivery` 由 `ui-design.md` 承担必要 UI 上下文；直接实现从原任务、来源、Git 差异、真实代码和必要交接摘要恢复，不为了记录倒写文档。多个本地 Spec 都可能匹配时由用户指定，不建设自动任务状态选择器。

## 5. 复杂度与路径映射

### 5.1 复杂度

只使用 4.2 至 4.5 四个维度，不做加权总分：

- `简单`：四项全部符合简单信号；
- `复杂`：任一项命中明确的复杂信号；
- `中等`：不满足全部简单，但没有复杂信号。

默认输出只写一个主导原因，其他维度事实保留在内部；只有命中第 7.2 节的展开条件时再展示，且不得把同一个跨模块事实在多个维度重复计算。

### 5.2 路径

按以下顺序映射：

1. 整个模块目标或商业前提尚未成形，或者用户要求先形成多人协作文档：`模块规划`；此时准备可以是 `需澄清`，但下一站直接写 `module-planning`。
2. 其他准备为 `需澄清` 或 `需调查` 的情况：暂不进入开发路径；分别请求会改变任务或路径的关键选择，或转只读调查后重新分流。已经能确定走方案先行的任务，不因方案内部仍有待确认选择而停在这里。
3. 复杂度为 `复杂`：纯前端进入 `frontend-delivery` 完整档；纯后端或混合进入 `方案先行`，使用 `solution-delegated-delivery`。
4. 其余简单或中等任务：纯前端进入 `frontend-delivery` 的最小足够档位；纯后端进入 `直接实现`。混合任务只有目标、全部消费方、契约和实现顺序都已明确且可逆时才直接实现，否则进入后端方案链。风险可以是常规或严格；记录为持久记录也不自动升级方案。

中等任务进入直接实现时必须同时满足：目标与完成结果已经收敛；所有消费方已找全；实现选择有界且可逆；不需要分阶段兼容或迁移；验收可以用短清单表达。缺一项时按对应维度重新判断，不使用“中等一律直接”或“中等一律方案”的规则。

数据库 schema 或数据迁移仍默认方案先行，因为它通常同时涉及迁移顺序、存量数据、兼容和回退；这不是因为“数据库”标签天然等于复杂。纯故障排查不进入开发分流，先转 `incident-triage`；获得修复授权并确认改动面后再回本站。

## 6. 判定步骤

1. 核对准备程度；不满足时先澄清、调查或进入模块规划。
2. 分别核对影响面、规则关系、实现确定程度和验证难度，并保存每项最短事实依据。
3. 根据四项得出简单、中等或复杂，只给一个主导原因。
4. 独立判断风险等级和具体触发项。
5. 独立判断记录需要。
6. 按 5.2 的顺序结合任务领域选择路径和唯一下一站。
7. 实现中出现新证据时，只重评受影响维度；风险或记录需要变化不自动切换路径，只有复杂度、准备程度或用户选择改变时才调整交付路径。

## 7. 输出格式

### 7.1 默认简报

完成内部判断后，默认只向用户展示三行：

```text
路径：直接实现 | 方案先行 | 模块规划 | 暂不进入开发路径
原因：<只写一个决定当前路径的主导事实>
额外检查：无 | <本次真实增加的权限、数据、兼容、人工验收或回退检查>
```

`原因` 不能只写“复杂”或“风险高”；必须说明影响路径的事实。常规任务没有额外检查时明确写“无”，下游不需要再读取一份七维表格。

### 7.2 需要展开的情况

只有准备不足、风险严格、需要持久记录或用户主动要求查看判断依据时，才向用户展开完整七维结论：

```text
准备：可实施 | 需澄清 | 需调查
领域：纯前端 | 纯后端 | 前后端混合
复杂度：简单 | 中等 | 复杂 | 暂不判定（主导原因）
风险：常规 | 严格（具体触发项）
记录：会话内 | 持久记录（原因）
路径：直接实现 | 方案先行 | 模块规划 | 暂不进入开发路径
维度依据：影响面=<事实>；规则关系=<事实>；实现确定=<事实>；验证难度=<事实>
预计影响：<模块、消费方、契约、数据、权限或部署范围>
未确认项：<列出会改变路径、严格检查、方案内容或验收结果的事项；没有则写“无”>
下一站：<frontend-delivery、implementation-execution、solution-delegated-delivery、module-planning、incident-triage 或等待用户补充，以及进入条件>
```

完整展开不是重新判断，也不能变成第二套路径规则。不要输出数字总分，不要只写路径名称，也不要把工作量大、文件多、风险严格或需要跨会话中的任一项直接称为复杂任务。
