# 方案驱动的分层模型交付

## 1. 定位

本技能是现有交付链的编排层，不重新定义方案、实施、测试或审查规则：

```text
flow-router
  → Sol 规划 Agent 使用 solution-generator
  → 用户确认 solution.md 与后续路径
  → acceptance-generator（命中契约验收时）
  → Luna Max 后端实施 Agent 使用 implementation-execution
  → frontend-delivery（混合任务的 UI 设计与前端实施）
  → 严格风险或 Luna 失败时直接升级 Sol Medium 实施 Agent
  → 主 Agent 整合并进入既有验证与质量链
```

主 Agent 始终拥有用户沟通、授权边界、工作区协调和最终结论。子 Agent 只承担收到的有界任务，不能创建分支、提交、推送、PR 或修改外部系统。

## 2. 进入条件

满足任一条件时使用：

- `flow-router` 已判纯后端或混合任务需要方案先行，且当前环境允许子 Agent；
- 用户明确要求由 Sol 先制定方案，再主要由 Luna 实施。

以下情况不使用：

- `flow-router` 判为直接实现，且用户没有明确要求本技能；
- 任务是纯前端页面、组件、布局或视觉改动，此时使用 `frontend-delivery`；
- 用户只要求解释、调查或评审，没有要求生成或实施方案；
- 工作无法拆成边界清晰的任务，或多个实施者必须频繁修改同一可变状态。此时由主 Agent 按现有工作流直接协调。

用户明确调用本技能等于选择方案先行，不再让 `flow-router` 用直接实现覆盖该选择；准备不足或模块目标尚未成形时仍按 `flow-router` 的门槛澄清、调查或转 `module-planning`。

用户只授权生成方案，或已有方案仍包含会改变范围、行为、权限、数据、安全、兼容、成本或不可逆结果的未确认项时，可以进入 Sol 方案阶段，但不得进入施工阶段。

## 3. Sol 方案阶段

始终创建一个 Sol 规划子 Agent，不根据主 Agent 当前模型省略：

- `model`: `gpt-5.6-sol`
- `reasoning_effort`: `medium`
- `fork_turns`: `none` 或只传必要的最近轮次；使用模型覆盖时不得继承完整历史。

在任务消息中给出用户当前请求、来源材料、仓库路径、分流结论和授权边界，并要求它完整使用 `solution-generator`：

1. 读取真实代码、直接消费方、配置和测试；
2. 创建或修订唯一的 `.specs/<KEY>/solution.md`；
3. 不修改业务代码、配置、迁移或测试；
4. 遇到需要用户决定的选择时，返回问题、推荐答案和影响，不自行猜测；
5. 返回方案路径、尚待确认的决定、推荐后续路径和可施工性结论。

混合任务的 `solution.md` 必须固定业务结果、API、权限、数据、状态与失败语义，并列出前端需要呈现的用户结果；详细信息结构、视觉、布局、组件选择和响应式由后续 `frontend-delivery` 写入从属 `ui-design.md`，不在两处重复维护。

主 Agent 负责把待决问题逐项交给用户。收到回答后，优先向同一个 Sol 规划 Agent 发送 follow-up，让它更新原方案；不要创建新的方案文件或让主 Agent 在未复核真实代码时代写决定。

没有用户对当前方案及后续路径的明确确认，不得启动实施 Agent。用户只授权生成方案时，在方案交付后停止。

方案选择直接施工时，确认当前 `solution.md` 和后续路径即可进入拆包。方案选择契约验收时，必须先使用 `acceptance-generator` 创建或修订 `acceptance.feature`，并取得用户对当前验收契约的明确确认；未确认前不得启动实施 Agent。

## 4. 施工拆包

方案及适用的验收契约满足上一节门禁后，主 Agent 按 `solution.md` 中的可观察结果、关键规则和编号实施步骤拆成工作包。每个工作包必须同时满足：

- 承接明确的 `R`、`BR` 或实施步骤；
- 有具体文件或目录边界；
- 有可观察完成判据和最小验证；
- 不要求实施 Agent 重新决定需求、契约、数据模型或发布策略；
- 与其他并行工作包没有写入冲突，也不依赖其尚未完成的结果。

混合任务只在这里拆后端、契约和配置工作包。确认当前 `solution.md` 后，把前端用户结果、不可改写契约和依赖状态交给 `frontend-delivery`；不得把 TSX、CSS 或页面测试混入后端工作包，也不让前端流程重新决定 API、权限或数据语义。

每个实施 Agent 的消息至少包含：

```text
任务标识和 solution.md 路径
完整使用 implementation-execution，并读取 AGENTS.md 和当前 solution.md
契约验收路径读取已经确认的 acceptance.feature
承接的 R / BR / 实施步骤
允许修改的文件或目录
禁止修改的范围
前置依赖和已完成工作
必须遵守的契约与风险约束
最小验证命令或关键断言
返回内容：修改文件、实现结果、真实命令及结果、方案差异、阻塞事项
```

项目规则、当前方案、已确认验收契约和工作包消息发生冲突时，实施 Agent 必须停止并报告具体冲突，不能自行裁决优先级或继续写入。

主 Agent 在派发前检查 `git status --short` 和相关差异，在消息中指出需要保护的用户改动。子 Agent 共享同一工作区，文件归属不清时不得并行写入。

## 5. 模型路由

### Luna

使用：

- `model`: `gpt-5.6-luna`
- `reasoning_effort`: `max`
- `fork_turns`: `none` 或必要的有限轮次。

确认后的后端实施工作包默认交给 Luna，包括局部修改、多文件同步、接口实现和邻近测试。只有命中下一节的 Sol 升级条件时才跳过 Luna；前端实施模型由 `frontend-delivery` 管理。

交给 Luna 前仍必须满足：

- 目标和修改路径已经由方案明确；
- 工作包已经被方案约束，不要求重新发明需求、契约、数据模型或发布策略；
- 验证方式明确，失败能由测试或一次确定观察暴露；
- 消费方已经找全，其他工作包的依赖状态明确。

不能只因 Luna 成本低而把仍需产品决定、方案修订或严格风险判断的问题伪装成实施细节。

### Sol 实施升级

使用：

- `model`: `gpt-5.6-sol`
- `reasoning_effort`: `medium`
- `fork_turns`: `none` 或必要的有限轮次。

创建独立的 Sol 实施 Agent，不解除 Sol 规划 Agent 的禁止写业务代码约束。以下情况直接使用 Sol 实施 Agent：

- 涉及权限可信边界、资源归属、数据库 schema 或存量数据迁移、兼容窗口、生产切换、凭据、数据丢失或不可逆操作；
- 正确实现需要跨多个紧密耦合模块持续追踪复杂状态、并发、事务、恢复或失败副作用，拆包会丢失关键上下文；
- 方案已经确认，但实施仍需要高强度代码推理且错误不容易被现有测试或确定观察暴露；
- Luna 已收到一次有具体证据的修正后，仍因自身实现问题未通过验证。

如果 Sol 实施 Agent 仍需要改变方案中的外部行为、权限、数据语义、兼容或发布决定，不得自行选择；返回主 Agent，按现有流程交 `solution-generator` 修订并确认。

## 6. 并发、失败与回流

- 写操作默认串行。只有工作包文件互斥、依赖独立且验证不会争用同一可变资源时，才并行启动，通常不超过两个实施 Agent。
- 读代码、独立测试分析或日志归纳可以并行，但不能重复已经完成的调查。
- Luna 因自身实现问题失败时，允许向同一 Agent 发送一次有具体证据的修正；仍失败则停止 Luna，整理已有差异和失败证据后交独立的 Sol 实施 Agent。
- Sol 实施 Agent 因自身实现问题失败时，最多向同一 Agent 发送一次有具体证据的修正；仍失败则停止自动施工，由主 Agent 判断是方案缺口、环境阻塞还是实现问题，并按事实回流或请求用户决定，不继续更换 reasoning effort 或重复派发。
- 环境阻塞、测试基础设施故障或方案缺口不能通过换模型掩盖；按真实原因报告或回流。
- 子 Agent 发现超范围、用户改动冲突、方案不可实施或新增高影响决定时必须停止写入并返回证据。
- 不无限重试，不同时让多个 Agent 对同一失败做竞争性修复。

## 7. 整合与完成

实施 Agent 返回后，主 Agent 必须亲自：

1. 检查完整工作区差异，确认没有越界修改、互相覆盖或静默方案偏差；
2. 对照方案的可观察结果、关键规则和实施步骤核实所有工作包已经闭环；
3. 按 `implementation-execution` 处理必要的契约、配置、迁移和长期文档同步；
4. 进入 `run-all-tests`、适用的 `manual-acceptance` 和 `code-review-and-quality`，只报告真实执行结果；
5. 发现方案级偏差时先回流更新方案，不能用实施总结替代用户确认；
6. 用户另行要求 Git 交付时再进入 `branch-pr-workflow`。

涉及严格风险、Sol 实施升级仍留下疑点或存在已允许的方案偏差时，可以向原 Sol 规划 Agent 发送一次最终一致性复核，输入当前方案、完整差异和验证证据；普通任务不固定增加这次成本。

最终向用户说明实际使用的模型分工、完成范围、验证结果、未覆盖区域和真实遗留项，不把子 Agent 的自述当作验证证据。
