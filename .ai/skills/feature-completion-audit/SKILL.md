# 功能完成度审计

## 1. 唯一问题

只回答：**相对已经确认的原始需求，这项功能是否完成，缺口在哪里。**

- `code-review-and-quality` 判断代码是否正确、安全、可维护；
- `run-all-tests` 执行测试并报告结果；
- 本技能把“需求 → 实现 → 验证”逐项对账，既查遗漏，也查超范围和偏离。

默认直接返回审计结果，不创建重复的本地审计文档、不修改代码、不提交或发布。

## 2. 两种入口

### 入口 A：审计当前会话刚完成的实现

实现者存在自证偏差，必须使用独立子 Agent 复核：

1. 主 Agent 整理审计输入包，只包含原始需求、冻结规格、改动范围和取证要求；
2. 小改动使用一个子 Agent 覆盖六个维度；中大改动可按需求验收、正确性契约、测试偏离分组并行；
3. 不把“我认为已完成”、预期答案或已写总结传给子 Agent；
4. 子 Agent 必须自行读取真实代码和测试证据，主 Agent 只负责交叉核对、去重和汇总。

### 入口 B：审计外部 PR、分支或历史提交

改动不是当前会话产出时，由当前 Agent 读取正确基线到目标的完整 diff 并完成核验，不强制再派子 Agent。先确认 base、head、提交范围和关联需求，不能只看工作区未提交差异。

## 3. 审计输入

尽量收齐：

1. 用户当前明确确认的需求与后续修订；
2. 来源 Issue 的完整正文及明确指定为有效输入的附件或补充，不限制 Multica、Linear、GitHub 或其他平台；
3. 飞书中已确认的周开发文档、详情文档、模块说明和后续补充；
4. `.specs/<KEY>/solution.md`、`acceptance.feature`、`implementation_report.md`；
5. 实际提交、完整 diff、关键调用方和保留的旧链路；
6. 自动化测试结果、人工验收记录和未覆盖区域；
7. 受影响的 HTTP、配置、数据库、Alembic、对象存储、部署和长期文档。

来源 Issue 是初始产品输入，飞书详情材料可以展开或明确替代其中的部分结论。输入之间冲突时先列出替代关系和时间顺序，不能静默选择最方便证明完成的一份。缺少关键证据时结论必须是“证据不足”。

## 4. 六个固定维度

1. **需求覆盖**：把目标、范围和非目标拆成离散条目，逐条映射到 `file:line` 或明确运行行为。
2. **验收对齐**：逐个 Scenario 核对 Given 前置、When 动作、Then 结果是否都有实现和验证承接。
3. **正确性边界**：检查失败、空值、边界、权限、重复请求、并发、幂等、部分失败与回滚。
4. **契约与集成**：检查 Web、FastAPI、HTTP、Cookie、共享类型、配置、MySQL、Alembic、MinIO 和部署是否同步。
5. **测试证据**：只有实际执行成功的相关测试、构建或人工验收才算证据；测试文件存在但未运行不算完成。
6. **范围偏离**：反向检查是否实现了需求未要求的能力、顺带重构无关模块、删除仍需兼容的旧链路或改变了非目标。

## 5. 条目状态与缺口分级

每个需求条目只能判为：

- `达成`：实现与验证证据完整；
- `部分达成`：只有部分行为、边界或验证闭环；
- `未达成`：确认范围没有对应实现；
- `待确认`：需求冲突或证据不足，无法客观判断。

缺口按影响分级：

- `阻断`：核心需求缺失、实现错误、关键契约或数据风险，不能算完成；
- `必须补齐`：验收偏差、关键测试缺失、迁移或边界未闭环；
- `建议`：不影响本次完成判定的改进项。

## 6. 输出报告

1. **审计范围**：需求来源、基线、目标提交、输入文档和入口类型；
2. **需求对账表**：需求条目、状态、实现证据、验证证据和缺口；
3. **六维小结**：每个维度的事实与风险；
4. **分级缺口清单**：阻断、必须补齐、建议；
5. **完成结论**：
   - `完成`：所有条目均有证据达成，无阻断或必须补齐项；
   - `未完成`：存在阻断或必须补齐项；
   - `证据不足`：关键需求、代码或验证证据无法取得；
6. **下一站**：补规格、补实现、补测试、数据库迁移、同步文档或质量审查。

不要给不同风险的条目计算虚假百分比，也不要用“主要流程能跑”替代逐项结论。

## 7. 客观性自检

- 每个“达成”都有具体代码或运行证据；
- 入口 A 确实由未参与实现的子 Agent 取证；
- 同时检查遗漏和偏离；
- 测试与人工验收都来自真实执行；
- 有阻断或必须补齐项时，结论没有写“完成”；
- 不确定内容保留为待确认，没有为了收口而乐观推断。
