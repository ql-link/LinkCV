# 前端独立交付

## 1. 领域边界

本技能处理 `apps/web` 中用户可见页面、组件、交互、状态、布局和视觉实现。先按任务领域选择依据：

| 领域 | 当前依据 | 本技能职责 |
| --- | --- | --- |
| 纯前端 | 当前请求；标准或完整档需要持久设计时使用 `ui-design.md` | 独立完成 UI 设计、实施和验证，不创建 `solution.md` |
| 纯后端 | `solution.md` 或直接实现依据 | 不使用本技能，转 `solution-delegated-delivery` 或 `implementation-execution` |
| 前后端混合 | 已确认 `solution.md` 是业务、API、权限、数据与失败语义的中心；`ui-design.md` 是从属 UI 附件 | 只补页面结构、交互呈现、状态反馈、布局和响应式，不改写上游契约 |

浏览器扩展、小程序和纯 PDF 文档布局不因使用 TypeScript 自动归入本技能；按各自模块和当前任务规则处理。前端调用既有 API 且不改变契约，可以视为纯前端；新增或改变请求、响应、权限、错误语义、配置或后端行为则属于混合任务。

## 2. 档位与产物

复用 `frontend-design` 的轻量、标准、完整档，选择最小足够路径：

| 档位 | 规划 | 持久产物 | 用户门禁 |
| --- | --- | --- | --- |
| `轻量` | Sol Medium 返回短实施简报 | 无 | 没有新的用户可见选择时直接实施 |
| `标准` | Sol Medium 核实页面并形成 UI 设计依据 | 仅在跨会话、需确认布局或交互选择、或用户要求记录时创建 `ui-design.md` | 只有存在会改变用户结果、页面结构或交互方式的选择时确认 |
| `完整` | Sol Medium 使用 `frontend-design` 与 `ui-layout-design` 创建或修订 `ui-design.md` | 必须存在 | 用户确认当前 UI 设计后实施 |

轻量档不得为了形式创建 Spec。标准档如果当前请求、现有设计系统和真实页面已经唯一确定结果，可以在会话内完成简报，不创建文档、不增加确认轮次。

## 3. Sol UI 规划 Agent

需要规划时创建一个独立 Agent：

- `model`: `gpt-5.6-sol`
- `reasoning_effort`: `medium`
- `fork_turns`: `none` 或必要的有限轮次。

任务消息包含当前请求、任务领域、前端档位、仓库路径、来源材料、用户授权和需要保护的工作区差异，并要求：

1. 完整使用 `frontend-design`；布局是实际改动内容时同时使用 `ui-layout-design`；
2. 读取目标页面、直接调用方、邻近测试、`DESIGN.md` 和必要组件，不扫描无关前端；
3. 纯前端不得创建或修订 `solution.md`；混合任务先读取已确认 `solution.md`，不得改变业务、API、权限、数据或失败语义；
4. 轻量档只返回修改对象、保持不变行为、文件边界和最小验证；
5. 标准或完整档需要持久产物时，读取 [ui_design.template.md](ui_design.template.md)，创建或修订唯一的 `.specs/<KEY>/ui-design.md`；
6. 不修改业务代码、样式、测试或配置；
7. 返回档位、设计依据路径或会话简报、待确认 UI 决定、建议工作包和验证重点。

收到用户回答后优先向同一个规划 Agent follow-up 更新原 `ui-design.md`。不创建“最终版”或另一份布局文档。

## 4. UI 设计依据

`ui-design.md` 只保存实现前必须稳定的 UI 事实：

- 使用者、主任务、可观察结果和不做内容；
- 当前页面证据与必须继承的设计系统；
- 信息结构、操作顺序和重要状态；
- 布局命题、密度以及窄、中、宽容器适配；
- 组件复用、新增边界和真实文件计划；
- 自动化、浏览器和人工验收映射；
- 真实发生的 UI 决定及确认来源。

不复制接口字段表、后端状态机、权限规则、数据模型或发布策略。混合任务通过链接引用当前 `solution.md`，冲突时停止并回到上游方案，不允许用 UI 文档覆盖契约。

完整档没有用户对当前 `ui-design.md` 的明确确认不得施工。标准档只有存在待确认 UI 决定时暂停；没有待决项的持久记录可以展示后直接实施，但用户只授权设计时必须停止。

## 5. Luna 实施 Agent

确认或简报满足门禁后创建实施 Agent：

- `model`: `gpt-5.6-luna`
- `reasoning_effort`: `max`
- `fork_turns`: `none` 或必要的有限轮次。

同一路由或同一页面的组件、样式、状态逻辑和邻近测试默认作为一个工作包交给同一个 Luna，不按 TSX、CSS 和测试机械拆包。只有页面和文件互斥、行为独立且整合成本确实更低时才拆开。

实施消息至少包含：

```text
任务领域、档位和目标页面
当前请求；存在时的 ui-design.md
混合任务的 solution.md 及不可改写契约
完整使用 frontend-design；布局命中时使用 ui-layout-design
允许和禁止修改的文件
必须保持的路由、API、权限和状态语义
邻近测试与最小验证
需要保护的用户改动
返回：修改文件、实现结果、真实命令及结果、设计偏差、阻塞
```

Luna 不创建分支、提交、推送、PR 或外部记录。发现新增产品选择、API/权限变化、设计依据冲突或超范围修改时停止并返回主 Agent。

## 6. 失败、升级与回流

- Luna 因自身实现问题失败时，向同一 Agent 提供一次具体失败证据进行修正；仍失败则交独立 Sol Medium 实施 Agent。
- Sol 实施 Agent 只接管已确认 UI 设计内的复杂实现；它仍不能改变产品、契约或确认后的布局方向，失败后最多修正一次。
- 纯前端出现 API、权限、数据或后端行为变化时，停止并由 `flow-router` 重判为混合任务；需要方案时先进入 `solution-delegated-delivery`。
- UI 主任务、信息结构、交互方式或完整档视觉方向改变时，回到原 Sol UI 规划 Agent 修订 `ui-design.md` 并确认受影响决定。
- 文件组织、方法命名、测试落点或不改变可见结果的局部实现差异继续处理，在 PR 中按重要性说明，不回写设计依据。
- 环境或测试基础设施故障按真实原因报告，不通过反复换模型掩盖。

## 7. 主 Agent 整合

主 Agent 亲自完成：

1. 检查完整差异和工作包边界，确认没有覆盖用户改动或静默改变上游契约；
2. 对照当前请求、`ui-design.md` 以及混合任务的 `solution.md` 核实用户结果；
3. 按 `frontend-design` 档位完成适用的界面审查和浏览器观察；
4. 交 `run-all-tests` 执行前端范围验证，必要时使用 `manual-acceptance`，最后使用 `code-review-and-quality`；
5. 只报告真实执行证据、未覆盖尺寸和残余风险；
6. 用户另行授权 Git 交付时才进入 `branch-pr-workflow`。

最终说明实际档位、Sol/Luna 分工、是否产生 `ui-design.md`、浏览器覆盖、自动化结果和遗留项。
