# 前端可视设计与分层交付

## 1. 领域边界

本技能处理 `apps/web` 的页面、组件、交互、状态、布局和视觉实现：

- 纯前端以当前请求、真实页面和已确认视觉产物为依据，不创建 `solution.md`；
- 混合任务先以 `solution.md` 固定业务、API、权限、数据和失败语义，视觉产物只能补 UI 呈现；
- 纯后端转 `backend-delivery`；浏览器扩展、小程序和 PDF 不因使用 TypeScript 自动进入本流程。

前端调用既有 API 且不改变契约仍是纯前端；新增或改变请求、响应、权限、错误语义、配置或后端行为时停止，由 `flow-router` 重判领域。

## 2. 档位、偏好和产物

选择最小足够档位：

| 档位 | 适用变化 | 设计产物与门禁 |
| --- | --- | --- |
| `轻量` | 纯逻辑、文案、局部尺寸或既有组件属性，且不改变交互模式和页面结构 | 短实施简报；无新的用户可见选择时直接实施，不强制画图 |
| `标准` | 既有页面的可见交互、状态、字段或局部布局变化 | 在真实路由中按“一个问题 → 一次可见修改 → 一轮反馈”迭代 |
| `完整` | 新页面、主要区域重组或新的视觉方向 | 先建立最小骨架，再按同样节奏逐步收敛；不要求首轮形成完整方案 |

标准和完整档以对话作为设计主线。首轮只确认一个最影响整体结果的方向，除非用户已经表达清楚；看到可见结果后再决定是否询问下一个问题，不在开工前收集完整偏好表。问题可以是：

- 信息密度：紧凑高效、平衡、宽松聚焦；
- 页面气质：克制工具感、温和生活感、较强品牌感；
- 本次更重视：快速完成任务、信息浏览、视觉辨识度。

每轮最多问一个问题，提供 2–3 个大方向并给出基于现有设计系统的推荐。不要追问色值、字号、圆角、精确间距、具体断点或控件坐标。用户不确定时直接实现推荐方向；用户要求比较或确有两个同样合理且会改变结果的方向时才画多版。提问、修改和反馈可以反复进行，不设固定轮数，也不因上一轮已确认就拒绝继续打磨。

对话中的最新明确反馈优先于较早判断。不要把同一个原型文件、`ui-design.md`、Design Brief 或首轮 Agent 输出当作后续生成的固定提示词；它们只能提供当前画面和已确认约束。每轮从当前请求、最新反馈、浏览器实际画面、Git 差异和真实代码重新判断本轮最小改动。

设计格式：

- 已有可运行路由或组件，且用户已经授权修改当前工作区：默认把真实页面作为可回退原型，不复制第二套 HTML；
- 全新页面、尚无可运行入口或真实代码预览会过早固化高影响结构：默认制作隔离的 HTML/CSS 原型；
- 用户明确指定 Figma：使用 Figma，不再额外生成 HTML 或真实路由原型；
- 用户明确指定多个方向：同一格式生成 2–3 个可比较方案；
- 用户明确要求概念图或图像生成时，`imagegen` 只用于视觉探索，不替代可实施原型，也不成为实施门禁；
- 不先询问产物格式；根据是否已有可运行页面自动选择，用户主动指定 Figma 时才切换。

## 3. Sol 判断与逐轮交接

标准或完整档由独立 Sol Agent 判断当前轮次：

- `model`: `gpt-5.6-sol`
- `reasoning_effort`: `medium`
- `fork_turns`: `none` 或必要的有限轮次。

优先复用同一 Sol Agent 维持上下文；不可复用时传入当前请求、最新一轮用户反馈、当前截图或可访问页面、当前 Git 差异、已确认约束、仓库路径和授权边界。不要传入一份要求它机械执行的“最终设计文件”。要求它：

1. 完整使用 `frontend-design`；布局是实际内容时同时使用 `ui-layout-design`；
2. 读取目标页面、直接调用方、邻近测试、`DESIGN.md` 和必要组件，不扫描无关前端；
3. 真实页面和 HTML 原型模式都读取并执行 `frontend-design/references/prototype-quality-gate.md`；已有页面继承真实应用壳，不自行发明导航、品牌或全局视觉语言；
4. 纯前端不创建 `solution.md`；混合任务不得改变已确认契约；
5. 只返回本轮会话级视觉判断，不另建或重写 UI 文档；全新页面需要画布时在 `.specs/<KEY>/prototype/` 创建自包含的 `index.html`，但该文件只是当前可见状态，不是后续轮次的唯一指导；
6. Figma 模式先完整使用适用的 Figma 前置 Skill，再创建或更新用户指定的设计文件并返回可访问链接；
7. 为当前轮次选择一个最值得解决的问题，例如信息顺序、主操作、密度、分组或移动重排；不要同时重做所有视觉维度；
8. HTML 原型是隔离的设计产物，不导入应用源码、不调用真实 API、不复制成第二套生产组件；不新增依赖，不请求外部资源；
9. 给 Luna 一份只覆盖当前轮次的短交接：要改变什么、保持什么、用户看完需要判断什么；不形成累计增长的完整设计说明；
10. 不修改业务代码、正式样式、测试或配置；
11. 返回当前轮次的判断、短实施交接和必要的 2–3 个下一问候选；由主 Agent 在看过实际页面后决定是否询问用户。

人与 AI 的问答和当前可见界面共同构成设计过程。不要先交付一篇 `ui-design.md`、完整 Brief 或“最终方案”要求用户一次确认，也不要用长篇说明替代可见布局、层级和交互。

## 4. 对话迭代与阶段收口

每轮由 Luna 完成一个可回退的小步修改，主 Agent 在浏览器查看桌面或本轮受影响断点，并执行视觉拒收门禁，再把实际页面交给用户。用户的下一句反馈直接开启下一轮；若反馈改变信息结构或视觉方向，Sol 重新判断本轮问题，不要求先修订某个指导文件。确认前不得提交、推送或创建 PR。无横向溢出、交互可点击或使用 Token 不能单独证明视觉合格。

当前轮次只改一个连贯层面，通常不超过一个页面区域或一种跨区域规则。能从用户反馈直接定位的视觉问题交给同一 Luna 修改；涉及目标、信息顺序、主次关系或交互方式时先回同一 Sol 判断。不要每轮运行完整测试、生成新 Spec、复制新原型或创建“最终版文档”。

只有用户明确表示方向稳定、可以收口或要求交付时，才由原 Sol Agent 或主 Agent 形成一次会话级短交接：

```text
当前可见界面：<真实路由与当前差异 / 本地 prototype/index.html 绝对路径 / Figma 链接>
最后确认方向：<一句话>
必须保持：<业务、API、权限、状态与路由>
实现文件：<真实文件边界>
关键交互与响应式：<图中无法完整表达的内容>
验证重点：<自动化、浏览器尺寸与状态>
```

不创建文字 UI Spec。跨会话继续时读取当前请求、当前可运行页面或原型/Figma、适用 `solution.md`、Git 差异和真实代码；持久文件只恢复当前画面，不能代替用户最新反馈。视觉依据不可访问时请用户重新附上或恢复权限，不根据旧聊天记忆猜测设计。

## 5. Luna 实施 Agent

需要形成或调整可见界面时创建 Luna 实施 Agent；真实页面模式从首轮即可介入，全新页面由它维护当前原型画布：

- `model`: `gpt-5.6-luna`
- `reasoning_effort`: `max`
- `fork_turns`: `none` 或必要的有限轮次。

优先复用同一 Luna Agent。每轮消息只包含最新反馈、本轮短交接、当前截图或页面、当前差异、允许和禁止文件、现有契约与需要保护的用户改动，并要求完整使用 `frontend-design`，布局命中时使用 `ui-layout-design`。不要要求它重新读取某个文件并一次性“完成整个设计”。

Luna 不创建分支、提交、推送、PR 或外部记录。发现新增产品选择、API/权限变化、视觉产物冲突或超范围修改时停止并返回主 Agent。

## 6. 失败、升级与回流

- Luna 因自身实现问题失败时，向同一 Agent 提供一次具体失败证据；仍失败才交独立 Sol Medium 实施 Agent；
- UI 主任务、信息结构、交互方式或视觉方向改变时，回原 Sol Agent 基于最新反馈重新判断下一轮，不先修订文档；
- API、权限、数据或后端行为变化时回 `flow-router`；
- 文件组织、测试落点和不改变可见结果的实现差异继续处理，按重要性在 PR 说明；
- 环境故障不得通过反复换模型掩盖。

## 7. 主 Agent 整合

主 Agent 每轮亲自检查本轮差异和实际画面；用户明确收口后，再对照当前页面、最终短交接和混合任务的 `solution.md` 检查完整差异，并进入 `run-all-tests`、适用的 `manual-acceptance` 和 `code-review-and-quality`。

最终说明档位、偏好选择、真实路由或原型/Figma 入口、Sol/Luna 分工、浏览器覆盖、自动化结果和遗留项。用户另行授权 Git 交付时才进入 `branch-pr-workflow`。
