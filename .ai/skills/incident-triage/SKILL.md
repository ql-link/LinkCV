# 故障分诊

## 1. 目的与边界

先确定故障落在哪一段，再用最小检查区分根因，避免看到表层错误就修改代码或配置。默认允许读取状态、日志和配置入口，运行可逆的诊断命令；不自动重启、清库、删除数据、改环境、回滚部署或提交修复。

## 2. 当前调用链

```text
浏览器
  → Vite 5173
    → /api → FastAPI 8000
      → 健康检查
      → 鉴权、简历 → SQLAlchemy → MySQL
      → 图片资源 → MinIO 9000

后端集成测试使用隔离 SQLite 和假 MinIO。它们是测试替身，不能用来推断本地、Dev 或 Production 的真实依赖状态。Redis 已有配置契约，但当前没有业务调用链。
```

先核对请求是否经过 Vite、实际 FastAPI 路由是否注册，以及目标环境是否已经应用对应 MySQL revision。当前全部 `/api` 由 FastAPI 承接；不得继续寻找已移除的 Express 进程或 `server/` 文件。

## 3. 固定故障事实

记录：

1. 原始动作、期望结果、完整错误、时间和退出码或 HTTP 状态；
2. 影响范围：单个用户或多人、本地或 CI、单路径或全部接口、持续或间歇；
3. 最近变化：代码、依赖、`.env`、端口、代理、Tailscale/VPN、凭据、数据或部署；
4. 当前分支、实际启动命令、运行中的进程和目标地址；
5. 已尝试操作及其结果。

能从仓库和本机核实的事实自行调查；只询问会改变诊断方向且无法本地获取的信息。

## 4. 分诊决策树

### A. 服务无法启动或页面打不开

- 分别运行或读取 `npm run dev:web`、`npm run dev:backend` 的真实错误；
- 核对 Node、Python、uv、依赖锁、工作目录和端口占用；
- 区分进程未启动、监听地址不对、端口冲突、依赖缺失和浏览器访问目标错误；
- 不用一个子进程启动成功推断 Web、FastAPI 和必要基础设施都正常。

### B. API 不可达、404、502 或请求进错服务

- 从 `apps/web/src/api/client.ts` 的相对路径追到 `apps/web/vite.config.mjs`；
- 核对 `BACKEND_PORT` 和 `BACKEND_PROXY_TARGET` 的实际覆盖关系；
- 分别直接探测目标服务和经过 Vite 的路径，区分代理错误与应用错误；
- 同一个值多处不一致时转 `config-contract-sync`。

### C. 登录、Cookie、简历保存或权限异常

- 当前事实源是 `apps/backend/src/linkcv/modules/identity/`、`modules/resumes/`、`core/security.py` 和 `core/database.py`；
- 核对 `resume_session` JWT Cookie 是否由正确路由设置、浏览器是否携带、签名和有效期是否符合当前环境；
- 区分浏览器登录、CLI 登录和其他 Agent 的凭据，它们不是同一身份；
- 核对查询是否按 `user_id` 限制，以及 401、403、404 的契约语义。

### D. 图片上传、读取或 MinIO 故障

- 从 `modules/resumes/asset_routes.py` 追到 `core/storage.py`，核对 endpoint、端口、bucket、凭据来源和对象名前缀；
- 区分上传数据校验失败、MinIO 不可达、bucket 不存在、对象不存在和跨用户路径被拒绝；
- 不输出真实图片、密钥或用户对象名，证据中先脱敏。

### E. MySQL、SQLAlchemy 或 Alembic 故障

- FastAPI 业务路由已经依赖 SQLAlchemy 模型和 MySQL 配置，仓库根 revision `0001` 创建 `users`、`resumes`；先区分仓库 head、目标环境实际 current revision 和应用期望 schema；
- 只读核对连接目标、数据库版本、current revision、heads、history、锁和应用期望 schema；
- 区分连接配置、未迁移、多 head、部分迁移、模型漂移、约束冲突和数据回填失败；
- 迁移设计或数据修复转 `alembic-migration`，未经授权不执行升级、降级、UPDATE、DELETE 或清库；SQLite 集成测试成功不能证明 MySQL schema 已就绪。

### F. 测试、构建或 CI 故障

- 使用 `run-all-tests` 复现真实命令，区分断言失败、测试基础设施错误和环境阻塞；
- 对比本地与 CI 的 Node、Python、依赖锁、环境变量和工作目录；
- 单个测试重跑成功不代表完整 `npm run check` 已恢复。

## 5. 网络与 Tailscale 专项

- 核对 DNS 解析、系统代理、路由表、Tailscale 接管的子网或 DNS、证书和目标端口；
- 比较直接地址、域名和代理后的实际连接目标，不默认要求关闭 Tailscale；
- 多人环境不同而同一服务间歇失败时，优先寻找固定服务地址、代理或认证配置，避免给出只适用于某台机器的绕过方案；
- “浏览器能登录”不等于 CLI、插件进程或当前 Agent 使用相同网络和身份；
- 网络恢复后用原始失败步骤复测，不能只用 ping 或一次成功请求宣布问题解决。

## 6. 假设与根因

维护证据表：

| 假设 | 支持证据 | 反证 | 下一项最小检查 | 状态 |
| --- | --- | --- | --- | --- |

状态只使用：`已证实`、`高度可能`、`待验证`、`已排除`。每次只改变一个观察变量；重复同一失败命令但没有新条件不算新证据。

只有根因能解释主要症状、有直接证据、隔离或修正后原复现步骤恢复，才写“根因已确认”。否则保留为“高度可能”。

## 7. 输出与转交

1. **定位**：故障在哪一段、哪个服务或数据边界；
2. **事实与证据**：命令、日志、配置读取链、HTTP 或数据状态；
3. **根因分类**：网络、配置漂移、服务归属、数据不一致、代码缺陷、外部依赖或尚未定位；
4. **已排除项**：只列有反证的方向；
5. **最小修复建议**：说明影响，但默认不执行；
6. **恢复验证**：原始复现步骤、相关测试和完整质量入口；
7. **残余未知**：仍缺的用户信息或外部证据。

用户授权修复后，代码和配置变更先回 `flow-router` 分级；数据库迁移转 `alembic-migration`；外部网络策略、凭据和数据操作需要单独明确授权。
