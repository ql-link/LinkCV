# 人工端到端验收

## 1. 职责与边界

把确认的验收规则转换为人可以按步骤执行、记录和复核的端到端清单。方案先行任务把实际结果保存到当前任务的本地 Spec 快照；直接实现没有 Spec，只在当前任务交接中保留精简记录。人工验收有自己的记录位置，不因存在 `implementation_report.md` 就复制一份结果。

本技能只处理自动化测试尚未覆盖的行为，例如：

- 浏览器中的完整用户流程和页面状态切换；
- Web 与 FastAPI 之间的真实路由协作；
- Cookie、登录态、上传、下载、打印和 PDF 导出；
- 字体、排版、响应式布局以及必须肉眼确认的视觉结果；
- 需要真实本地服务或基础设施协作的关键流程。

以下情况不要使用：

- 编写组件、单元或后端集成测试，转 `test-authoring`；
- 运行自动化测试并判断仓库是否通过，转 `run-all-tests`；
- 纯后端函数、局部逻辑已经被自动化测试充分覆盖且没有人工观察面；
- 用人工验收替代本应存在的自动化测试。

## 2. 产物位置与生命周期

方案先行任务固定写入：

```text
.specs/<KEY>/manual_acceptance.md
```

生成时读取 [manual_acceptance.template.md](manual_acceptance.template.md)，替换全部占位内容。该文件是任务级执行记录，不放入 `docs/`；`.specs/<KEY>/` 默认不提交，因此 PR 中只摘要结论和失败项。来源 Issue 存在时是有效输入，但不是开工门槛或验收结果存储位置；不要向任何 Issue 系统自动写回验收结果。

直接实现不创建 `.specs` 或 `manual_acceptance.md`。若局部 UI、浏览器行为或视觉结果确实需要人工确认，在对话中生成最小清单，记录实际环境、步骤、结果和证据，并把摘要交给实施交接和后续 PR，不为此单独创建 Spec 或实施报告。只有方案先行任务命中已允许的实际方案偏差、已接受限制或必须交接的遗留风险或下一步事项时，`implementation_report.md` 才可作为增量补充，也不复制整份人工验收记录。未执行时只能写“未执行”，不能因为直接实现没有阶段命令而省略风险。

清单可以在实现前预先生成，但只有在目标实现和自动化验证稳定后才执行。结果变化时直接更新原文件，不另建多份“最终版”。

## 3. 必读材料

1. 方案先行任务读取当前 `solution.md`，选定契约验收路径时一并读取 `acceptance.feature`；直接实现读取用户当前请求、已确认结果和存在的有效来源材料；
2. 当前实现、Git 差异、自动化测试结果和未覆盖区域；
3. 与流程相关的 Web、FastAPI、配置和部署事实；
4. 本技能所属模板。

不要根据聊天印象重新发明验收规则。发现清单需要新的业务结果时，返回 `solution-generator` 或 `acceptance-generator` 修订并确认受影响内容。

## 4. 生成清单

1. 选定契约验收路径时从 `acceptance.feature` 提取场景；选定直接施工路径时从方案文档的“可观察结果”和“验证与验收”提取；直接实现从当前请求、已确认结果和存在的有效来源材料中，只提取需要真实浏览器或真实服务协作的可观察结果。
2. 排除已经由稳定自动化测试完整覆盖、且没有视觉或跨端观察面的场景。
3. 为每项保留验收场景名称，补充环境、测试数据、前置条件、编号、操作步骤和具体预期。
4. 一条步骤只包含一个可执行动作；一条预期只描述一个可以观察或核对的结果。
5. 覆盖适用的主流程、权限、失败、边界、兼容和回归行为，不为增加数量复制相同流程。
6. 测试数据使用虚构信息，默认姓名为“张三”；不得把真实账号、简历、联系方式、Cookie 或密钥写入文件。

## 5. 记录执行结果

- 状态只允许：`未执行`、`通过`、`失败`、`阻塞`、`不适用`。
- AI 可以启动本地服务、准备虚构数据和指导执行，但不能把“计划执行”写成“已经通过”。
- 只有执行人明确确认，或存在本次真实浏览器操作、截图、日志等证据时，才能标记 `通过`。
- `失败` 必须记录实际结果、复现条件和关联缺陷；`阻塞` 必须记录环境或依赖原因。
- 截图和日志记录路径或链接即可；不要把大体积二进制产物放入 `.specs`。
- 任一必要项为 `未执行`、`失败` 或 `阻塞` 时，人工验收结论不得写“通过”。
- 开始执行时记录当前分支或提交以及可提交内容状态。任一验收项执行后若生产代码、配置、依赖或测试替身发生变化，由 AI 根据真实影响把受影响项恢复为 `未执行`；重新执行后才能再次通过。之后运行的自动化测试不能反向证明较早的人工步骤仍然有效。

## 6. 与自动化验证和质量审查衔接

人工验收开始前，实施任务应已由 `run-all-tests` 执行与改动范围匹配的自动化验证。所有必要人工项通过后，把人工结果和已有自动化结果一起交给 `code-review-and-quality`；只有人工验收过程中又修改了代码、配置、依赖或测试替身，才返回 `run-all-tests` 重跑受影响检查。任务验证不为了凑“完整仓库”而固定运行 `npm run check`，准备 PR 时再按 Git 交付规则执行完整检查。

人工验收文件保存真实步骤和结果，不保存工作流阶段或代码哈希。代码变化时，AI 结合 Git 差异、实现和测试判断哪些人工项与自动化检查需要重做；无法可靠缩小影响时扩大验证。必要项仍有未执行、失败或阻塞时，不得给出质量审查通过结论。

## 7. 完成输出

最终报告至少说明：

- 记录位置（方案先行任务写文件路径；直接实现写“会话级记录”）和覆盖的验收场景；
- 执行环境、分支或提交、执行人和日期；
- 通过、失败、阻塞、未执行和不适用数量；
- 失败或阻塞项及下一步；
- 自动化验证证据和人工验收是否足以进入质量审查。
