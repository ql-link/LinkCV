# 人工端到端验收

## 1. 职责与边界

把确认的验收规则转换为人可以按步骤执行、记录和复核的端到端清单。方案先行任务把实际结果保存到当前任务的本地 Spec 快照；直接实现没有 Spec，只在当前任务交接中保留精简记录，原本需要实施报告时再同步进去。

本技能只处理自动化测试尚未覆盖的行为，例如：

- 浏览器中的完整用户流程和页面状态切换；
- Web 与 FastAPI 之间的真实路由协作；
- Cookie、登录态、上传、下载、打印和 PDF 导出；
- 字体、排版、响应式布局以及必须肉眼确认的视觉结果；
- 需要真实本地服务或基础设施协作的关键流程。

以下情况不要使用：

- 编写组件、单元或后端集成测试，转 `test-authoring`；
- 运行自动化测试并判断仓库是否通过，转 `run-all-tests`；
- 纯后端函数、局部逻辑已经被自动化测试充分覆盖且没有人工观察面；
- 用人工验收替代本应存在的自动化测试。

## 2. 产物位置与生命周期

方案先行任务固定写入：

```text
.specs/<KEY>/manual_acceptance.md
```

生成时读取 [manual_acceptance.template.md](manual_acceptance.template.md)，替换全部占位内容。该文件是任务级执行记录，不放入 `docs/`；`.specs/<KEY>/` 默认不提交，因此 PR 中只摘要结论和失败项。来源 Issue 是初始产品输入，不是验收结果存储位置；不要向任何 Issue 系统自动写回验收结果。

直接实现不创建 `.specs` 或 `manual_acceptance.md`。若局部 UI、浏览器行为或视觉结果确实需要人工确认，在对话中生成最小清单，记录实际环境、步骤、结果和证据，并把摘要交给实施交接和后续 PR；任务本来需要实施报告时再写入报告，不为此单独创建 Spec。未执行时只能写“未执行”，不能因为直接实现没有阶段门禁而省略风险。

清单可以在实现前预先生成，但只有在目标实现和自动化验证稳定后才执行。结果变化时直接更新原文件，不另建多份“最终版”。

## 3. 必读材料

1. 方案先行任务读取 `.specs/<KEY>/state.yaml`；直接实现读取来源 Issue 与当前确认结果；
2. 方案先行任务读取冻结的 `solution.md`，选定契约验收路径时一并读取 `acceptance.feature`，重点核对其中的状态机与数据模型结论；
3. 当前实现、自动化测试结果和未覆盖区域；
4. 与流程相关的 Web、FastAPI、配置和部署事实；
5. 本技能所属模板。

不要根据聊天印象重新发明验收规则。发现清单需要新的业务结果时，返回 `acceptance-generator` 修订并重新冻结。

## 4. 生成清单

1. 选定契约验收路径时从 `acceptance.feature` 提取场景；选定直接施工路径时从方案文档 1.4 交付结果和 9.3 验证方式提取；直接实现从来源 Issue 和当前确认结果中只提取需要真实浏览器或真实服务协作的可观察结果。
2. 排除已经由稳定自动化测试完整覆盖、且没有视觉或跨端观察面的场景。
3. 为每项保留验收场景名称，补充环境、测试数据、前置条件、编号、操作步骤和具体预期。
4. 一条步骤只包含一个可执行动作；一条预期只描述一个可以观察或核对的结果。
5. 覆盖适用的主流程、权限、失败、边界、兼容和回归行为，不为增加数量复制相同流程。
6. 测试数据使用虚构信息，默认姓名为“张三”；不得把真实账号、简历、联系方式、Cookie 或密钥写入文件。

## 5. 记录执行结果

- 状态只允许：`未执行`、`通过`、`失败`、`阻塞`、`不适用`。
- AI 可以启动本地服务、准备虚构数据和指导执行，但不能把“计划执行”写成“已经通过”。
- 只有执行人明确确认，或存在本次真实浏览器操作、截图、日志等证据时，才能标记 `通过`。
- `失败` 必须记录实际结果、复现条件和关联缺陷；`阻塞` 必须记录环境或依赖原因。
- 截图和日志记录路径或链接即可；不要把大体积二进制产物放入 `.specs`。
- 任一必要项为 `未执行`、`失败` 或 `阻塞` 时，人工验收结论不得写“通过”。
- 开始执行时记录当前分支或提交以及可提交内容状态。任一验收项执行后若生产代码、配置、依赖或测试替身发生变化，受影响项立即失效并恢复为 `未执行`；重新执行后才能再次通过。最终自动化验证绑定代码快照，不能反向证明较早的人工步骤仍然有效。

## 6. 与验证状态衔接

方案先行任务的所有必要人工项均通过后，由统一命令执行最终自动化验证并记录完整证据：

```bash
npm run spec -- verify <KEY> \
  --run "npm run check" \
  --manual-acceptance
```

`spec verify` 会亲自执行最终自动化命令，并自动校验本文件的总体结论、统计、残留占位内容和 SHA-256；不要求开发者手填证明字段。成功后进入 `quality_review`。如果任务不需要人工验收，由 `run-all-tests` 直接执行自动验证；如果需要但尚未完成，则不能提前进入质量审查。

直接实现不运行 `spec verify`。完成必要人工项后，把实际结果交给 `run-all-tests` 汇总自动化与人工覆盖，再进入代码审查或 Git 交接；代码变化时仍按上一节重新执行受影响人工项。

## 7. 完成输出

最终报告至少说明：

- 记录位置（方案先行任务写文件路径；直接实现写“会话级记录”）和覆盖的验收场景；
- 执行环境、分支或提交、执行人和日期；
- 通过、失败、阻塞、未执行和不适用数量；
- 失败或阻塞项及下一步；
- 自动化验证证据和人工验收是否足以进入质量审查。
