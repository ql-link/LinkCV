# 阿里巴巴 MySQL 规约（DrawOffer 适用版）

依据《阿里巴巴 Java 开发手册》MySQL 数据库章节（嵩山版、黄山版）整理。手册按约束力分为：

- **【强制】**：必须遵守，违反即为缺陷；
- **【推荐】**：默认遵守，偏离要写明理由；
- **【参考】**：设计时参考。

手册面向 Java/MyBatis，只与 Java 语言或 iBATIS/MyBatis 写法相关的条目没有收录。“项目落地”是 DrawOffer 对条文的具体解释，与条文同等执行。

## 适用范围

- **新建表、新增字段、新增索引**：全部条目适用。
- **修改存量表**：不追溯改名、改主键或删除已有外键，新增字段仍遵守字段级条目；与存量命名冲突时沿用该表已有写法（例如该表已用 `created_at`，就不再新增 `create_time`），并在方案的“规约自检”中列为存量例外。
- **偏离**：新结构确需偏离【强制】条目时，必须作为待确认问题由用户确认，并在“规约自检”中写明原因。

存量整改另行批量处理，不在单个业务需求中顺带完成。

## 一、建表规约

1. 【强制】表达“是与否”的字段必须命名为 `is_xxx`，类型为 `unsigned tinyint`（1 表示是，0 表示否）。任何非负数字段都必须是 `unsigned`。
   - 项目落地：注释写明 `1 是，0 否`；可以加 `CHECK (is_xxx IN (0, 1))`。Python/TypeScript 字段名可以去掉 `is_` 前缀，由 ORM 列名映射。
2. 【强制】表名、字段名只使用小写字母、数字和下划线；不能以数字开头，两个下划线之间不能只有数字。
   - 反例：`level_3_name`。正例：`level3_name`。
3. 【强制】表名不使用复数名词。表名只表示实体类型，不表示实体数量。
   - 正例：`job_match_result`。反例：`job_match_results`。
4. 【强制】不使用保留字作为表名或字段名，例如 `desc`、`range`、`match`、`delayed`。
   - 项目落地：完整列表以 MySQL 8.4 官方“Keywords and Reserved Words”中标记为保留字的条目为准。
5. 【强制】主键索引名为 `pk_字段名`，唯一索引名为 `uk_字段名`，普通索引名为 `idx_字段名`。
   - 项目落地：为避免全库重名，使用 `uk_<表名>_<字段>`、`idx_<表名>_<字段>`；检查约束使用 `ck_<表名>_<含义>`。名称不超过 64 字符，超长时缩写表名并保持可读。
6. 【强制】小数类型使用 `decimal`，禁止使用 `float` 和 `double`。
   - 说明：`float`、`double` 存在精度损失，比较时可能得到错误结果。超出 `decimal` 范围时把整数和小数部分拆开存储。
7. 【强制】存储的字符串长度几乎相等时，使用 `char` 定长类型。
   - 正例：SHA-256 十六进制摘要使用 `char(64)`。
8. 【强制】`varchar` 长度不超过 5000。超过时使用 `text`，并独立成一张表、用主键对应，避免影响其他字段的索引效率。
   - 项目落地：`varchar` 长度来自协议、产品限制或真实数据上界，不无依据地统一写 255。大正文、JSON 和原始文件内容优先放对象存储或独立表；放在主表时在方案中说明读写频率和行大小影响。
9. 【强制】表必备三字段：`id`、`create_time`、`update_time`。
   - `id` 为主键，类型 `bigint unsigned`，单表自增，步长 1；
   - `create_time`、`update_time` 为 `datetime` 类型；
   - 项目落地：沿用项目的 `datetime(6)` 微秒精度与 UTC 语义，默认值 `current_timestamp(6)`；更新记录时必须同时更新 `update_time`（见 ORM 映射第 2 条）。
10. 【推荐】表名遵循“业务名称_表的作用”。
    - 正例：`mock_interview_question`、`job_match_result`。
11. 【推荐】库名与应用名称尽量一致。
12. 【推荐】修改字段含义或给状态字段追加取值时，及时更新字段注释。
    - 项目落地：表和每个字段都必须有中文注释；状态字段在注释中列出全部合法值。
13. 【推荐】字段允许适当冗余以提高查询性能，但必须考虑数据一致。冗余字段应当满足：不是频繁修改的字段；不是唯一索引的字段；不是 `varchar` 超长字段，更不能是 `text` 字段。
    - 项目落地：方案中写明冗余字段的真值来源和同步时机。
14. 【推荐】单表行数超过 500 万行或单表容量超过 2GB 时才考虑分库分表。预估三年内达不到这个量级时，不要在建表时就分库分表。
15. 【参考】选择合适的存储长度，既节约表空间和索引空间，也提升检索速度。
    - 例如：人的年龄用 `tinyint unsigned`（0～255）；龟的年龄用 `smallint unsigned`；恐龙化石年龄用 `int unsigned`；太阳年龄用 `bigint unsigned`。

## 二、索引规约

1. 【强制】业务上具有唯一特性的字段，即使是组合字段，也必须建成唯一索引。
   - 说明：应用层即使做了完善的校验，只要没有唯一索引，根据墨菲定律，必然会产生脏数据。唯一索引对插入速度的影响可以忽略。
2. 【强制】超过三个表禁止 join。需要 join 的字段，数据类型必须绝对一致；多表关联查询时，被关联的字段必须有索引。
   - 项目落地：关联字段与被引用主键的类型、长度、有无符号完全一致。
3. 【强制】在 `varchar` 字段上建立索引时必须指定索引长度，没必要对全字段建立索引，根据实际文本区分度决定索引长度。
   - 说明：可以用 `count(distinct left(列名, 索引长度)) / count(*)` 估算区分度；长度 20 的前缀索引区分度通常可达 90% 以上。
   - 项目落地：普通索引评估前缀长度；需要整值唯一的唯一索引使用全长，并在方案中说明理由；索引总长度不超过 InnoDB 3072 字节上限（`utf8mb4` 每字符按 4 字节计）。
4. 【强制】页面搜索严禁左模糊或全模糊，需要时走搜索引擎。
   - 说明：索引文件具有 B-Tree 的最左前缀匹配特性，左边的值不确定时无法使用索引。
5. 【推荐】有 `order by` 的场景利用索引的有序性。`order by` 的字段作为组合索引的最后一部分，并放在索引组合顺序的最后，避免 `file_sort`。
   - 正例：`where a = ? and b = ? order by c`，索引 `a_b_c`。
   - 反例：索引中有范围查找时，索引有序性无法利用，如 `where a > 10 order by b`，索引 `a_b` 无法排序。
6. 【推荐】利用覆盖索引进行查询，避免回表。
7. 【推荐】利用延迟关联或子查询优化超多分页场景。
   - 项目落地：用户可见列表优先使用“时间 + ID”游标分页。
8. 【推荐】SQL 性能优化目标：至少达到 `range` 级别，要求是 `ref` 级别，最好是 `consts`。
9. 【推荐】建组合索引时，区分度最高的列放在最左边。存在非等值和等值混合判断时，把等值条件的列前置。
   - 正例：`where c > ? and d = ?`，即使 `c` 区分度更高，也把 `d` 放在索引最前列，即索引 `idx_d_c`。
10. 【推荐】防止字段类型不同造成隐式转换，导致索引失效。
11. 【参考】避免三种极端误解：宁滥勿缺（认为一个查询就需要建一个索引）；宁缺勿滥（认为索引消耗空间、拖慢更新和新增速度）；抵制唯一索引（认为唯一性一律在应用层“先查后插”解决）。

## 三、SQL 语句

建表评审主要关注第 6 条；其余条目约束实现阶段的查询写法。

1. 【强制】统计行数使用 `count(*)`，不要用 `count(列名)` 或 `count(常量)` 替代。`count(*)` 是 SQL92 定义的标准统计行数语法，会统计值为 NULL 的行，`count(列名)` 不会。
2. 【强制】`count(distinct col)` 计算该列除 NULL 之外的不重复行数；`count(distinct col1, col2)` 中只要有一列全为 NULL，即使另一列有不同的值，也返回 0。
3. 【强制】某一列的值全是 NULL 时，`count(col)` 返回 0，但 `sum(col)` 返回 NULL，使用 `sum()` 时注意 NPE 问题。
   - 正例：`select if(isnull(sum(g)), 0, sum(g)) from table;`
4. 【强制】使用 `isnull()` 判断是否为 NULL 值。NULL 与任何值的直接比较都为 NULL。
5. 【强制】代码中写分页查询逻辑时，`count` 为 0 应当直接返回，避免执行后面的分页语句。
6. 【强制】不得使用外键与级联，一切外键概念必须在应用层解决。
   - 说明：外键与级联更新适用于单机低并发，不适合分布式、高并发集群；级联更新是强阻塞，存在数据库更新风暴的风险；外键影响数据库的插入速度。
   - 项目落地：新表不建 `FOREIGN KEY` 约束，也不依赖 `ON DELETE CASCADE/SET NULL`。关联字段必须建索引；存在性和归属由 FastAPI 在可信边界校验；删除时在同一事务中显式清理或拒绝；对应测试覆盖“关联对象不存在”“删除父对象”“跨用户引用”三类场景。存量表已有外键不在单个需求中移除。
7. 【强制】禁止使用存储过程。存储过程难以调试和扩展，更没有移植性。
8. 【强制】数据订正（特别是删除或修改记录操作）时，先 `select`，避免误删除，确认无误才能执行更新语句。
   - 项目落地：迁移中的回填和清理先做只读预检，范围不符时中止。
9. 【推荐】`in` 操作能避免则避免；避免不了时，`in` 后面的集合元素数量控制在 1000 个以内。
10. 【参考】需要全球化时，字符存储与表示均使用 UTF-8 编码；需要存储表情时选择 `utf8mb4`。
    - 项目落地：业务表统一 `InnoDB`、`utf8mb4`、`utf8mb4_0900_ai_ci`；需要区分大小写或按字节比较的列单独声明排序规则并说明原因。
11. 【参考】`truncate table` 比 `delete` 速度快、使用的系统和事务日志资源少，但 `truncate` 无事务且不触发 trigger，有可能造成事故，不建议在开发代码中使用。

## 四、ORM 映射

1. 【强制】表查询中一律不要使用 `*` 作为查询的字段列表，需要哪些字段必须明确写明。
   - 说明：增加查询分析器解析成本；增减字段容易与映射配置不一致；无用字段增加网络消耗，尤其是 `text` 类型字段。
   - 项目落地：手写 SQL 和迁移中的数据处理语句明确列出字段；SQLAlchemy 查询大字段时使用延迟加载或只选必要列。
2. 【强制】更新数据表记录时，必须同时更新记录对应的 `update_time` 字段值为当前时间。
3. 【推荐】不要写一个大而全的数据更新接口。不管是不是自己的目标更新字段，都进行 `update table set c1=value1, c2=value2, c3=value3` 是不对的；只更新改动的字段。
4. 【参考】事务不要滥用。事务会影响数据库的 QPS；使用事务的地方需要考虑各方面的回滚方案，包括缓存回滚、搜索引擎回滚、消息补偿、统计修正等。

## 五、规约自检清单

新增或修改结构时逐项核对，结果写入方案的“规约自检”：

- [ ] 新表名为小写单数、“业务名称_表的作用”，非保留字；
- [ ] 新表有 `id bigint unsigned` 自增主键、`create_time`、`update_time`；
- [ ] 布尔字段为 `is_xxx tinyint unsigned`，非负数字段为 `unsigned`；
- [ ] 小数为 `decimal`，没有 `float`/`double`；
- [ ] 定长字符串为 `char`，`varchar` 长度有依据且不超过 5000，超长内容独立成表或放对象存储；
- [ ] 表和每个字段有中文注释，状态字段列出全部合法值；
- [ ] 业务唯一性都有唯一索引，命名为 `uk_`；普通索引为 `idx_`；
- [ ] 每个索引都对应真实查询，组合索引顺序符合等值前置、区分度和排序要求；
- [ ] `varchar` 索引已评估前缀长度，或说明使用全长的理由；
- [ ] 关联字段类型与被引用主键完全一致且有索引；
- [ ] 新表没有外键与级联，关联完整性和删除清理在应用层有明确归属和测试；
- [ ] 存量表的冲突写法已列为存量例外，偏离【强制】条目的已经用户确认。
