# MySQL 表结构规范

## 1. 职责与当前边界

把已确认的业务实体和访问模式转换为物理 schema 设计，输出设计依据与评审清单。本技能不直接连接数据库、不执行 DDL，也不把示例 SQL 当成已经落库的事实。

LinkCV 已有 FastAPI 业务模型、MySQL 8.4 配置和 Alembic/SQL-first 基础；根 revision `0001` 已创建 `users`、`resumes`。现有 ORM 与迁移链共同约束当前 schema，但不能证明每个目标环境都已经迁移到 head。后续 schema 设计必须结合冻结需求、真实访问模式、当前模型和已有物理约束；不得因为其他项目使用某种主键、状态或时间策略就直接照搬。

## 2. 必读输入

1. 方案文档中的实体、字段和关系；本技能通常由 `solution-generator` 在起草数据模型章节时调用，不要求方案文档先冻结；
2. 已有 Acceptance 或方案文档中的查询、写入、唯一性、权限、并发和失败场景；
3. 方案文档中已经确认的持久化边界、数据归属与旧数据决策；
4. 真实调用方的读写模式、排序、分页、过滤和生命周期；
5. 已存在的模型、Alembic 基础、revision、SQL 文件和数据库文档；分别说明“模型与仓库 head 的状态”和“目标环境是否已迁移”，不得合并成一个状态。

## 3. 命名与所有权

- 表、列统一使用小写 `snake_case`，名称表达业务含义，不用拼音、缩写堆叠或框架术语代替领域概念；
- 同一类对象的单复数约定在首次模型基线中统一，之后不得混用；
- 主键、外键、唯一约束、普通索引和检查约束使用稳定前缀，例如 `pk_`、`fk_`、`uk_`、`idx_`、`ck_`，具体长度满足 MySQL 限制；
- 多租户或用户资源表必须有明确所有权字段及数据库索引，但权限仍在可信应用边界校验，不能只依赖字段存在。

## 4. 字段与约束

### 主键

- 根据跨系统生成、写入局部性、暴露风险和关联成本选择 `BIGINT`、UUID 或其他方案，并在方案文档的数据模型章节说明；
- 不同时保留两个含义不清的“主键”；业务唯一标识使用显式唯一约束；
- 外键类型、长度和有符号性必须与被引用主键完全一致。

### 字符串、状态与大字段

- `VARCHAR` 长度来自协议、产品限制或真实数据上界，不统一使用无依据的 255；
- 可扩展状态优先使用受应用枚举约束的短字符串，并明确合法状态、默认值和状态迁移；是否增加数据库检查约束由兼容需求决定；
- 长文本、JSON 和二进制只用于确实需要的内容，不把高频过滤字段藏进 JSON；
- 区分 `NULL`、空字符串和缺省值的业务语义，避免用多个表示表达同一状态。

### 数值、布尔与时间

- 金额和精确比例使用 `DECIMAL`，不用浮点数；计数明确是否允许负值和溢出范围；
- 布尔字段明确默认值和历史数据处理，不用含义模糊的整数状态替代多状态枚举；
- 全部业务时间明确时区语义和精度。创建、更新时间是否由应用或数据库维护必须全项目一致；
- 需要软删除时明确唯一约束、查询过滤、恢复和真正清理策略，不能只增加一个删除时间字段。

### 关系与删除

- 外键、级联、限制删除或置空必须根据资源生命周期设计；高风险级联删除需要明确验收和恢复方案；
- 多对多关系使用显式关联表，并对重复关系建立唯一约束；
- 依赖业务代码维护的完整性也要说明并测试，不能误称数据库已经保证。

## 5. 索引设计

1. 从真实查询的等值条件、范围条件、排序、分页和关联路径反推索引，不按字段数量机械添加。
2. 联合索引按最左前缀与选择性设计，同时检查是否被已有索引覆盖；唯一约束本身已有索引语义。
3. 避免对低选择性字段单独建索引；状态字段通常需要与所有权或时间字段组成联合索引。
4. 检查函数、隐式类型转换、前导通配符和排序方向是否导致索引无法使用。
5. 对关键查询使用代表性数据和 `EXPLAIN` 验证；没有执行计划时只写“索引设计待验证”。
6. 评估索引对写入、锁、存储和迁移时间的影响，不追求固定索引数量。

## 6. 引擎、字符集与注释

- 业务表使用 InnoDB；字符集使用 `utf8mb4`；排序规则在首次持久化基线中统一，禁止各表随意漂移；
- 表和关键字段应有准确中文注释，状态字段说明合法值或指向权威枚举；
- 数据库默认值与 ORM 默认值的生效位置必须明确，避免两套默认逻辑不一致；
- 不在 schema、注释、默认值或示例中写入真实用户简历、联系方式、密码或密钥。

## 7. 输出格式

```text
设计结论：可落迁移 | 需要决策 | 证据不足
实体与关系：<表及所有权、关联和生命周期>
字段清单：<名称、类型、可空、默认、约束、语义>
约束与索引：<对应的业务规则或查询路径>
时间与删除：<时区、审计字段、软硬删除>
兼容与存量数据：<已有数据处理和发布窗口>
待验证：<EXPLAIN、数据量、锁或边界假设>
```

若由 `solution-generator` 调用，把物理 schema 结论返回方案文档的数据模型章节和定稿 DDL，不能另建第二份方案或直接落地代码；方案文档冻结并进入实施后，才转 `alembic-migration` 同步 ORM 与 SQL-first revision。若字段语义、所有权、旧数据或删除行为仍有分歧，交回 `solution-generator` 向用户确认，不要在 DDL 中替用户决定。
