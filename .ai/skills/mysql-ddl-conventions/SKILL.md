# MySQL 表结构规范

## 1. 职责与当前边界

把已确认的业务实体和访问模式转换为物理 schema 设计，输出结构片段、设计依据和规约自检结果。本技能不直接连接数据库、不执行 DDL，也不把示例 SQL 当成已经落库的事实。

表结构和字段的唯一规范是 [alibaba-mysql-rules.md](alibaba-mysql-rules.md)，它整理了《阿里巴巴 Java 开发手册》MySQL 章节的建表、索引、SQL 和 ORM 规约，以及 LinkResume 的落地解释。本文件只补充流程和项目特有约定，与规约冲突时以规约为准。

LinkResume 使用 MySQL 8.4、SQLAlchemy 和 SQL-first Alembic。现有 ORM 与迁移链共同约束当前 schema，但不能证明每个目标环境都已迁移到 head。

## 2. 新表与存量表

- **新表、新增字段、新增索引**：全部规约条目适用，包括单数表名、`id`/`create_time`/`update_time` 三字段、`is_xxx tinyint unsigned`、`decimal` 小数、`pk_`/`uk_`/`idx_` 命名，以及不建数据库外键与级联。
- **修改存量表**：不追溯改名、改主键或删除已有外键。新增字段遵守字段级规约，但与该表已有写法冲突时沿用已有写法（例如该表已有 `created_at`、`updated_at`，就不再新增 `create_time`），并在方案“规约自检”中列为存量例外。
- **新表关联存量表**：关联字段类型与被引用主键完全一致；即使被引用表本身使用外键，新表也不新增外键。
- **偏离**：新结构确需偏离【强制】条目时，交回 `solution-generator` 作为待确认问题由用户确认，不在结构片段中替用户决定。

存量整改由专门的批量迁移处理，不在单个业务需求中顺带完成。

## 3. 必读输入

1. 方案文档中的实体、字段、关系和已确认的数据决策；
2. 方案或 Acceptance 中的查询、写入、唯一性、权限、并发和失败场景；
3. 真实调用方的读写模式、排序、分页、过滤和生命周期；
4. 相关表的现有 ORM 模型、`apps/backend/migrations/sql/` 中的 SQL 和 `docs/internals/backend.md`；分别说明“模型与仓库 head 的状态”和“目标环境是否已迁移”，不得合并成一个状态；
5. [alibaba-mysql-rules.md](alibaba-mysql-rules.md)。

## 4. 设计要点

规约已经覆盖的内容不在此重复，这里只列设计时容易遗漏的判断：

- **所有权**：用户资源表必须有所有权字段（通常是 `user_id`）及以它开头的索引；权限仍在可信应用边界校验，不能只依赖字段存在。
- **对外 ID**：数据库中的 `bigint unsigned` ID 在 HTTP、TypeScript 和对象存储 key 中表示为规范十进制字符串，与现有约定一致。需要不可枚举的对外标识时，单独设计唯一列并在方案中说明。
- **状态字段**：使用受应用枚举约束的短字符串，注释列出全部合法值，并配 `CHECK` 约束；状态迁移规则写在方案状态机中。
- **NULL 语义**：区分 `NULL`、空字符串和缺省值的业务含义，避免多种表示表达同一状态。
- **JSON 与大字段**：不把高频过滤字段藏进 JSON；JSON 列写明结构、版本和 `json_type` 校验；大正文优先放对象存储或独立表。
- **时间**：业务时间统一 UTC 语义和 `datetime(6)` 精度；`create_time`、`update_time` 沿用现有模型的时间列映射，`update_time` 在 ORM 中声明 `onupdate`，保证每次更新都刷新。
- **软删除**：确需软删除时同时设计唯一约束、查询过滤、恢复和真正清理策略，不能只加一个删除时间字段。
- **应用层完整性**：不建外键时，写清由哪个服务在什么事务中校验存在性和归属、删除父对象时清理还是拒绝，并要求测试覆盖。
- **默认值**：数据库默认值与 ORM 默认值的生效位置必须明确，避免两套默认逻辑不一致。
- **索引验证**：对关键查询用代表性数据和 `EXPLAIN` 验证；没有执行计划时只写“索引设计待验证”。同时评估索引对写入、锁、存储和迁移时间的影响。
- **示例数据**：不在 schema、注释、默认值或示例中写入真实用户简历、联系方式、密码或密钥。

## 5. 输出格式

输出供 `solution-generator` 写入方案“数据库变更”章节，包含：

1. **数据影响**：按数据对象用正常文本说明读写方、归属、权限和不变量，不使用横向表格；
2. **数据结构变更**：按表组织。每张表先说明用途、一行代表什么和预计量级；字段用 SQL 风格结构片段，写类型、可空性、默认值和注释；约束与索引放在单独的片段中，每个索引用行尾注释写明对应的业务规则或查询路径；最后写关联与完整性由哪一层保证；
3. **存量数据与迁移**（按需）：只有存在存量数据处理、兼容窗口、迁移顺序、数据回退或不可逆点时输出，用正常文本描述，不生成回填 SQL；
4. **规约自检**：按 [alibaba-mysql-rules.md](alibaba-mysql-rules.md) 的自检清单逐项核对，全部符合时写一句结论；有存量例外或经确认的偏离时逐条列出条目和原因。

所有结构片段只供评审，不生成 `CREATE TABLE`、`ALTER TABLE`、`CREATE INDEX` 等可直接执行的 DDL。

由 `solution-generator` 调用时，把结论返回方案文档，不另建第二份方案或直接落地代码；方案确认并开始实施后，才转 `alembic-migration` 同步 ORM 与 SQL-first revision。字段语义、所有权、旧数据或删除行为仍有分歧时，交回 `solution-generator` 向用户确认。
