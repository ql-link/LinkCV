# LinkCV 前端设计

## 1. 目标与边界

在业务目标、后端契约和权限规则已经明确后，把功能转成一致、可用、可测试且具有明确设计意图的页面。不要要求用户先给出字号、间距、色值或控件坐标；按本次档位从真实代码、根目录 [`DESIGN.md`](../../../DESIGN.md)、[Web 模块事实](../../../docs/internals/web.md) 和适用的上游视觉方法中读取必要依据。

本技能把 Anthropic 的审美与自我批评方法、LinkCV 的工程约束和 Vercel 的界面质量规则组合成一条路径，不重新发明接口、权限、状态或业务流程。公共 `/` 落地页可以独立设计；登录与注册属于宣传入口层，但表单控件仍使用项目 UI 组件。简历纸张、Markdown 内容和 PDF 排版不使用软件界面 Token。

## 2. 先选择执行档位

根据本次实际变化选择最小足够档位，不按文件数量升级：

| 档位 | 适用范围 | 默认处理 |
| --- | --- | --- |
| `轻量` | 纯逻辑修复、文案、局部间距或尺寸、已有组件属性调整，且不新增交互模式、页面区域或响应式规则 | 直接核实邻近实现，不写 Design Brief，不做视觉方向探索 |
| `标准` | 既有页面内新增或改变可见交互、字段、状态、弹窗或局部布局，但整体信息架构和视觉方向不变 | 写 3–5 行变化摘要，只检查受影响状态和断点 |
| `完整` | 新页面、页面主要区域重组、营销或入口视觉重做、从截图或 21st.dev 适配、建立新的视觉方向 | 使用完整 Brief、组件选型、界面审查和多断点浏览器闭环 |

无法明确归入轻量或完整时使用标准。严格权限、数据或契约风险增加针对性验证，但不自动升级为完整视觉设计；纯逻辑修改如果改变用户可见行为，至少使用标准档。

## 3. 必读材料

按顺序读取：

1. 用户当前请求、真实路由中已确认的当前差异或已经确认的 HTML 原型/Figma 设计稿、可用 Issue；混合任务同时读取已确认 `solution.md`；
2. 当前 Agent 尚未读取时读取 `AGENTS.md`；只有本次需要定位模块事实时才进入 `docs/README.md`，不重复加载同一会话已有且未失效的材料；
3. 标准或完整档读取根目录 [`DESIGN.md`](../../../DESIGN.md) 和 [Web 模块事实](../../../docs/internals/web.md)；轻量档只在改动涉及对应规则时读取；
4. 只有完整档才读取 [Anthropic 视觉方向适配](references/aesthetic-direction.md)；
5. 标准或完整档制作真实页面预览或 HTML 原型时读取 [可视预览拒收门禁](references/prototype-quality-gate.md)；
6. 页面对应的目标实现、直接调用方和最近测试；API、类型与路由只在本次行为涉及它们时读取；
7. 新增或替换共享组件时读取 `apps/web/components.json`、`src/design-system/tokens.css` 和相关 `src/components/ui/` 文件；复用已有组件时不盘点整个组件目录；
8. 用户提供的 21st.dev 文字、截图或代码；有截图时把它当作局部设计来源，而不是全站事实源。

如果后端契约、权限、状态或错误语义仍未确定，回到当前交付路径的上游收敛需求，不用视觉设计掩盖业务缺口。

## 4. 页面设计流程

### 4.1 先收敛方向，再形成最小设计判断

轻量档不写 Design Brief，直接说明修改对象、保持不变的行为和最小验证。

标准和完整档先按 `frontend-delivery` 用一个问题询问大致方向偏好。只问密度、气质或本次优先目标，不让用户提前规定色值、字号、间距和控件坐标；用户已经给出清楚方向时不重复询问。应告诉用户可以画一版推荐方案，也可以按需画多个方向供比较。

标准档在会话或实施 Agent 的任务消息中用 3–5 行说明：用户结果、受影响区域或操作、涉及的状态、需要检查的断点、复用的现有组件。已有确认的真实路由差异、HTML 原型或 Figma 时直接使用；混合任务的 `solution.md` 只提供业务与契约约束，不替代 UI 设计。

完整档不要求在实施前一次写完 Design Brief。下面这些判断按依赖逐轮进入会话级短判断，只有当它会影响下一次可见修改时才处理：

- 页面主题与目标受众；
- 页面类型和唯一主任务；
- 信息优先级与主要区域；
- 主操作、次操作和危险操作；
- 加载、空、错误、成功、禁用和权限不足状态；
- 桌面、小桌面、移动端的布局变化；
- 从现有 Token 和字体角色形成的视觉方向，以及一个有业务理由的标志性元素；
- 计划复用、查询和新增的组件。

复杂列表、工作台或设置页最终要收敛出明确操作顺序和状态反馈，但不要求用户在看到页面前一次回答所有问题。

每一轮遵循：读取最新反馈和当前画面 → 只提出一个高影响问题或采用推荐假设 → 修改一个连贯层面 → 展示实际结果 → 等待下一轮反馈。当前文件、原型和 Brief 只保存画面或约束，不是固定提示词；用户最新明确反馈优先。

### 4.2 视觉判断

轻量档继承目标页面现有视觉决定，不提出新的构图、字体、色板或标志性元素。标准档只核对新增内容是否延续现有层级、Token 和空间关系，不要求为了“辨识度”创造新元素。

完整档才进行以下两遍判断：

第一遍从 Brief 得到紧凑设计计划：

- `主题`：从简历创建、求职、编辑或管理任务自身提取语言和结构，不套用任意 SaaS 页面；
- `色彩`：内部功能区把 4–6 个语义角色映射到现有 `--ui-*` Token，不为单页另建十六进制色板；营销页可以提出独立色板，但要限定在营销样式边界；
- `字体`：从 `DESIGN.md` 选择 display、body、utility 角色，不因追求独特而为每页新增字体；
- `布局`：用一两句说明信息流，布局仍不清楚时用小型 ASCII 线框比较；
- `标志性元素`：只选择一个与任务有关、用户能记住的构图、材质或交互，其余区域保持克制。

第二遍在编码前自我批评：如果换成任意后台产品仍然成立，说明设计过于模板化；如果记忆点只是装饰、影响效率或破坏四类视觉边界，就删除或收敛。内部功能区的“冒险”可以只是更精确的信息结构、排版或空间关系，不要求炫技。

新增页面、主要区域重组、信息层级、密度或响应式结构是本次设计内容时，使用 `ui-layout-design` 形成布局命题并验证；局部文案、颜色、单个控件或已定位间距修改不为此增加布局流程。

### 4.3 生成可运行预览

标准或完整档的用户评审对象必须是当前可见、可操作的界面，不是长篇 UI 文档。预览是人与 AI 对话的共享画布，不是需要一次确认的最终方案：

- 已有可运行路由且用户授权修改当前工作区时，默认直接修改真实页面形成可回退预览；复用真实应用壳、组件、字体、Token 和数据边界，用户确认前不提交或推送；
- 全新页面、没有可运行入口或真实代码预览会过早固化高影响结构时，在 `.specs/<KEY>/prototype/index.html` 制作自包含原型，使用语义 HTML、原生 CSS 和表达关键状态所需的最少 JavaScript；不新增依赖，不访问网络，不调用真实 API；
- 独立 HTML 原型从目标页面和设计 Token 提取视觉依据，但保持与生产源码隔离，不导入应用组件，也不把原型当作最终实现；
- 在本地浏览器实际渲染并向用户展示。标准档聚焦受影响区域和关键状态；完整档覆盖完整页面，并至少核对宽屏与窄屏结构；
- 使用真实字段、合理内容长度、明确操作层级与可操作状态；本次新增或改变的按钮、表单、切换、弹层或响应式变化应能用即时状态切换演示，而不是只画静态外观；
- 每轮以尽快验证一个判断为目标：不复刻未改变的完整业务逻辑，不模拟网络延迟、真实文件处理、全量校验或所有异常；只有这些行为本身是当前轮次待确认设计时才纳入；
- 用户要求多个方向时保持同一内容与状态，分别生成清楚命名的原型入口，只改变待比较的布局、密度或视觉方向；
- 用户明确指定 Figma 时，完整使用适用的 Figma Skill 创建或更新设计稿，返回用户可访问链接，不再生成 HTML 原型；
- 用户明确要求概念图或图像生成时才使用 `imagegen`；图像只用于发散视觉方向，不替代可实施原型或 Figma，也不作为确认门禁；
- 加载、错误、键盘、焦点和响应式行为不能完全演示时只附短说明，不回退为 `ui-design.md`。
- 展示前必须按 [可视预览拒收门禁](references/prototype-quality-gate.md) 查看实际桌面和移动截图；卡片滥用、比例失衡、层级扁平、核心文字过小、模板化装饰或错误强调命中任意一项时先修订，不能用“无溢出、可点击、使用了 Token”代替视觉判断。

真实页面、HTML 原型或 Figma 都可以连续修改，不把某一版冻结成后续唯一指导。用户明确表示方向稳定后再统一补齐实现、测试和交付；视觉判断与真实契约冲突时以业务和权限依据为准，不让实施 Agent 自行猜测，也不要把独立原型文件直接搬入生产目录。

### 4.4 按需选择组件

需要新增或替换组件时依次判断：

1. `src/components/ui/` 是否已有满足语义的组件；
2. shadcn registry 是否有适合的 primitive；
3. 是否只需在同一 `components/ui/` 中组合已有 primitive；
4. 只有前三项都不适用时才手写基础交互。

已有项目组件能够满足语义时直接复用，不查询 Registry。确实缺少 primitive 时，优先调用已配置的 shadcn MCP 搜索、查看和安装；默认只查官方 `@shadcn` Registry。当前会话未加载 MCP 时，从仓库根目录使用：

```bash
npx shadcn@latest search @shadcn -q "<需要的语义>" --cwd apps/web
npx shadcn@latest view @shadcn/<name> --cwd apps/web
npx shadcn@latest add @shadcn/<name> --cwd apps/web --dry-run
```

确认 dry-run 的文件、依赖和覆盖范围后才执行真实 `add`。不要因为工具未热加载而改变组件目录或复制 Registry 源码，不批量安装未知组件。21st.dev、Magic UI、Aceternity、React Bits 和 Motion Primitives 默认只是参考来源；只有用户指定效果且已检查依赖、许可、性能和视觉边界时，才通过 shadcn Registry 或对应 CLI 引入单个组件。

shadcn primitive 和 LinkCV 通用组合组件都放在 `apps/web/src/components/ui/`，不创建 `components/product`。一个文件只承担一个组件职责；业务数据请求、权限判断和页面状态留在 feature 内。所有共享组件从 `@/components/ui` 导入。

### 4.5 实现页面

- 使用 `--ui-*` Token 或 Tailwind 中的语义映射；新内部组件不得写死品牌色、阴影或圆角。
- 保持操作层级：每个区域通常只有一个主操作；危险操作使用 destructive 语义并二次确认。
- 表单标签必须与控件关联，错误靠近字段或表单，提交中禁用重复操作并保留明确文案。
- 新增列表或重做其数据流时设计加载、空、错误和分页/继续加载状态；局部修改只保证受影响状态不退化，不借机补做与任务无关的全部页面状态。
- 不使用持续背景 Shader、无意义粒子、自动播放装饰或会干扰工作的循环动画。动效只说明状态变化和空间关系，并支持 `prefers-reduced-motion`。
- 不用纯色块或装饰卡片填补缺少的信息层级；先调整信息结构、间距和排版。
- 页面结构、编号、眉题、分隔线和标签必须表达真实关系，不把无顺序内容伪装成 `01 / 02 / 03` 流程。
- 界面文案站在用户一侧，用可识别的任务和动作命名；按钮、反馈和结果沿用同一个动词，错误说明下一步，空状态提供可执行入口。
- 保持业务事件、API 调用、错误码、路由和权限行为不变，除非当前任务明确要求改变。

### 4.6 分级验证与浏览器闭环

编码过程中只运行能快速暴露当前错误的聚焦测试或检查。实现稳定后统一交给 `run-all-tests` 执行本次范围要求的前端测试、类型检查和构建；代码未变化时，不在两个阶段重复同一条完整命令。

- `轻量`：行为变化时补最近的 Vitest/Testing Library 测试；纯文案或样式变化不强制新增断言。只有结果无法从代码和自动化检查确定时才启动浏览器，并只检查受影响区域。
- `标准`：为改变的交互补最近测试；按 [Vercel 界面质量审查适配](references/interface-quality.md) 的稳定检查面审查受影响代码，不固定联网刷新上游规则；浏览器检查受影响路由、状态和主要目标断点，响应式可能受影响时再增加一个相邻断点。
- `完整`：获取最新版 Vercel 规则并审查本次 TSX/CSS；构建通过后启动真实 Web，至少检查 1440、1024、390，覆盖适用的键盘、焦点、溢出、弹窗、加载/空/错状态和 reduced motion；对照 Brief 完成一轮可见问题修正并复查。

所有档位最后都按项目主链进入 `run-all-tests` 和 `code-review-and-quality`。只有自动化未覆盖且本次实际涉及跨端流程、浏览器交互、上传下载、PDF 或视觉结果时才进入 `manual-acceptance`，不因文件位于前端目录就固定生成或执行完整人工清单。

不能把组件测试或 jsdom 描述成真实浏览器验收。后端、鉴权或数据环境阻塞时，报告未验证的页面和原因，不猜测通过。

## 5. 21st.dev 参考处理

用户提供参考后，先提取可复用意图：布局比例、视觉层级、交互时序、材质、动效和响应式变化。只实现与当前页面任务有关的部分，并用 LinkCV Token、组件和可访问性规则重写。

不要：

- 原样复制未知依赖、全局 reset 或页面级硬编码；
- 把宣传页效果推广到所有内部页面；
- 为单个效果新建第二套 Token 或组件目录；
- 在没有真实内容和状态时只复刻静态截图。

如果参考与业务可用性、性能或可访问性冲突，保留其视觉意图并采用项目内可落地的简化方案，在交付说明中指出差异。

## 6. 完成标准

- 已选择与实际改动匹配的最小执行档位；标准或完整档已确认的真实路由预览、HTML 原型或 Figma 与最终页面一致；
- 真实页面预览或 HTML 原型在交给用户前通过实际截图自审，且没有把明显的比例、层级或审美问题转嫁给用户发现；
- 完整档的视觉方向来自页面主题，标志性元素有业务理由且没有蔓延为装饰噪声；轻量和标准档保持既有视觉方向；
- 页面只使用集中 UI 入口或有明确理由的 feature 局部结构；
- 新组件值来自 `--ui-*` Token，无新的视觉事实源；
- 本次新增或改变的状态、键盘、焦点、响应式和 reduced motion 行为已按档位覆盖；
- 标准或完整档的界面质量审查没有未处理的阻断问题，语境性取舍已有理由；
- 自动化检查有当前证据；真实浏览器检查适用时有当前证据，不适用时没有为了流程形式强制执行；
- 营销、入口、内部功能区和简历文档四个视觉边界没有相互污染；
- 没有顺带改变后端契约、权限或业务语义。
