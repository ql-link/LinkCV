# 模块飞书文档写作指南

这是一份内容指南，不是固定模板。根据模块复杂度选择标题和展开程度，优先使用自然叙述；只有并列关系明显时才使用列表或表格。

## 文档要回答的问题

### 开头摘要

先用一小段话说明本次希望得到的产品能力和用户可见结果。让没有参与讨论的人读完开头就知道“要做成什么”。

### 项目现状

说明当前真实能力、已有入口、可复用部分和具体缺口。只写已通过代码或现有材料核实的事实；计划中的能力不能写成已经实现。

### 本次范围

讲清楚本次会做什么、关键用户流程如何运行，以及哪些相邻能力明确不在本次处理。范围简单时可以融入自然段，不必单独列清单。

### 确认方案

把讨论后的结论组织成接手者能够执行的方案。按需说明模块职责、主要状态或数据流向、接口边界、权限、失败反馈、兼容和迁移方向。说明选择理由，但不保留完整备选方案和问答过程。

前端视觉模块可以重点写产品行为、交互状态和可见结果，不为形式强行补技术建议。鉴权、数据、对象存储、LLM 接入和跨端契约等高风险模块，应展开实际命中的安全、失败、成本、兼容或数据边界。

### 完成结果

用可观察结果说明怎样算完成，包括主流程和真正重要的异常结果。避免“功能正常”“体验良好”“完成相关逻辑”等无法复核的说法。

## 不进入文档的内容

- 逐轮问答、聊天记录和决策树过程；
- 已淘汰的方案堆栈；
- 尚未确认却被写成结论的建议；
- 容易过期的方法级文件清单、代码片段和本地 Spec 状态；
- Issue 评论同步、需求指纹或平台专属元数据。

## 写入前检查

- 开头能独立说明产品目标和结果；
- 当前状态来自真实仓库或明确材料；
- 范围、非目标和确认方案之间没有冲突；
- 所有高影响结论已经过用户确认；
- 接手者无需查看聊天记录也能理解方案；
- 没有仍会改变 Brief 的阻塞性决策。
