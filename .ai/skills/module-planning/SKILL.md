# 模块规划

## 1. 唯一职责

负责一段完整但封闭的前置流程：

```text
读取来源 → 核实事实 → 建立决策树 → 逐项讨论 → 展示完整草稿 → 用户确认 → 写入飞书 → 读回核对 → 停止并交接
```

本技能拥有模块规划会话和飞书详情文档；不拥有来源 Issue、本地 Spec 或代码。标准团队任务以来源 Issue 为初始产品输入，飞书详情文档保存需要跨人协作或长期留存的模块方案。

本技能不是方案先行的强制前置。单个需求范围内的不确定点由 `solution-generator` 在方案文档阶段直接向用户确认；只有整个模块的目标、边界或商业前提尚未成形，或用户要求把结论写入飞书时才使用本技能。

## 2. 与其他技能的调用边界

| 技能 | 本技能如何使用它 | 对方不能替代的职责 |
| --- | --- | --- |
| `decision-grilling` | 对每个阻塞性决策调用一次，按 `confirmed`、`blocked`、`replan` 结果维护当前决策树 | 不调查整个模块、不组织文档、不写飞书 |
| `lark-doc` | 完整草稿确认后执行飞书读取、创建、更新和读回 | 不判断内容是否充分，不发起产品或技术决策 |
| `lark-drive` | 仅在用户未给出目标文档或目录、确需定位位置时使用 | 不负责文档正文 |
| `flow-router` | 规划完成后，尚未分流的开发请求由它判定走直接实现还是方案先行 | 不主持讨论、不写飞书 |
| `solution-generator` | 方案先行且飞书文档确认完成后，由用户另行授权进入 | 不重新采访用户，只综合已确认输入 |

标准调用方向是：

```text
尚未分级的代码请求 ──> flow-router ──需要模块规划──> module-planning
明确要求讨论或撰写模块方案 ──> module-planning
module-planning ──单个决策──> decision-grilling ──确认结论──> module-planning
module-planning ──草稿已确认──> lark-doc ──写入并读回──> module-planning
module-planning ──完成交接并停止──> 用户另行启动 flow-router 或 solution-generator
```

调用方拥有阶段和产物，被调用技能只返回自己边界内的结果。不要让 `decision-grilling` 直接写飞书，也不要让 `lark-doc` 决定正文；本技能完成后不得在同一次调用中自动生成 Brief 或开始编码。

## 3. 进入和停止条件

正常团队任务开始前必须取得：

- 一条可完整读取的来源 Issue；来源可以是 Multica、Linear、GitHub 或其他系统；
- 可以识别的目标模块和期望结果；
- 用户提供的飞书周文档、既有详情文档或目标位置（存在时）。

用户明确要求讨论或撰写模块方案时，即使用户同时指定了交付路径，也直接使用本技能，不先让 `flow-router` 重复分流；已指定的路径只作为后续交接信息。只有“准备改代码但尚未分流”的请求才先进入 `flow-router`。判为直接实现的确定性小改动不强制创建详情文档；但用户明确要求模块规划时仍按本技能执行。

遇到以下情况停止在当前阶段，不越界补救：

- 缺少普通团队任务的来源 Issue：请求稳定链接或正文；
- 飞书不可读：报告权限或连接问题，不根据标题和聊天记忆猜测内容；
- 用户尚未确认完整草稿：保留在讨论或修订阶段，不写飞书；
- 飞书写入后无法读回：报告写入状态未知，不宣布可以生成 Brief；
- 用户要求生成方案文档或代码：完成当前交接后停止，交给对应技能。

工作流自举、本地维护或用户明确关闭工作流时，可以当前请求代替来源 Issue，但必须明确这是例外。

不要为“已确认”新增状态文件、Issue 字段或飞书元数据。当前会话中的最终确认，或者用户在后续会话明确指定“按这份飞书文档生成 Brief/开发”，都可以作为确认依据；仅发现一份文档但无法判断是否定稿时，只询问这一项，不猜测状态。

## 4. 调查事实

1. 读取 `AGENTS.md`、来源 Issue 完整正文和所有明确关联材料。
2. 有飞书链接时先读取 `lark-doc` Skill，再完整读取目标文档；需要定位云空间位置时才读取并使用 `lark-drive`。
3. 读取与模块直接相关的代码、测试和 `docs/`，核实当前入口、已有能力、限制和可复用边界。
4. 把信息分为：已核实事实、仍需调查的事实、用户必须决定的选择。
5. 能从仓库、工具或文档确认的事实继续调查，不把它包装成问题交给用户。

完成本阶段的标准是：足以说明项目现状和真实约束，且每个剩余问题都确实需要用户取舍。

## 5. 收敛决策

建立按依赖排序的决策树，优先处理目标和范围，再处理用户流程、失败表现、权限与数据语义、接口与兼容、迁移与发布，最后才是会影响前述结论的实现方向。局部、可逆且不改变外部行为的实现细节留给方案文档阶段。

每次只把最上游的一项交给 `decision-grilling`。收到用户回答后：

1. `confirmed`：核实回答中新增的事实，记录简洁结论及理由，再继续下一项；
2. `blocked`：记录责任人、所需证据或恢复条件并停止，不起草文档、不进入下一题；
3. `replan`：撤销受影响结论，重建和重排决策树，再从新的最上游问题开始；
4. 用户提前回答的未来问题只作为待核实候选，等依赖成立且轮到该题时再确认；
5. 任何上游结论改变时，使依赖旧结论的下游选择失效并重新排序；
6. 继续到没有阻塞分支后，用简短摘要请用户确认已经形成共同理解。

讨论阶段只维护当前会话中的决策树，不逐题写飞书、不创建独立决策日志，也不修改任何 Issue。

## 6. 起草并确认飞书文档

决策树清空且用户确认共同理解后，完整读取 [模块文档写作指南](references/module-document-guide.md)，在对话中展示一份完整草稿。正文只保留已确认结论，不保留问答过程、备选方案堆栈或聊天记录。

根据复杂度组织内容，不强制套固定标题。草稿必须使接手者能够理解：为什么做、当前怎样、这次做到哪里、主要方案如何运行、哪些边界已经确认、看到什么结果算完成。

用户修订草稿时，先判断反馈是文字调整还是新决策。文字调整直接修订；新决策返回决策树，只处理该分支及受影响内容。每次写入前都重新展示完整最终草稿，并取得明确的“可以写入飞书”确认。

## 7. 写入、读回和交接

取得最终确认后：

1. 按优先级确定唯一目标：来源 Issue 中关联的既有详情文档，或用户直接给出的既有详情文档；其次是用户指定的目标目录；再次是当前周文档所在目录。仍有多个位置或无法确定时才询问，不能擅自在默认根目录创建。
2. 读取最新飞书正文；更新已有文档时只修改已确认范围，保留无关内容。
3. 使用 `lark-doc` 创建或更新文档，并立即保存工具返回的文档 token 和链接。
4. 立即读回标题和正文，逐项核对草稿中的目标、范围、关键结论、实现方向和完成结果。
5. 返回来源 Issue、飞书文档链接、读回结论和下一站。

若创建或更新已经返回成功，但读回失败，状态必须写成“写入状态未知”，同时返回已取得的 token、链接、操作类型和错误。下一次恢复时先读取同一个 token 并比对确认草稿；只有明确证明该对象不存在时才允许重新创建，禁止因读回超时生成重复文档。

只有读回内容与确认草稿一致，才可以标记“模块规划完成”。最终输出使用：

```text
模块规划：已完成 | 未完成
来源 Issue：<链接或稳定引用>
飞书详情文档：<链接；未写入时说明原因>
确认范围：<一句话>
未解决决策：无 | <具体事项>
下一站：等待用户另行启动 flow-router；已判为方案先行时可启动 solution-generator
```

交接后停止。即使用户最初同时要求“规划并开发”，也先让用户看到飞书读回结果，再由新的明确指令启动下游阶段。
