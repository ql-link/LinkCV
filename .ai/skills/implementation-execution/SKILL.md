# 实施执行

## 1. 职责

把已确认的需求和适用设计落实为真实代码，并保持实现、测试和当前确认依据一致。本技能负责：

- 核实前置条件和当前工作区；
- 在确认范围内修改代码、配置、测试和必要文档；
- 处理实现中发现的确认依据或冻结规格偏差；
- 在严格风险或有偏差时，按交付路径形成实施报告或交付摘要；
- 把完成的实现交给测试和质量审查。

本技能不负责创建分支、提交、推送、PR，除非用户另外明确要求进入 `branch-pr-workflow`。

## 2. 进入条件

### 直接实现

- 已由 `flow-router` 明确判为直接实现；
- 分流结果为准备 `可实施`、记录 `会话内`，复杂度为简单或符合直接实施条件的中等；
- 风险可以是常规或严格。严格风险的具体触发项、必要确认、失败结果、回退或不可逆点和验证要求已经明确；仍有会改变权限、数据、安全、兼容或生产结果的选择时不能开工；
- 不要求创建 `.specs`；
- 完整读取来源 Issue 正文；已有详情文档时同时读取；
- Issue 已经足以确定目标、边界和可观察结果。用户明确关闭工作流、自举或本地维护请求可以当前请求代替外部 Issue。

### 方案先行

实现前运行：

```bash
npm run spec -- check <KEY> implementation
```

必须已有冻结的 `solution.md`；方案文档选定契约验收路径时还必须有冻结的 `acceptance.feature`，选定直接施工路径时不产出该文件，方案文档“代码实施计划”和“验证与验收”就是施工与验证契约。已有飞书模块详情文档时一并读取。这些产物应从来源 Issue、飞书详情文档和真实代码中单向收敛。门禁失败时停止，按提示返回上游，不得绕过。Issue 来源平台不参与实现门禁，项目也不接收或生成规格评论回写。

## 3. 必读材料

1. `AGENTS.md`；
2. 来源 Issue 的完整正文和关联材料，不限制来源平台；
3. 用户当前请求和已经确认的范围；
4. 存在飞书模块详情文档时完整读取，不限交付路径；
5. 方案先行任务的 `.specs/<KEY>/state.yaml` 和全部冻结产物；
6. 目标文件、直接调用方、共享类型和最近测试；
7. `git status --short`、当前任务相关差异和用户已有未提交修改；
8. 涉及 API、环境变量或部署时，读取前端 API 客户端、Vite 代理和部署配置；
9. 涉及迁移或存储时，读取现有模型、迁移、事务和回滚方式。

不要只读方案文档而跳过真实代码。方案文档中的路径、字段和契约都需要在实施前再次核实。

## 4. 实施纪律

### 聚焦范围

- 只实现确认范围，不顺带重构无关模块；
- 复用现有模式前先确认它仍适用于当前模块；
- 新依赖必须说明必要性并更新对应锁文件；
- 不覆盖、不丢弃用户已有修改；重叠区域必须先理解再编辑。

### 契约同步

修改接口、共享类型、错误、环境变量或部署行为时，同步检查所有消费方。结构、语义或兼容影响不清楚时使用 `contract-guard`；同一个具体值散落多处时使用 `config-contract-sync`；最终实现改变长期项目事实时使用 `doc-maintenance-sync`。只选择真实命中的技能，不固定串行调用。修改数据库模型时先核实已确认物理 schema，再使用 `alembic-migration` 同步模型与 revision，处理旧数据、事务、兼容发布和回滚；不要手工改库绕过迁移链。

### FastAPI 路由与部署契约

- 当前全部 `/api` 由 FastAPI 处理，仓库不再存在 Express 运行入口；不得寻找或恢复 `server/` 作为兼容方案；
- 修改路由、前端 API client、Vite Proxy、环境变量或部署入口时，必须按当前路径的确认依据同步处理消费方、验证和回滚。方案先行任务以冻结方案文档为准；直接实现以来源材料、当前确认结论和 `flow-router` 列出的严格检查项为准；
- SQLAlchemy 模型和 Alembic 基础已经存在，根 revision `0001` 创建 `users`、`resumes`；后续数据库任务必须落地顺序编号的 SQL-first migration，并核对目标环境 current revision，不能把 SQLite 集成测试当作 MySQL 就绪证据。

### 安全与数据

- 鉴权、资源归属和文件访问必须在可信边界校验；
- 不把用户真实简历、联系方式、密钥或本地敏感路径写入代码和测试；
- 示例与测试数据使用虚构信息，默认姓名使用“张三”。

涉及 LLM 或第三方服务时，严格按当前路径的确认依据落实数据最小化、后端密钥边界、预算和限流、超时重试与幂等、取消和部分结果、降级反馈、脱敏可观测性以及测试替身。方案先行任务消费冻结方案文档；直接实现消费来源材料、当前确认结论和 `flow-router` 的严格检查项。不得把真实简历正文、密钥或供应商完整响应写入日志和测试；不得为了成功率无限重试，或静默切换会改变数据处理承诺的供应商。

## 5. 实施步骤

1. 确认交付路径，运行适用的阶段门禁。
2. 检查工作区和相关差异，区分用户修改与本任务修改。
3. 读取目标代码和测试，列出最小可交付改动顺序。
4. 按依赖顺序实现，每完成一个可验证单元就运行最窄相关检查。
5. 补充或修改距离行为最近的有效测试；简单邻近测试可直接编写，需要独立测试设计、复杂 Mock 或分层调整时使用 `test-authoring`。测试必须能在实现错误时失败。
6. 检查 API、类型、权限、数据、配置、部署和长期文档是否需要同步，按契约影响选择对应专项技能。
7. 实现稳定后更新必要 `docs/`，不要把临时 Spec 内容复制成项目现状。
8. 完成后交给 `run-all-tests` 执行范围匹配的自动化验证；方案先行任务的最终命令由 `spec verify --run` 亲自执行并自动绑定当前代码快照。
9. 存在跨端、浏览器、上传下载、PDF 或视觉行为且自动化测试未覆盖时，转 `manual-acceptance` 生成并记录人工验收；不适用时直接跳过。
10. 全部必要验证通过后交给 `code-review-and-quality` 做最终质量审查。方案先行任务进入 `quality_review`，无阻断问题时由 Agent 记录审查结论并进入 `release_ready`；直接实现不伪造 Spec 阶段，只保留真实验证、审查和风险结论。

## 6. 实施偏差与回流

实施中发现以下情况时停止当前实现：

- 新行为不在需求范围内；
- 验收契约遗漏了权限、异常、边界或幂等规则；
- 方案文档中的路径、契约、数据模型或兼容方案无法成立；
- 真实影响面已经超出当前交付路径能承担的范围。

按归属回流：

- 整个模块目标或商业前提变得不成立，或者新的结论会推翻已经确认并读回的飞书详情文档：`module-planning`，先更新并读回飞书；
- 单个需求内出现需要用户确认的新范围、用户结果、权限、数据语义、兼容或发布决策：先回 `flow-router` 重评准备和路径；判为方案先行时由 `solution-generator` 确认并冻结，不因选择影响大就自动升级为模块规划；
- 上游决定未变化、只是本地规格遗漏：按影响返回 `solution-generator` 或 `acceptance-generator`；
- 文件、接口、数据模型或迁移方案与冻结方案文档不一致：返回 `solution-generator` 修订并重新冻结，不在实现中静默改变定稿；
- 准备程度、复杂度、风险或记录需要发生变化，导致原路径不再成立：返回 `flow-router` 只重评受影响维度；风险升高本身不自动等于方案先行。

不改变核心产品目标、验收、权限、数据安全或兼容承诺的实现偏差，可以继续推进，但必须记录原确认依据、实际实现、原因、影响和验证，并在 PR 中明确提出。会改变上述产品或风险边界的事项必须先回到对应上游：只有模块前提变化或已有飞书结论需要更新时才进入 `module-planning`；其他单需求问题由 `flow-router` 重新分流，并在方案先行时交 `solution-generator` 修订和冻结。任何情况都不要向来源 Issue 回写规格评论。

## 7. 实施报告

方案先行任务命中任一条件时，读取 [implementation_report.template.md](implementation_report.template.md) 并生成 `.specs/<KEY>/implementation_report.md`：

- 本次涉及数据库迁移、跨端契约、权限边界或部署配置变更；
- 实际实现明显偏离冻结方案文档；
- 改动跨多个模块、数据层或部署链路；
- 实施中出现需要在 PR 中说明的方案偏差；
- 有需要测试、审查或发布阶段重点关注的遗留风险。

报告是给接手开发者、审查者和产品负责人阅读的交付说明，不是机器检查表。使用完成时和具体事实，开头先说明用户或调用方现在获得了什么，再解释真实运行链路。按产品能力或运行职责组织正文，不按“代码、配置、数据、测试”机械分类；文件路径只作为实际落点证据。

报告至少讲清楚：

- 最终交付了什么，哪些明确边界没有改变；
- 真实触发入口、处理链路、校验位置、成功结果和失败副作用；
- 与冻结产物的实际差异、调整原因和影响；
- 真实执行的验证命令、覆盖行为、人工验收和未覆盖区域；
- 当前接受的限制，以及 PR 需要重点核实的具体事项。

不得使用“完成相关逻辑”“优化体验”“测试正常”等无法复核的表述，不保留空表或只有“无”的可选章节。没有方案差异时删除差异章节；如果差异实际改变核心产品目标、验收、权限、数据安全或兼容承诺，必须先回流并重新冻结上游产物，不能只在实施报告中说明。

报告不重复完整需求与技术方案。直接实现不创建 Spec 或实施报告文件；如果直接实现命中上述风险、跨端或偏差信号，把同样的关键信息写入本次交付摘要，并在创建 PR 时同步到 PR 正文。若这些内容需要跨会话保存，说明记录判断已经变化，应返回 `flow-router` 重新分流，而不是另建第二套报告。

## 8. 完成标准

进入下游前必须满足：

- 实现与确认范围一致；
- 没有静默规格偏差；
- 相关测试已新增或更新；
- 适用的人工端到端流程已有清单，未执行、失败和阻塞项没有被隐去；
- API、配置、数据、部署和文档已按影响同步；
- 涉及数据库时，ORM、Alembic revision、数据处理、升级降级测试和 schema 文档保持一致；
- 用户已有修改保持完整；
- 未执行的验证和已知风险已明确记录；
- 没有自动修改 Issue、创建提交或发布远端变更。
