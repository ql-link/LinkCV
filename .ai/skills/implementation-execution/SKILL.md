# 实施执行

## 1. 职责

把已确认的需求和设计落实为真实代码，并保持实现、测试和规格一致。本技能负责：

- 核实前置条件和当前工作区；
- 在确认范围内修改代码、配置、测试和必要文档；
- 处理实现中发现的规格偏差；
- 在高风险或有偏差时生成实施报告；
- 把完成的实现交给测试和质量审查。

本技能不负责创建分支、提交、推送、PR，除非用户另外明确要求进入 `branch-pr-workflow`。

## 2. 进入条件

### L1

- 已由 `flow-router` 明确判定为 L1；
- 不要求创建 `.specs`；
- 直接以用户请求和真实代码为实现边界。

### L2 与 L3

实现前运行：

```bash
npm run spec:source -- check <KEY> --gate implementation # 仅 Multica 来源
npm run spec -- check <KEY> implementation
```

L2 必须已有冻结的 `brief.md` 和 `acceptance.feature`；L3 还必须已有冻结的 `technical_design.md`。Multica 来源必须先完成当前阶段的权威需求核验。门禁失败时停止，按提示返回上游，不得绕过。实现期间若发现会改变范围或验收的规格缺口，返回 `brief-generator`；用户确认差异后先由其完成结构化评论回写或无差异对账，再重新冻结下游产物，不能只改本地 Spec。

## 3. 必读材料

1. `AGENTS.md`；
2. 用户当前请求和已经确认的范围；
3. L2/L3 的 `.specs/<KEY>/state.yaml` 和全部冻结产物；
4. 目标文件、直接调用方、共享类型和最近测试；
5. `git status --short`、当前任务相关差异和用户已有未提交修改；
6. 涉及 API、环境变量或部署时，读取前端 API 客户端、Vite 代理和部署配置；
7. 涉及迁移或存储时，读取现有模型、迁移、事务和回滚方式。

不要只读技术设计而跳过真实代码。技术设计中的路径和方法也需要在实施前再次核实。

## 4. 实施纪律

### 聚焦范围

- 只实现确认范围，不顺带重构无关模块；
- 复用现有模式前先确认它仍适用于当前模块；
- 新依赖必须说明必要性并更新对应锁文件；
- 不覆盖、不丢弃用户已有修改；重叠区域必须先理解再编辑。

### 契约同步

修改接口、共享类型、错误、环境变量或部署行为时，同步检查所有消费方。结构、语义或兼容影响不清楚时使用 `contract-guard`；同一个具体值散落多处时使用 `config-contract-sync`；最终实现改变长期项目事实时使用 `doc-maintenance-sync`。只选择真实命中的技能，不固定串行调用。修改数据库模型时先核实已确认物理 schema，再使用 `alembic-migration` 同步模型与 revision，处理旧数据、事务、兼容发布和回滚；不要手工改库绕过迁移链。

### Express 与 FastAPI 过渡

- 当前 `/api/health` 由 FastAPI 处理，其他 `/api` 请求暂时由 Express 处理；
- 未完成实现和回归前，不切换旧路由，不删除 `server`、SQLite 或旧部署拓扑；
- 如果任务要求切换路由，必须按冻结技术设计同步处理 API 客户端、Vite 代理、环境变量、部署和回滚。

### 安全与数据

- 鉴权、资源归属和文件访问必须在可信边界校验；
- 不把用户真实简历、联系方式、密钥或本地敏感路径写入代码和测试；
- 示例与测试数据使用虚构信息，默认姓名使用“张三”。

## 5. 实施步骤

1. 确认车道，运行适用的阶段门禁。
2. 检查工作区和相关差异，区分用户修改与本任务修改。
3. 读取目标代码和测试，列出最小可交付改动顺序。
4. 按依赖顺序实现，每完成一个可验证单元就运行最窄相关检查。
5. 补充或修改距离行为最近的有效测试；简单邻近测试可直接编写，需要独立测试设计、复杂 Mock 或分层调整时使用 `test-authoring`。测试必须能在实现错误时失败。
6. 检查 API、类型、权限、数据、配置、部署和长期文档是否需要同步，按契约影响选择对应专项技能。
7. 实现稳定后更新必要 `docs/`，不要把临时 Spec 内容复制成项目现状。
8. 完成后交给 `run-all-tests` 执行范围匹配的自动化验证；L2/L3 的最终命令由 `spec verify --run` 亲自执行并自动绑定当前代码快照。
9. 存在跨端、浏览器、上传下载、PDF 或视觉行为且自动化测试未覆盖时，转 `manual-acceptance` 生成并记录人工验收；不适用时直接跳过。
10. 全部必要验证通过后，状态进入 `quality_review`，交给 `code-review-and-quality` 做最终质量审查；无阻断问题时由 Agent 自动记录审查结论并进入 `release_ready`。

## 6. 规格缺口与回流

实施中发现以下情况时停止当前实现：

- 新行为不在需求范围内；
- 验收契约遗漏了权限、异常、边界或幂等规则；
- 技术设计中的路径、契约、迁移或兼容方案无法成立；
- 真实影响面达到更高车道。

按归属回流：

- 范围和用户结果变化：`brief-generator`；
- 可观察规则变化：`acceptance-generator`；
- 文件、接口、数据、迁移或发布方案变化：`technical-design`；
- 车道错误：`flow-router`。

修订后必须重新获得用户确认并重新冻结，再继续实现。不得只改代码让规格与实现分离。

## 7. 实施报告

命中任一条件时，读取 [implementation_report.template.md](implementation_report.template.md) 并生成 `.specs/<KEY>/implementation_report.md`：

- 当前任务为 L3；
- 实际实现明显偏离技术设计；
- 改动跨多个模块、数据层或部署链路；
- 实施中回写过需求简报、验收契约或技术设计；
- 有需要测试、审查或发布阶段重点关注的遗留风险。

报告只记录实际落点、差异、验证证据和遗留事项，不重复完整需求与技术方案。L1 和无明显偏差的 L2 通常不需要单独报告。

## 8. 完成标准

进入下游前必须满足：

- 实现与确认范围一致；
- 没有静默规格偏差；
- 相关测试已新增或更新；
- 适用的人工端到端流程已有清单，未执行、失败和阻塞项没有被隐去；
- API、配置、数据、部署和文档已按影响同步；
- 涉及数据库时，ORM、Alembic revision、数据处理、升级降级测试和 schema 文档保持一致；
- 用户已有修改保持完整；
- 未执行的验证和已知风险已明确记录；
- 没有自动修改 Issue、创建提交或发布远端变更。
