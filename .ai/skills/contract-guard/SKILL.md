# 契约影响分析

## 1. 唯一职责

判断一项改动是否复用、新增或破坏公共契约，并输出影响与同步清单。只做结构和语义分析：

- 契约的字段、必填性、错误、权限或状态语义是否变化；
- 调用方、数据、部署或旧链路是否需要配合；
- 哪些实现、迁移、配置和 `docs/` 文档必须同步；
- 是否需要兼容窗口和回滚安排。

本技能不逐处比较同一个端口、路径或变量值，不改代码和文档，也不代替方案文档的契约定稿或代码审查。

## 2. 使用前先确定是否需要

以下改动通常需要：

- HTTP 路由、请求/响应 schema、状态码或错误语义；
- 鉴权、资源归属、文件访问和敏感信息边界；
- 数据模型、迁移、唯一性、事务或旧数据处理；
- FastAPI 路由、Vite Proxy、客户端和部署入口的归属与兼容窗口；
- 对象存储路径、公私有访问或部署入口；
- 模块边界变化导致长期项目文档需要更新。

纯内部重构、格式调整、局部修复且外部行为不变时不要调用。

## 3. 必读材料

1. 用户确认的范围和适用的冻结规格；
2. 改动文件、直接调用方和现有测试；
3. [契约面与事实源映射](../../../docs/internals/contract-governance.md) 中命中的契约面；
4. 对应 `docs/` 长期文档；
5. `scripts/quality/doc-sync-rules.yaml` 中适用的机器同步规则。

只读取命中的契约面，不为一次局部 API 改动加载全部项目文档。

## 4. 分析步骤

1. 列出改动前后的可观察结构和语义，不把实现细节误判为公共契约。
2. 对每个契约面判定：`复用`、`兼容新增`、`破坏性变更` 或 `待确认`。
3. 沿真实调用关系检查生产者、消费者、持久化、配置、部署和旧链路。
4. 区分机器能验证的确定性关系与必须人工判断的语义关系。
5. 列出最小同步清单；不在本技能中执行修改。
6. 存在会改变范围、兼容或回滚方式的分歧时，返回 `module-planning` 更新飞书，再修订受影响的上游规格；不得自行决定或直接盘问。

## 5. 单向转交

- 同一物理值需要跨文件核对：转 `config-contract-sync`。
- 当前实现已经确定且需要更新长期知识：转 `doc-maintenance-sync`。
- 需要落实代码、配置或迁移：转 `implementation-execution`。
- 需要设计 MySQL 字段、约束或索引：转 `mysql-ddl-conventions`；需要编写或校验 Alembic revision：转 `alembic-migration`。
- 只需运行确定性检查：转 `run-all-tests`。

转交只列出原因和输入，不要求三个技能固定串行，也不回头重复其他技能已经完成的结论。

## 6. 输出

```text
契约结论：无变化 | 兼容新增 | 存在破坏性变化 | 待确认

| 契约面 | 变化 | 判定 | 受影响消费方 | 必须同步 |
| --- | --- | --- | --- | --- |

机器可验证：<对应门禁或无>
人工核实：<语义、兼容、权限或回滚问题>
下一站：<按需选择，不固定串行>
```

没有公共契约变化时明确说明，不为了使用本技能制造同步任务。
