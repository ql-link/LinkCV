# 分支、提交与 PR 工作流

## 1. 职责与授权边界

本技能负责把已经完成并验证的改动安全发布为独立分支和 PR，包括：

- 核对工作区、目标分支、来源分支、提交和完整差异；
- 从最新 `origin/master` 创建或确认业务需求分支；
- 创建或确认规范分支；
- 只暂存本任务文件并创建规范化中文提交；
- 推送当前独立分支；
- 创建以 `dev` 为目标分支的中文 PR；
- `dev` PR 创建成功且存在来源 Issue 时，发布一条交付评论，链接 PR 并说明实际结果、重要差异和遗留项。

只有用户明确要求相应 Git 操作时才能执行。创建分支不自动授权提交；提交不自动授权推送；推送不自动授权创建 PR，除非用户一次请求明确包含完整流程。创建 `dev` PR 不自动授权合并。用户授权创建 `dev` PR 时，若存在可写的来源 Issue，默认同时授权发布上述一条交付评论；用户明确要求不评论 Issue 时跳过。该授权不包含修改 Issue 正文、状态、负责人、标签或其他字段。

本技能是 LinkCV 中分支命名、共享分支保护、中文提交、PR 门槛和 base/head 选择的唯一项目策略来源。环境中同时存在通用 GitHub 发布 Skill 时，可以复用其底层 `git`/`gh` 操作能力，但不得采用与本技能冲突的命名、授权或发布规则，也不得绕过本技能的检查。

来源 Issue 是可选的追踪信息，不是创建分支、提交、推送或 PR 的许可证。存在 Issue 时读取并准确关联；不存在时按用户请求和已确认范围继续，不得要求先补建 Issue，也不得因此改变质量与授权门槛。

禁止自动修改任何来源 Issue 的正文或状态、自动合并 PR 或删除远端分支。任务过程中不发送进度评论、规格同步评论或逐次测试评论，避免把 Issue 变成第二份实施记录。

## 2. 共享分支保护

不得直接向远端 `dev`、`main`、`master` 推送、合并、强推或改写历史。

新的业务需求分支必须遵循：

1. `git fetch origin --prune` 后从最新 `origin/master` 创建独立业务分支；
2. 实现、验证并推送业务分支；
3. 创建 `业务分支 -> dev` PR，交由用户或远端审核合并。

不得从 `dev` 或其他业务分支创建新的业务需求分支；业务需求 PR 的默认目标为 `dev`。

只有用户明确说出允许绕过 PR 并直接推送的共享分支名称时，才获得例外授权；执行前仍需复述目标和影响范围。

## 3. 发布前检查

执行任何写操作前检查：

```bash
git branch --show-current
git status --short --branch
git diff --stat
git diff
git log --oneline --decorate -n 10
```

创建 PR 前还要检查：

```bash
git fetch origin --prune
git show-ref --verify refs/remotes/origin/master
git show-ref --verify refs/remotes/origin/dev
git merge-base origin/master HEAD
git log --oneline origin/master..HEAD
git diff --stat origin/master...HEAD
git diff origin/master...HEAD
git diff --stat origin/dev...HEAD
git diff origin/dev...HEAD
```

必须确认：

- 当前仓库和远端正确；
- 当前业务分支确实从 `origin/master` 创建，没有混入 `dev` 或其他业务分支历史；
- 当前 PR 目标分支为 `dev`；
- 提交范围只包含当前任务；
- 用户原有或其他任务修改没有混入；
- 没有密钥、真实用户数据、构建产物或本地临时文件；
- 任务范围验证已通过；当前可提交内容已有覆盖全部 PR 差异的领域检查证据。同一会话、同一文件内容的结果可以复用；证据缺失、代码或环境变化时只补跑失效范围。

发现无关修改时，只暂存当前任务文件；无法安全拆分时停止并说明重叠范围。

## 4. 分支命名

根据是否存在来源 Issue 使用以下格式：

```text
# 有来源 Issue
<type>/<issue-key-lower>-<slug>

# 无来源 Issue
<type>/<slug>
```

允许的类型：

| 类型 | 用途 |
| --- | --- |
| `feat` | 新增用户能力或业务行为 |
| `fix` | 修复明确缺陷 |
| `refactor` | 不改变外部行为的结构重构 |
| `docs` | 仅文档和规则说明 |
| `test` | 仅测试 |
| `chore` | 日常维护 |
| `ci` | 持续集成配置 |
| `build` | 构建系统或依赖管理 |
| `perf` | 性能改进 |
| `hotfix` | 需要快速交付的生产修复 |

命名规则：

- 禁止使用 `codex/`；
- Issue 可选；存在时标识使用小写，例如 `lcv-21`，不存在时不得为了满足分支格式而补建 Issue；
- 主题段使用简短的小写英文、数字和连字符；
- 根据主要交付目的选择类型，不根据修改文件数量选择；
- 避免 `update`、`changes`、`misc` 等没有信息量的名称。

示例：

```text
feat/lcv-21-ai-workflow
refactor/lcv-34-api-client
docs/deployment-guide
fix/login-redirect
```

如果当前已经位于符合规则、从 `origin/master` 创建且范围正确的独立业务分支，不重复创建分支。新建时先获取远端并核对工作区安全，再执行 `git switch -c <branch> origin/master`；不通过重置或覆盖处理用户修改。当前分支不是从 `master` 创建时停止发布并报告，不用 rebase、cherry-pick 或重建分支擅自改写用户现有工作。

## 5. 提交范围

1. 用 `git status` 和文件差异列出本次应提交文件。
2. 使用显式路径暂存，不默认使用可能纳入无关文件的宽泛操作。
3. 暂存后检查：

```bash
git diff --cached --stat
git diff --cached
```

4. 每个提交只表达一个逻辑变更；工作流规则、业务实现和无关格式化不要混成一个提交。
5. 提交前再次确认验证结果和暂存内容。

## 6. 提交信息格式

标题使用：

```text
<type>(<scope>): <中文简述>
```

`scope` 可以省略，建议使用稳定模块名，例如 `ai`、`web`、`backend`、`resume`、`deploy`。

标题要求：

- 类型与分支主要目的一致；
- 中文简述使用动词开头，明确说明完成了什么；
- 不加句号；
- 禁止“update”“修改代码”“修复问题”等缺少对象和结果的标题。

正文用于解释为什么改、核心改动、验证和关联事项：

```text
feat(ai): 建立仓库级 AI 交付工作流

原因：统一项目规则和方案任务的执行依据。
核心变更：新增项目技能、方案文档和质量检查入口。
验证：<实际任务范围命令>
关联：LCV-21（没有来源 Issue 时写“无”）
```

如果存在破坏性变更，在正文末尾追加：

```text
BREAKING CHANGE: <中文说明、受影响方和迁移方式>
```

## 7. 创建 PR 前的门槛

1. 最终差异没有未解决的阻断问题；只有后端、混合任务或用户明确要求专项审查时才要求已有 `code-review-and-quality` 结论；
2. 与任务改动范围匹配的验证已经通过，未执行项和未覆盖区域已经明确；
3. PR 按当前差异组合领域检查：纯 Web 使用 `npm run check:web`；纯后端使用后端测试和构建；其他单一领域使用 `run-all-tests` 定义的对应命令。跨领域只组合受影响命令，只有差异实际覆盖全仓、无法可靠缩小范围或用户明确要求时运行 `npm run check`；
4. 适用检查因依赖、权限、网络、服务或其他环境问题无法完成时停止创建 PR，明确报告阻塞、已完成检查和未验证范围；
5. 设计任务已经对照实际存在的适用依据检查一致性：后端和混合任务读取 `solution.md`，前端存在已确认 Figma 或用户视觉材料时使用 `frontend-visual-check`；改动包含需要真实运行才能确认的交互或状态时使用 `frontend-browser-check`。没有相应问题或依据时不补做；
6. 只有任务确实存在自动化无法覆盖的跨端、上传下载、PDF 或高风险流程时才要求独立人工验收记录；
7. API、类型、配置、迁移、部署和文档已经同步；
8. 业务分支的 `origin/master...HEAD` 功能差异，以及目标分支 `origin/dev...HEAD` 的完整 PR 差异均已检查；
9. 搭建工作流本身检查真实差异并运行 `npm run check:ai`；同时修改应用代码或运行契约时再叠加对应范围检查。

同一会话中，任务范围验证后代码、配置、依赖、生成物输入和测试替身均未变化，且已有命令完整覆盖当前 PR 差异时，可以复用结果；提交本身不使结果失效。跨会话、环境变化、证据不完整或无法确认快照一致时，按受影响领域重新运行。

门槛失败时停止，回到对应测试、审查或实施技能，不强行发布。

本地范围检查是创建 PR 前的门槛，不替代共享 CI。PR 创建后，共享 CI 仍运行其配置的检查；远端结果尚未产生时只能报告“待运行”，不能把本地通过描述成共享 CI 已通过。

## 8. PR 标题与正文

PR 标题使用与提交相同的格式，标题和正文全部使用中文：

```text
<type>(<scope>): <中文简述>
```

创建 PR 前必须完整读取并使用 [pull_request.template.md](pull_request.template.md)。替换全部占位内容，保留模板章节及顺序，不在 Skill 正文复制或维护第二份 PR 正文模板。

“概述”固定放在 PR 正文开头，用 2–3 句话直接说明修改对象、明确或新增的内容、是否影响现有功能以及验证是否通过。使用具体名词和动作，避免背景铺垫以及“完善、优化、提升”等空泛表达；只有存在必须提前说明的风险时才补充风险。背景、实现细节和常规风险放在后续章节，不在概述重复。

“重点核实”必须列出 2–5 个与实际风险直接相关的检查项，明确需要核实的契约、权限、数据、兼容、部署或产品行为。不能只写“请审查”或复制核心改动。

“来源差异与取舍”只写会影响理解、验收或后续维护的差异：后端和混合方案任务对照当前 `solution.md`，前端对照已确认原型或 Figma，混合任务同时核对且以 `solution.md` 的契约为准；直接实现任务对照当前确认范围。没有重要差异时明确写“无重大差异”。

“验证结果”记录当前 PR 前实际运行的范围检查、前端页面浏览器与视觉检查、适用的人工验收和共享 CI 状态，不把其中一项冒充另一项。

“关联事项”固定放在 PR 正文最后，避免外部链接打断背景、改动、验证和风险的阅读顺序。来源 Issue 是可选项；存在时统一记录平台、准确 key 和链接，需要补充其他关联对象时另起一行。不能假设来源一定是 Multica 或 GitHub，也不能因为是否存在 Issue 或平台不同改变 PR 门槛。没有对应对象时明确写“无”，不要省略整个章节。

## 9. 推送与创建 PR

1. 只向 `origin` 推送当前独立分支并设置上游，不推送共享分支；
2. PR 固定使用 `base=dev`、`head=当前业务分支`，命令必须显式传入 `--base dev --head <当前业务分支>`；
3. 创建前检查远端存在 `dev`、来源分支已推送，并确认没有相同 `base/head` 的打开 PR；
4. PR 创建后复核远端返回的实际 `base/head`，确认无误后再报告链接、提交、测试结果和未纳入提交的本地修改；PR 正文不重复展示 GitHub 页面已有的分支信息；
5. 存在来源 Issue 且用户未明确关闭评论时，在 `dev` PR 创建成功后读取 [issue_delivery_comment.template.md](issue_delivery_comment.template.md)，基于该 PR 和差异发布一条交付评论；
6. PR 交给用户审核，不自动合并。

## 10. 来源 Issue 的一次性交付评论

Issue 评论是跟踪收尾，不是新的规格或第二份 PR 正文：

- 只评论主要来源 Issue；其他关联 Issue 只有用户明确要求时才评论，避免批量通知；
- 同一业务需求默认只在 `dev` PR 创建后发布一条交付评论，不发送阶段进度、每次提交或每轮测试结果；
- 评论固定使用所属模板，保留 PR 链接、实际交付、重要来源差异、验证摘要和未完成项；详细文件和审查信息继续留在 PR；
- 后续代码变化优先更新 PR 正文。若原 Issue 评论已经实质错误，优先编辑原评论；平台不支持编辑时，取得用户确认后再补一条更正，不静默追加重复评论；
- 评论成功不代表修改 Issue 状态。除非用户另行明确授权，不关闭 Issue、不改正文、不改负责人或标签；
- 评论工具、权限或平台不可用时，保留已经成功创建的 PR，报告评论未发布，并把可直接发送的评论正文交给用户；不得宣称已经同步，也不得重试到产生重复评论。

如果实际变化已经使原目标或核心验收失效，不用交付评论掩盖任务重启：停止把新旧目标混入同一 PR，按单向交付规则建立新的 Issue 或 Spec，并在旧 Issue 留下指向后续任务的说明。

## 11. 完成报告

最终至少说明：

- 分支名；
- 业务分支基线为 `master` 的核对结果；
- 提交哈希和规范化中文提交信息；
- 推送是否成功；
- Dev PR 的目标分支、来源分支、标题和链接；
- 来源 Issue 交付评论的链接或未发布原因；
- 实际运行的验证命令与结果；
- 共享 CI 的真实状态；
- 是否仍有未提交或未纳入本 PR 的本地修改；
- 需要用户重点核实的事项。
