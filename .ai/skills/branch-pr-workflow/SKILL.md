# 分支、提交与 PR 工作流

## 1. 职责与授权边界

本技能负责把已经完成并验证的改动安全发布为独立分支和 PR，包括：

- 核对工作区、目标分支、来源分支、提交和完整差异；
- 创建或确认规范分支；
- 只暂存本任务文件并创建规范化中文提交；
- 推送当前独立分支；
- 创建以 `dev` 为目标分支的中文 PR。

只有用户明确要求相应 Git 操作时才能执行。创建分支不自动授权提交；提交不自动授权推送；推送不自动授权创建 PR，除非用户一次请求明确包含完整流程。

本技能是 LinkCV 中分支命名、共享分支保护、中文提交、PR 门槛和 base/head 选择的唯一项目策略来源。环境中同时存在通用 GitHub 发布 Skill 时，可以复用其底层 `git`/`gh` 操作能力，但不得采用与本技能冲突的命名、授权或发布规则，也不得绕过本技能的检查。

禁止自动修改任何来源 Issue 的状态、自动合并 PR 或删除远端分支。

## 2. 共享分支保护

不得直接向远端 `dev`、`main`、`master` 推送、合并、强推或改写历史。

用户说“合入 dev”“推到 dev”“并入 dev”时，默认解释为：

1. 推送独立功能分支；
2. 创建以 `dev` 为目标分支的 PR；
3. 交由用户或远端审核后合并。

只有用户明确说出允许绕过 PR 并直接推送的共享分支名称时，才获得例外授权；执行前仍需复述目标和影响范围。

## 3. 发布前检查

执行任何写操作前检查：

```bash
git branch --show-current
git status --short --branch
git diff --stat
git diff
git log --oneline --decorate -n 10
```

创建 PR 前还要检查：

```bash
git fetch origin --prune
git log --oneline origin/dev..HEAD
git diff --stat origin/dev...HEAD
git diff origin/dev...HEAD
```

必须确认：

- 当前仓库和远端正确；
- 目标分支为预期的 `dev`，来源分支为独立分支；
- 提交范围只包含当前任务；
- 用户原有或其他任务修改没有混入；
- 没有密钥、真实用户数据、构建产物或本地临时文件；
- 相关验证已通过。

发现无关修改时，只暂存当前任务文件；无法安全拆分时停止并说明重叠范围。

## 4. 分支命名

格式固定为：

```text
<type>/<issue-key-lower>-<slug>
```

允许的类型：

| 类型 | 用途 |
| --- | --- |
| `feat` | 新增用户能力或业务行为 |
| `fix` | 修复明确缺陷 |
| `refactor` | 不改变外部行为的结构重构 |
| `docs` | 仅文档和规则说明 |
| `test` | 仅测试 |
| `chore` | 日常维护 |
| `ci` | 持续集成配置 |
| `build` | 构建系统或依赖管理 |
| `perf` | 性能改进 |
| `hotfix` | 需要快速交付的生产修复 |

命名规则：

- 禁止使用 `codex/`；
- Issue 标识使用小写，例如 `lcv-21`；
- 主题段使用简短的小写英文、数字和连字符；
- 根据主要交付目的选择类型，不根据修改文件数量选择；
- 避免 `update`、`changes`、`misc` 等没有信息量的名称。

示例：

```text
feat/lcv-21-ai-workflow
refactor/lcv-34-api-client
docs/lcv-18-deployment-guide
```

如果当前已经位于符合规则且范围正确的独立分支，不重复创建分支。需要从 `origin/dev` 新建时，先确认基线和工作区安全，不通过重置或覆盖来处理用户修改。

## 5. 提交范围

1. 用 `git status` 和文件差异列出本次应提交文件。
2. 使用显式路径暂存，不默认使用可能纳入无关文件的宽泛操作。
3. 暂存后检查：

```bash
git diff --cached --stat
git diff --cached
```

4. 每个提交只表达一个逻辑变更；工作流规则、业务实现和无关格式化不要混成一个提交。
5. 提交前再次确认验证结果和暂存内容。

## 6. 提交信息格式

标题使用：

```text
<type>(<scope>): <中文简述>
```

`scope` 可以省略，建议使用稳定模块名，例如 `ai`、`web`、`backend`、`resume`、`deploy`。

标题要求：

- 类型与分支主要目的一致；
- 中文简述使用动词开头，明确说明完成了什么；
- 不加句号；
- 禁止“update”“修改代码”“修复问题”等缺少对象和结果的标题。

正文用于解释为什么改、核心改动、验证和关联事项：

```text
feat(ai): 建立仓库级 AI 交付工作流

原因：统一项目规则和复杂任务的阶段门禁。
核心变更：新增项目技能、本地规格状态脚本和质量检查入口。
验证：npm run check
关联：LCV-21
```

如果存在破坏性变更，在正文末尾追加：

```text
BREAKING CHANGE: <中文说明、受影响方和迁移方式>
```

## 7. 创建 PR 前的门槛

1. `code-review-and-quality` 没有未解决的阻断问题；
2. 与改动范围匹配的验证已通过，默认包含 `npm run check`；
3. 方案先行任务的 `state.yaml` 已进入 `release_ready`，自动验证快照和质量审查快照都与当前可提交内容一致；
4. 方案先行任务已运行 `npm run spec -- check <KEY> release_ready`；验证后代码又变化时停止收口，实施阶段的必要偏差已经在 PR 中说明；
5. 适用的人工端到端验收已完成，PR 验证结果摘要了通过、失败、阻塞和未覆盖项；
6. API、类型、配置、迁移、部署和文档已经同步；
7. 目标分支、来源分支、提交列表和 `origin/dev...HEAD` 完整差异已检查；
8. 首次建立工作流、无法使用自身阶段门禁时，在 PR 中明确写明“工作流自举例外”和替代验证证据。

门槛失败时停止，回到对应测试、审查或实施技能，不强行发布。

## 8. PR 标题与正文

PR 标题使用与提交相同的格式，标题和正文全部使用中文：

```text
<type>(<scope>): <中文简述>
```

创建 PR 前必须完整读取并使用 [pull_request.template.md](pull_request.template.md)。替换全部占位内容，保留模板章节及顺序，不在 Skill 正文复制或维护第二份 PR 正文模板。

“概述”固定放在 PR 正文开头，用 2–3 句话直接说明修改对象、明确或新增的内容、是否影响现有功能以及验证是否通过。使用具体名词和动作，避免背景铺垫以及“完善、优化、提升”等空泛表达；只有存在必须提前说明的风险时才补充风险。背景、实现细节和常规风险放在后续章节，不在概述重复。

“重点核实”必须列出 2–5 个与实际风险直接相关的检查项，明确需要核实的契约、权限、数据、兼容、部署或产品行为。不能只写“请审查”或复制核心改动。

“关联事项”固定放在 PR 正文最后，避免外部链接打断背景、改动、验证和风险的阅读顺序。来源 Issue 统一记录平台、准确 key 和链接；需要补充其他关联对象时另起一行。不能假设来源一定是 Multica 或 GitHub，也不能因为平台不同改变 PR 门槛。没有对应对象时明确写“无”，不要省略整个章节。

## 9. 推送与创建 PR

1. 只向 `origin` 推送当前独立分支并设置上游，不推送共享分支；
2. 用户未明确指定其他目标时，远端 PR 固定使用 `base=dev`、`head=当前独立分支`；
3. 创建命令必须显式传入 `--base dev --head <当前独立分支>`，不得依赖仓库默认分支或 GitHub 的自动选择；用户明确指定其他目标分支时，用已核实的实际目标替换 `dev`；
4. 创建前检查远端存在目标分支、来源分支已推送，并确认没有相同 `base/head` 的打开 PR，避免目标错误或重复创建；
5. PR 创建后复核远端返回的实际 `base/head`，确认无误后再报告链接、提交、测试结果和未纳入提交的本地修改；PR 正文不重复展示 GitHub 页面已有的分支信息；
6. 把 PR 交给用户审核，不自动合并。

## 10. 完成报告

最终至少说明：

- 分支名；
- 提交哈希和规范化中文提交信息；
- 推送是否成功；
- PR 的目标分支、来源分支、标题和链接；
- 实际运行的验证命令与结果；
- 是否仍有未提交或未纳入本 PR 的本地修改；
- 需要用户重点核实的事项。
