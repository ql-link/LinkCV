# 需求简报生成与收敛

## 1. 职责

把尚未稳定的需求整理成 `.specs/<KEY>/brief.md`，让另一位开发者能够明确理解：

- 为什么做、交付什么；
- 哪些内容属于本次范围，哪些明确不做；
- 当前行为和问题是什么；
- 哪些模块、契约和数据概念会受影响；
- 有哪些具体风险、依赖和阻塞决策。

需求简报回答“做什么、边界在哪里、影响什么”。类名、方法签名、物理表结构、迁移步骤和详细算法属于技术设计，不在本阶段展开。

## 2. 使用前提与边界

使用前必须满足：

- `flow-router` 已判定为 L2 或 L3；
- 有稳定的 Issue key，例如 `LCV-21`；
- 用户请求或 Issue 内容足以识别核心目标。

以下情况停止或转交：

- 车道尚未确定：转 `flow-router`；
- 已有冻结需求简报，用户要求生成验收场景：转 `acceptance-generator`；
- 用户要求直接写代码，但 L2/L3 前置产物未冻结：说明缺失阶段，不跳过；
- 用户只要求改项目技能或模板：直接维护技能，不创建业务规格。

Multica 是长期需求主记录。可以读取和引用，但没有用户明确授权时，不修改 Issue、评论、自定义属性或状态。

## 3. 自动初始化与机器门禁

不要要求用户手动初始化。读取请求来源并检查 `.specs/<KEY>/state.yaml`：

- 不存在时，由本技能自动执行初始化；
- 已存在时，不得覆盖，先读取状态并核对车道和来源；
- 现有车道与 `flow-router` 结论冲突时停止，说明冲突和影响，不擅自改写状态。

根据真实来源选择命令：

```bash
# 来自 Multica Issue
npm run spec -- init <KEY> --lane L2|L3 --source-system multica \
  --issue-id <ISSUE_UUID> --workspace-id <WORKSPACE_UUID>
npm run spec:source -- capture <KEY> --gate brief

# 来自 GitHub Issue
npm run spec -- init <KEY> --lane L2|L3 --source-system github --issue-id <ISSUE_ID>

# 来自用户对话或其他没有外部 Issue 的请求
npm run spec -- init <KEY> --lane L2|L3 --source-system manual
```

命令中的 `L2|L3` 表示根据分级结果选择一个值，不能原样传入。初始化只创建目录和 `state.yaml`，不会生成需求简报、修改外部 Issue 或执行 Git 操作。

状态已存在时运行：

```bash
npm run spec -- status <KEY>
npm run spec:source -- check <KEY> --gate brief # 仅 Multica 来源
npm run spec -- check <KEY> brief
```

Multica 查询只读，不修改 Issue。首次 `capture` 保存标题与描述的需求指纹；状态、负责人、标签等元数据变化不会让 Brief 失效。评论线程属于待判读上下文，不进入机器指纹；评论中的正式范围变化必须先整理到 Issue 描述。`check` 发现标题或描述变化时会把 Brief、Acceptance、Technical Design 和验证状态退回未冻结，并返回非零退出码。此时必须重新读取 Issue、在原文件修订 Brief，再运行：

```bash
npm run spec:source -- accept <KEY> --gate brief
```

`accept` 只表示本地开始以当前 Issue 正文作为新基线，不代表范围已经获得用户确认；仍须完成本技能的分歧扫描和用户确认后才能冻结。Multica CLI 不可用、认证失效、无权访问或网络失败时，准确报告“需求未核验”并停止，不得把缓存状态当成最新需求继续推进。

需求简报固定输出到：

```text
.specs/<KEY>/brief.md
```

`.specs/<KEY>/` 是本地阶段快照，不是长期需求库。已有文件时先读取并在原章节修订，不创建第二份简报，也不追加流水账式“修改记录”。

## 4. 必读材料

1. `AGENTS.md`；
2. 用户原始请求和已确认的补充信息；
3. Multica Issue 内容（如果任务来自 Multica）；
4. `.specs/<KEY>/state.yaml`；
5. 与需求直接相关的入口文件、相邻模块、类型和测试；
6. [brief.template.md](brief.template.md)。

代码探索以支撑范围判断为限，但必须基于真实文件。不要凭技术栈常识编造现有模块、接口或能力。

## 5. 内容要求

### 背景与目标

- 描述当前问题和触发来源；
- 给出本次要达到的结果；
- 使用可验证的业务结果，避免“完善体验”“优化相关逻辑”等空泛表述。

### 用户价值

- 明确受影响用户和使用场景；
- 说明用户最终能够做什么，或原有问题如何被消除。

### 范围与非目标

- 范围写清本次必须交付的能力和行为；
- 非目标主动排除容易顺带扩张的事项；
- 对兼容旧行为、数据处理和迁移边界给出明确结论或列为阻塞决策。

### 当前行为与问题

- 描述真实代码当前如何工作；
- 区分已核实事实、合理推断和待确认信息；
- 不把期望方案写成当前能力。

### 受影响模块与概念契约

每个模块至少说明：

- 真实位置和当前职责；
- 本次新增、复用或修改的责任；
- 会影响的调用方、数据或运行配置；
- 是否触碰 API、共享类型、错误语义、权限、持久化或部署契约。

涉及接口或数据变化时，在需求层明确字段的业务含义、必填性和归属；精确类型、索引、约束、迁移顺序和代码落点留给 L3 技术设计。

### 风险、依赖和阻塞决策

- 风险必须包含触发条件、影响和应对方向；
- 依赖必须指出依赖对象和无法满足时的后果；
- 只有会实质改变范围、行为、数据或兼容策略的问题才列为阻塞决策。

## 6. L2 与 L3 的差异

L2 不单独生成技术设计，因此需求简报必须补充足以直接实现的最小技术边界，例如复用入口、状态流向和受影响契约，但仍不写方法级方案。

L3 只在需求简报中确定范围、概念契约和关键约束，具体文件、方法、物理数据结构、迁移、发布与回滚由 `technical-design` 承接。

如果 L2 写到必须设计跨模块调用、迁移或回滚顺序，说明分级可能过低，应返回 `flow-router` 升级为 L3。

## 7. 分歧发现与回流闭环

盘问完成不代表初稿不会暴露新分歧。把需求简报初稿视为一致性探针，每次生成或修订后都重新检查：

- 目标、范围与非目标是否互相冲突；
- 主流程和异常流程是否隐含不同产品选择；
- 模块影响判断是否要求新增未确认的用户行为；
- 兼容、权限、历史数据或失败策略是否存在两个以上合理答案；
- 风险应对是否实际改变了交付范围。

发现问题后按以下方式处理：

1. 能从代码、Issue 或文档核实的事实，由本技能继续探索，不询问用户。
2. 不影响外部行为和风险的局部实现取舍，采用有证据的推荐方案并在适当章节说明。
3. 会改变范围、行为、契约、数据、兼容或发布策略的选择，写入“阻塞性决策（仅草稿阶段）”，不得把推荐答案写成已确认结论。
4. 使用 `decision-grilling` 按依赖顺序一次询问一个决策，并附推荐答案与影响分析。
5. 用户确认后，把结论写回正文对应章节，删除该阻塞项，再扫描整份简报及依赖它的结论。
6. 如果回写产生新的分歧，继续同一闭环；不以“初稿已经写完”为理由跳过。

阻塞性决策区是草稿期工作区，不是冻结产物的一部分。冻结前必须删除整节，而不是保留“无”。

## 8. 工作步骤

1. 从请求和 Issue 中提取目标、范围、非目标和显式验收要求。
2. 检查本地状态；缺失时按真实来源自动初始化并捕获 Multica 需求基线，存在时核对车道、来源和需求指纹。
3. 读取真实代码，核对当前行为、影响模块和可复用能力。
4. 读取模板并生成或修订 `.specs/<KEY>/brief.md`，替换所有占位内容。
5. 把初稿作为一致性探针，扫描事实缺口、正文冲突和真实决策分支。
6. 事实缺口继续探索；真实决策进入 `decision-grilling`，每轮只处理一个最上游问题。
7. 用户确认后重新读取当前文件，把结论写回对应章节，删除已解决阻塞项并重新扫描全文。
8. 持续迭代，直到阻塞性决策区为空且正文没有依赖冲突。
9. 只有用户明确确认范围后才能删除阻塞性决策整节并冻结：

```bash
npm run spec -- freeze <KEY> brief
```

未经用户确认，不得自行冻结。

## 9. 冻结质量标准

冻结前必须满足：

- 目标、用户价值、范围和非目标互不冲突；
- 当前行为有仓库证据；
- 受影响模块均有真实路径或明确标注待确认；
- API、权限、数据、迁移、部署等高风险影响没有被隐藏；
- 风险是具体场景，不是泛泛提醒；
- 没有仍会改变范围或行为的阻塞问题，草稿期“阻塞性决策”整节已经删除；
- 文件中不包含占位符、过程记录或未经确认的实现承诺。

冻结后转 `acceptance-generator`，不要直接进入实现。
