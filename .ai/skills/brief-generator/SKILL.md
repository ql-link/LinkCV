# 需求简报生成与收敛

## 1. 职责

把尚未稳定的需求整理成 `.specs/<KEY>/brief.md`，让另一位开发者能够明确理解：

- 为什么做、交付什么；
- 哪些内容属于本次范围，哪些明确不做；
- 当前行为和问题是什么；
- 主流程如何运行、关键异常在哪里发生；
- 哪些模块、契约和数据概念会受影响；
- 有哪些具体风险、依赖和阻塞决策。

需求简报回答“做什么、边界在哪里、影响什么”。类名、方法签名、物理表结构、迁移步骤和详细算法属于技术设计，不在本阶段展开。

## 2. 使用前提与边界

使用前必须满足：

- `flow-router` 已判定为 L2 或 L3；
- 有稳定的 Issue key，例如 `LCV-21`；
- 已能读取来源 Issue 正文，且其中至少可以识别核心目标；
- 已有相关飞书详情文档时能够一并读取。

以下情况停止或转交：

- 车道尚未确定：转 `flow-router`；
- 已有冻结需求简报，用户要求生成验收场景：转 `acceptance-generator`；
- 用户要求直接写代码，但 L2/L3 前置产物未冻结：说明缺失阶段，不跳过；
- 用户只要求改项目技能或模板：直接维护技能，不创建业务规格。

来源 Issue 是需求简报的初始产品输入，必须读取完整正文，而不是只读取标识、摘要或链接。Issue 可以来自 Multica、Linear、GitHub 或其他系统，平台不改变输入权重或后续流程。关联的飞书周开发文档、详情文档和用户明确确认的补充内容负责展开或修正范围、验收和实现前决策；已有详情文档时必须和 Issue 一起读取。

Issue 正文与详情文档不一致时，先根据明确的替代说明和时间顺序核实哪份是当前有效结论；无法确认时使用 `decision-grilling`，不得静默选择。普通评论不自动进入需求输入，除非用户明确指定某条评论为有效补充。本技能不创建、修改或评论任何外部 Issue。

## 3. 自动初始化与机器门禁

不要要求用户手动初始化。读取请求来源并检查 `.specs/<KEY>/state.yaml`：

- 不存在时，由本技能自动执行初始化；
- 已存在时，不得覆盖，先读取状态并核对车道和来源；
- 现有车道与 `flow-router` 结论冲突时停止，说明冲突和影响，不擅自改写状态。

初始化时只记录来源 Issue 的完整链接或稳定引用，不声明平台：

```bash
npm run spec -- init <KEY> --lane L2|L3 --source-issue <ISSUE_URL_OR_REF>

# 明确关闭常规认领流程、自举或本地维护等没有外部 Issue 的例外
npm run spec -- init <KEY> --lane L2|L3
```

命令中的 `L2|L3` 表示根据分级结果选择一个值，不能原样传入。初始化只创建目录和 `state.yaml`，不会生成需求简报、修改外部 Issue 或执行 Git 操作。

状态已存在时运行：

```bash
npm run spec -- status <KEY>
npm run spec -- check <KEY> brief
```

`source_issue` 原样保存 Issue 的完整链接或稳定引用，便于状态恢复和 PR 关联。它不拆分平台、workspace 或内部 ID，也不参与冻结门禁；需要读取时根据引用本身选择可用工具。Issue 正文仍是人工或 Agent 必须读取的业务输入；本地状态工具不访问外部 Issue，不捕获需求指纹，不比较评论链，也不向任何 Issue 系统回写需求变化。

开始编写 Brief 前，先读取来源 Issue，再读取用户指定、Issue 关联或当前周对应的飞书材料。若 Issue、飞书材料与用户本轮补充冲突，使用 `decision-grilling` 收敛结论；没有明确写入授权时，把高影响结论交给用户更新飞书。进入编码前必须解决并记录会改变范围、验收、权限、数据或兼容策略的问题。Issue 本身已经足够明确且不存在这类决策时，不强制为了形式另写一份飞书详情文档。

需求简报固定输出到：

```text
.specs/<KEY>/brief.md
```

`.specs/<KEY>/` 是本地阶段快照，不是长期需求库。已有文件时先读取并在原章节修订，不创建第二份简报，也不追加流水账式“修改记录”。

## 4. 必读材料

1. `AGENTS.md`；
2. 用户原始请求和已确认的补充信息；
3. 来源 Issue 的标题、完整正文、附件或关联文档链接；
4. 用户指定或 Issue 关联的飞书周开发文档、模块说明和已经确认的补充材料；
5. `.specs/<KEY>/state.yaml`；
6. 与需求直接相关的入口文件、相邻模块、类型和测试；
7. [brief.template.md](brief.template.md)。

代码探索以支撑范围判断为限，但必须基于真实文件。不要凭技术栈常识编造现有模块、接口或能力。

## 5. 内容要求

### 需求摘要

- 用“做什么、为什么做、用户价值、交付结果、本次不做”建立完整边界；
- 描述问题来源、受影响用户和最终可获得的结果；
- 使用可验证的业务结果，避免“完善体验”“优化相关逻辑”等空泛表述。

### 当前行为与问题

- 描述真实代码当前如何工作；
- 区分已核实事实、合理推断和待确认信息；
- 不把期望方案写成当前能力。

### 业务流程

- 使用 Mermaid 画出主链路和关键异常分支，节点使用业务语言，不写类名或方法名；
- 对每个关键节点说明触发者与动作、系统责任与依赖、状态与数据流向、用户或下游可见结果；
- 异常分支必须明确触发条件、系统行为、可见反馈以及失败后的状态或数据结果；
- 流程必须覆盖需求摘要中的交付结果，不能只描述当前行为或模块清单。

### 涉及模块与影响面

每个模块至少说明：

- 真实位置和当前职责；
- 本次承担的业务责任，以及复用还是新增能力；
- 会影响的调用方、状态、数据或运行配置；
- 是否触碰 API、共享类型、错误语义、权限、持久化或部署契约；
- 关键实体、字段业务含义、必填性、归属与关系；
- 已核实的可行性、实现风险和仍需确认的事实。

涉及接口、表或其他对外数据契约变化时，在需求层用字段级清单明确新增、修改或删除的对象、字段、业务含义、必填性、归属和大致类型；精确长度、索引、约束、默认值、迁移顺序和代码落点留给 L3 技术设计。

### 风险、依赖和阻塞决策

- 风险和依赖必须包含触发条件、影响和应对方向；
- 依赖必须指出依赖对象和无法满足时的后果；
- 只有会实质改变范围、行为、数据或兼容策略的问题才列为阻塞决策。

## 6. L2 与 L3 的差异

L2 不单独生成技术设计，因此在“涉及模块与影响面”末尾保留“L2 最小实现思路”，补充足以直接实现的最小技术边界，例如复用入口、新增链路、状态流向和受影响契约，但仍不写方法级方案。

L3 删除模板中的“L2 最小实现思路”，只在需求简报中确定范围、概念契约和关键约束，具体文件、方法、物理数据结构、迁移、发布与回滚由 `technical-design` 承接。

如果 L2 写到必须设计跨模块调用、迁移或回滚顺序，说明分级可能过低，应返回 `flow-router` 升级为 L3。

## 7. 分歧发现与回流闭环

盘问完成不代表初稿不会暴露新分歧。把需求简报初稿视为一致性探针，每次生成或修订后都重新检查：

- 目标、范围与非目标是否互相冲突；
- 主流程和异常流程是否隐含不同产品选择；
- 模块影响判断是否要求新增未确认的用户行为；
- 兼容、权限、历史数据或失败策略是否存在两个以上合理答案；
- 风险应对是否实际改变了交付范围。

发现问题后按以下方式处理：

1. 能从代码、Issue 或文档核实的事实，由本技能继续探索，不询问用户。
2. 不影响外部行为和风险的局部实现取舍，采用有证据的推荐方案并在适当章节说明。
3. 会改变范围、行为、契约、数据、兼容或发布策略的选择，写入“阻塞性决策（仅草稿阶段）”，不得把推荐答案写成已确认结论。
4. 使用 `decision-grilling` 按依赖顺序一次询问一个决策，并附推荐答案与影响分析。
5. 用户确认后，把结论写回正文对应章节，删除该阻塞项，再扫描整份简报及依赖它的结论。
6. 如果回写产生新的分歧，继续同一闭环；不以“初稿已经写完”为理由跳过。

阻塞性决策区是草稿期工作区，不是冻结产物的一部分。冻结前必须删除整节，而不是保留“无”。

## 8. 工作步骤

1. 从来源 Issue 提取初始目标、范围、现状和显式验收要求，再用关联飞书详情文档和用户已确认补充展开或修正。
2. 检查本地状态；缺失时按真实来源自动初始化，存在时核对车道和记录来源。
3. 读取真实代码，核对当前行为、影响模块和可复用能力。
4. 读取模板并生成或修订 `.specs/<KEY>/brief.md`，替换所有占位内容；主流程、异常分支和模块影响不能省略为一张概括表。
5. 把初稿作为一致性探针，扫描事实缺口、正文冲突和真实决策分支。
6. 事实缺口继续探索；真实决策进入 `decision-grilling`，每轮只处理一个最上游问题。
7. 用户确认后重新读取当前文件，把结论写回对应章节，删除已解决阻塞项并重新扫描全文。
8. 持续迭代，直到阻塞性决策区为空且正文没有依赖冲突。
9. 向用户展示最终范围和仍需确认的差异；用户确认后删除阻塞性决策整节并冻结：

```bash
npm run spec -- freeze <KEY> brief
```

未经用户确认，不得自行冻结。

## 9. 冻结质量标准

冻结前必须满足：

- 目标、用户价值、范围和非目标互不冲突；
- 当前行为有仓库证据；
- 主流程可以从触发运行到可见结果，关键异常包含触发条件、反馈及失败后的状态或数据结果；
- 受影响模块均有真实路径或明确标注待确认；
- 每个模块均说明职责、复用或新增、公共契约、关键数据和可行性；L2 已给出最小实现思路，L3 已删除该模板节；
- API、权限、数据、迁移、部署等高风险影响没有被隐藏；
- 风险是具体场景，不是泛泛提醒；
- 没有仍会改变范围或行为的阻塞问题，草稿期“阻塞性决策”整节已经删除；
- Brief 与当前有效的来源 Issue、飞书详情材料及用户补充一致；
- 文件中不包含占位符、过程记录或未经确认的实现承诺。

冻结后转 `acceptance-generator`，不要直接进入实现。
