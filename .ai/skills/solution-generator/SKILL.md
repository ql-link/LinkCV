# 方案文档生成与收敛

## 1. 定位

`.specs/<KEY>/solution.md` 写给开发者看，帮助他在动手前回答四个问题：

1. **要做什么**：需求是什么，拆成哪几块，每块完成后能看到什么；
2. **难在哪**：哪些点容易做错、代价高或依赖外部条件；
3. **还有什么没定**：哪些问题必须由人来拍板，推荐答案是什么；
4. **哪些硬约束不能错**：数据库表结构、接口与数据结构、中间件和外部依赖。

具体实现方式（文件拆分、函数设计、代码写法）由实施 Agent 依据已确认的需求和真实代码决定，方案只固定影响范围、粗粒度顺序和验证标准，不替 Agent 逐行设计。

本阶段不写业务代码，不执行 DDL 或迁移，不修改任何外部 Issue。

## 2. 使用前提与边界

使用前必须满足：

- `flow-router` 已选定方案先行，或用户明确指定方案先行；
- 任务属于纯后端或前后端混合领域；纯前端任务由当前 Codex 直接处理；
- 有稳定的任务标识：有 Issue 时用其 key，例如 `LCV-21`；没有时用 `LOCAL-YYYYMMDD-<SHORT-SLUG>`，同日重名追加 `-2`、`-3`；
- 当前请求、可读取的 Issue 或用户明确指定的外部材料中，至少有一项能识别核心目标。没有 Issue 不阻止创建方案，也不算例外。

以下情况停止或转交：

- 后端交付路径或范围尚未确定：转 `flow-router` 重评；
- 任务经核实是纯前端：停止本技能，由当前 Codex 直接开发；
- 整个模块的目标或商业前提尚未成形：暂停方案，先在对话中确认目标；
- 已有确认的方案，用户要求生成验收场景：转 `acceptance-generator`；
- 用户要求直接写代码，但仍有会改变实现的待确认问题：指出具体问题，不用阶段名称阻塞；
- 用户只要求维护项目 Skill 或模板：直接维护，不创建业务 Spec。

用户指定的外部材料只作为初始输入。存在 Issue 时读取完整正文、附件和明确关联材料；普通评论除非用户指定，不进入需求输入。本技能不创建、修改或评论外部 Issue，也不创建或回写其他外部材料。

## 3. 文档位置与真相源

方案固定写入 `.specs/<KEY>/solution.md`，需要时直接创建目录，不创建额外机器状态文件，也不运行阶段管理命令。已有文件时在原文档中收敛，不另建“最终版”“修订版”，不追加对话流水账。

`solution.md` 是方案任务的唯一中心文档。Acceptance、人工验收、实施报告和混合任务的视觉材料都是从属附件。方案确认后，它取代 Issue 和其他初始材料成为实施依据。AI 根据当前请求、Spec 文档、视觉产物、Git 差异、真实代码和实际测试判断下一步，不维护阶段、确认状态、哈希或历史验证标记。

当前结论与 Issue 或其他初始材料冲突时不静默选择：能由用户最新明确指令消解的，把已确认的取舍和被替代的来源结论写入当前 `solution.md`；仍有多个合理答案时，列入“待确认问题”。冲突在当前方案内收敛，不回写初始材料。

## 4. 必读材料

1. `AGENTS.md`；
2. 用户原始请求和已确认补充；存在来源 Issue 时读取其完整内容；
3. 需求直接相关的入口、调用方、共享类型、配置和测试；
4. 涉及持久化时的 ORM 模型、`apps/backend/migrations/` 迁移链和 `docs/internals/backend.md`；
5. 涉及中间件时的现有接入代码、环境变量和 `deploy/` 配置；
6. [solution.template.md](solution.template.md)。

写路径、表名、接口或配置前必须亲自核实真实仓库，不把来源材料中的旧路径当作当前事实。

## 5. 文档结构

模板分三部分，篇幅和用心程度按“读者是谁”分配：

| 部分 | 读者 | 要求 |
| --- | --- | --- |
| 第一部分 · 需求理解 | 开发者 | 核心。必须完整、好读，用业务语言 |
| 第二部分 · 设计约束 | 开发者与实施 Agent | 只写改错代价高的硬约束，命中就必须写全 |
| 第三部分 · 实施与验证 | 实施 Agent | 轻量。范围、粗粒度顺序和验证映射 |

始终保留：需求概述、需求拆分、业务流程与规则、影响范围、代码实施计划、验证与验收。

按事实保留，未命中整节删除，不写“无”“不涉及”或空表：

- **难点与风险**：存在真正难、容易做错或代价高的点时保留；方案先行的任务通常都会命中；
- **待确认问题**：仍有需要人拍板的问题时保留，全部确认后删除；
- **已确认决策**：发生过值得追溯的真实选择时保留；
- **数据库变更**：只要读写持久数据就必须保留，不得为了缩短文档省略；
- **接口与数据结构**：新增或修改 HTTP 接口、共享类型、事件、消息体、JSON 字段结构、文件格式或配置键时必须保留；
- **中间件与外部依赖**：用到 Redis、RabbitMQ、MinIO、LLM、第三方服务或新依赖包时必须保留；
- **状态机**：涉及生命周期、状态决定权限或操作、并发、重试或恢复时必须保留。

章节号只帮助阅读。下游按“可观察结果”“关键规则”“代码实施计划”“验证与验收”等名称读取，不依赖固定章节编号；删除章节后无需重新编号。

主线是“可观察结果（R）→ 关键规则（BR）→ 代码实施计划 → 验证与验收（V）”：每个 R 都要被至少一个实施步骤和一项验证承接，决定行为的 BR 也一样。

## 6. 可读性规则

方案读不懂就没有价值。写作时遵守：

- **先结论后细节**：每节第一句话就是结论，读者只读每节首句也能掌握大意；
- **短段落和分条列表优先**：一段不超过四句；表格不超过 4 列，信息更多时改成分条列表；
- **一件事只说一次**：流程图画过的不在正文逐节点复述；规则写在“关键规则”里，其他地方用 `BR` 编号引用；
- **第一部分只用业务语言**：不出现类名、方法名、表名、字段名、框架名和文件路径；
- **第二、三部分必须落地**：使用真实表名、接口和路径，不写“在服务层处理”“补充相关逻辑”“按需测试”这类无法施工或验证的话；
- **只解释自创说法**：幂等、乐观锁、索引等通用术语直接使用；
- **不留模板痕迹**：删除模板说明、占位符和未命中的章节；
- **图按内容选型**：单主体分支用 `flowchart`，多方往返用 `sequenceDiagram`，迁移发布画变更顺序，状态复杂时另加 `stateDiagram-v2`。同一条链路只画一次。

## 7. 第一部分 · 需求理解

### 需求概述

用两到四段短文讲清：谁在什么场景遇到什么问题，本次交付什么，交付后整件事如何运转。“现在的情况”只写已核实事实，计划不写成现状。业务动机会影响范围或取舍时才写“为什么现在做”。

### 需求拆分

- 按可以独立理解、独立验收或有先后依赖的业务能力拆成子需求；单一能力不硬拆；
- 每个子需求下列出可观察结果，使用全局稳定编号 `R1`、`R2`……，每条是完成后可以观察或断言的事实；
- “本次不做”写明排除原因，避免实现者当作遗漏补回。

### 业务流程与规则

- 一张主流程图从触发走到成功结果，包含决定行为的拒绝或失败分支；
- 关键规则使用稳定编号 `BR1`、`BR2`，每条写清条件、系统行为、可见结果和失败后的数据状态；
- 图和规则共同覆盖全部 R。

### 难点与风险

这是开发者最需要的信息之一，必须基于对真实代码和需求的调查，不写泛泛的“注意性能”“注意安全”。每条写清：

- 难在哪：并发重复、数据量、旧数据形态、外部服务不稳定、跨端兼容、成本等具体原因；
- 不处理会怎样：可观察的后果；
- 应对思路：方向性结论；细节留给实施 Agent。

严格风险（权限越界、数据丢失、凭据泄露、不可逆操作）必须出现在这里，并在验证与验收中有对应项。

### 待确认问题

先分类，再决定是否提问：

1. 能从代码、请求、Issue、外部材料或配置核实的事实：自己调查，不提问；
2. 不影响外部行为、成本、风险或长期边界的实现细节：交给实施 Agent，不提问；
3. 会改变范围、业务规则、数据归属、权限、状态、兼容、失败表现、架构、外部依赖、运行成本或不可逆结果的选择：写入待确认问题并向用户确认；
4. 整个模块目标或商业前提尚未成形：暂停方案，先确认目标。

每个问题写清背景、选项、推荐答案和不同选择的影响。按依赖顺序一次确认一个，先问会影响后续选择的问题；不重复问来源材料已经回答的内容。用户说“你定”时采用推荐答案并记录来源。

确认后立即更新正文，把结论移到“已确认决策”，写明结论、放弃的方案、理由与代价和确认来源。未确认的推荐答案不得写成用户决定。单个问题内部有多层依赖时，可以调用 `decision-grilling`：返回 `confirmed` 后写入，`blocked` 时暂停，`replan` 时在本方案内重建受影响的决定。

## 8. 第二部分 · 设计约束

本部分只写实现前必须定死、改错代价高的内容。普通代码组织、命名和函数设计不写。

### 数据库变更

只要读写持久数据就必须保留。

- 只读写现有数据、不改结构：写清数据对象的读写方、归属、权限和必须保持的不变量，以及模型定义现状；
- 新增或修改表、字段、约束、索引、枚举，或回填、迁移、改变归属和清理规则：完整写出数据结构变更、存量数据与迁移和规约自检。

结构设计必须使用 `mysql-ddl-conventions`，并遵守其中整理的阿里巴巴 MySQL 规约：

- **新表和新增字段全量遵守**：单数表名、`id bigint unsigned` 自增主键、`create_time`/`update_time`、`is_xxx tinyint unsigned` 布尔字段、`decimal` 小数、`pk_`/`uk_`/`idx_` 命名、表和字段注释、不建数据库外键与级联；
- **存量表不追溯**：修改已有表时沿用该表已有的命名和关联方式（例如复数表名、`created_at`、已有外键），在“规约自检”中列为存量例外；
- **偏离需确认**：新结构确有理由偏离规约时，写入待确认问题，由用户确认后在规约自检中记录原因。

分别记录模型定义、仓库 migration head 和目标环境 current revision；无法核实目标环境时写“尚未核实”。

数据结构变更的写法：

- 按表组织，每张表先用一句话说明用途、一行代表什么和预计数据量级；
- 字段用 SQL 风格结构片段，每个字段写类型、可空性、默认值和注释；约束与索引放在单独的片段里，每个索引用行尾注释写明支撑的真实查询；
- 结构片段只供评审，不是可执行 DDL，不生成完整的 `CREATE TABLE`、`ALTER TABLE`、`CREATE INDEX`、`INSERT`、`UPDATE`、`DELETE` 语句；
- 写清关联关系由哪一层保证存在性、归属校验和删除清理；
- 只有存在回填、清理、兼容窗口、发布顺序、数据回退或不可逆点时才保留“存量数据与迁移”，用正常文本描述处理范围、回填规则、异常数据结果和幂等要求。

本阶段只定稿结构和数据处理规则，不创建 revision、不改模型、不执行迁移。

### 接口与数据结构

- HTTP 契约必须同时写方法和路径，并写清权限与归属校验位置、关键请求和响应字段、错误码与触发条件、消费方和兼容方式；
- JSON 字段、消息体、缓存值、共享类型或文件格式用 TypeScript 或 JSON 示例写清结构，并说明版本与兼容方式；
- 数据库中的整数 ID 在 HTTP 和 TypeScript 中的表示沿用项目现有约定，以 `docs/internals/backend.md` 为准。

### 中间件与外部依赖

用到中间件、外部服务或新依赖时，逐项写清：

- **用途**：为什么需要它；
- **新增或变化**：Redis key 格式与 TTL、队列与消息体、对象存储路径、LLM 场景、第三方接口、依赖包名与版本；
- **配置**：新增环境变量和默认值，以及需要同步的 Vite、Compose 和部署入口；
- **失败与降级**：超时、重试、幂等、取消和用户可见结果；
- **安全**：发送哪些数据、如何脱敏、密钥位置和日志禁区。

只复用已有能力且不新增 key、队列、路径或配置时，一句话带过。新依赖必须说明必要性并在实施时更新对应 lockfile。

### 状态机

涉及生命周期、状态决定权限或操作、并发、重试或恢复时必须保留。写清状态对象与真值来源、初始状态、终态、合法与非法流转；每条流转写触发者、重复或并发处理、副作用与可见结果；以及超时、重试和恢复规则。单个布尔判断不制造状态机。

## 9. 第三部分 · 实施与验证

### 影响范围

列出已核实会被改动的模块和直接消费方，每项一行并给出真实路径。用于让开发者和 Agent 判断改动面，不逐函数展开。

### 代码实施计划

- 按依赖顺序写粗粒度步骤，每步是一个可以独立完成和验证的单元，例如“迁移与 ORM”“服务与接口”“前端 API client 同步”；
- 每步引用承接的 `R` 或 `BR`，并写可验证的完成判据；
- 不逐文件、逐函数设计，具体做法由实施 Agent 依据真实代码决定；
- 跨模块、多阶段、迁移或生产发布的顺序约束写在这里，或在“存量数据与迁移”中写清；
- 真正影响正确性的事务、并发、幂等或性能约束写在“实现要点”，并引用步骤编号。

### 验证与验收

- 每个 `R` 和决定行为的 `BR` 都映射到单元、集成、迁移或人工验证；
- 自动化项给出真实测试文件或命令以及关键断言；人工项写清环境、动作和可观察结果；
- 直接施工路径把本节作为唯一验证契约；契约验收路径由 `acceptance-generator` 基于同一批 R 和 BR 展开场景；
- 不把 Gherkin、组件测试或接口测试称为已完成的自动化端到端验收。

## 10. 提交确认前自检

1. 第一部分单独交给不看代码的人，能复述目标、拆分、难点和待确认问题；
2. 每个 `R` 都在流程或关键规则中有来源，并被至少一个实施步骤和一项验证承接；
3. 难点基于真实调查，严格风险都有验证项；
4. 持久数据、接口、中间件和状态机的适用性已逐项判断，命中的写全；
5. 新增或修改的表结构已按 `mysql-ddl-conventions` 逐条自检，例外已列明原因；
6. 表名、字段、接口、路径和配置已与真实仓库核对；
7. 没有残留会改变代码行为的未确认选项；与初始材料不同的结论已写清替代关系；
8. 没有模板说明、占位符、空章节和超过 4 列的宽表格。

缺一项就继续调查、提问或补写。

## 11. 确认方式与后续路径

确认的重点是第一部分和第二部分。第三部分属于实施 Agent 的工作计划，向用户展示但不逐条要求确认。

- 没有待确认问题的短方案，整份展示一次并确认一次；
- 有待确认问题时按依赖顺序逐个确认，再整体确认一次，不把已确认的决定换个环节再问；
- 用户已经明确选择 `直接施工` 或 `契约验收` 时，确认方案时直接复用该选择；未选择时把推荐路径并入最后一次确认：

| 路径 | 含义 | 适用信号 |
| --- | --- | --- |
| `契约验收` | 方案 → 验收契约 → 实现 | 多角色或状态交互；权限和失败规则需要独立确认；人工场景需要在实现前固定 |
| `直接施工` | 方案 → 实现 | 规则能由短清单完整表达，验证映射已经落到具体测试或人工步骤 |

选择直接施工时不生成 `acceptance.feature`。实现中发现规则需要独立契约时，说明原因并取得确认，再把后续路径改为契约验收。

方案确认后，契约验收路径转 `acceptance-generator`；直接施工路径返回 `flow-router`，由当前 Codex 使用 `implementation-execution` 按“代码实施计划”和“验证与验收”继续实施。实施中发现需要改变已确认的需求、数据结构、接口或中间件约束时，先更新本方案并重新确认受影响内容；普通实现细节不回写方案。

## 12. 工作步骤
