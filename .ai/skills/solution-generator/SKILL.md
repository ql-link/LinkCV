# 方案文档生成与收敛

## 1. 定位

`.specs/<KEY>/solution.md` 是整个交付流程中**唯一需要用户确认的文档**，确认完就能直接施工。它同时回答两件事：

- **要做什么**：完整、清晰、用户能读懂的业务逻辑；
- **实现步骤**：架构、选型、数据、接口、文件落点和实现路径。

由此产生三条不可让步的原则：

1. **需求分析是核心。** 结合用户提供的信息反复补全，直到需求完整且可执行；不完整就不能进入实现。
2. **必须让用户读得懂。** 方案文档第一部分（1–5 节）是与用户对齐的地方，用白话写业务，不掺技术符号。
3. **技术方案必须能开工。** 不写"采用分层架构"这类空话，要写清新增哪些文件、每个文件干什么、每个模块从入口到结果怎么走。

本阶段不写业务代码，不执行 DDL 或迁移，不修改任何外部 Issue。

## 2. 使用前提与边界

使用前必须满足：

- `flow-router` 已判为方案先行；
- 有稳定的 Issue key，例如 `LCV-21`；
- 能读取来源 Issue 正文，且其中至少可以识别核心目标。

以下情况停止或转交：

- 交付路径尚未确定：转 `flow-router`；
- 整个模块的目标、边界或商业前提本身尚未成形，不是若干可回答的具体问题：转 `module-planning`；
- 已有冻结方案文档，用户要求生成验收场景：转 `acceptance-generator`；
- 用户要求直接写代码，但方案文档尚未冻结：说明缺失阶段，不跳过；
- 用户只要求改项目技能或模板：直接维护技能，不创建业务规格。

来源 Issue 是初始产品输入，必须读取完整正文，而不是只读取标识、摘要或链接。Issue 可以来自 Multica、Linear、GitHub 或其他系统，平台不改变输入权重或后续流程。已有经 `module-planning` 确认的飞书模块详情文档时必须一并读取，它对范围、验收和实现前决策的结论优先于本技能的推断。

普通评论不自动进入需求输入，除非用户明确指定某条评论为有效补充。本技能不创建、修改或评论任何外部 Issue，也不写入飞书。

## 3. 自动初始化与机器门禁

不要要求用户手动初始化。读取请求来源并检查 `.specs/<KEY>/state.yaml`：

- 不存在时，由本技能自动执行初始化；
- 已存在时，不得覆盖，先读取状态并核对当前阶段和来源；
- 现有状态与 `flow-router` 结论冲突时停止，说明冲突和影响，不擅自改写状态。

初始化时只记录来源 Issue 的完整链接或稳定引用，不声明平台：

```bash
npm run spec -- init <KEY> --source-issue <ISSUE_URL_OR_REF>

# 明确关闭常规认领流程、自举或本地维护等没有外部 Issue 的例外
npm run spec -- init <KEY>
```

初始化只创建目录和 `state.yaml`，不会生成方案文档、修改外部 Issue 或执行 Git 操作。后续路径不在初始化时决定，而在方案文档冻结时选定。

状态已存在时运行：

```bash
npm run spec -- status <KEY>
npm run spec -- check <KEY> solution
```

`source_issue` 原样保存 Issue 的完整链接或稳定引用，便于状态恢复和 PR 关联。它不拆分平台、workspace 或内部 ID，也不参与冻结门禁。本地状态工具不访问外部 Issue，不捕获需求指纹，不比较评论链，也不向任何 Issue 系统回写需求变化。

方案文档固定输出到：

```text
.specs/<KEY>/solution.md
```

`.specs/<KEY>/` 是本地阶段快照，不是长期需求库。已有文件时先读取并在原章节修订，不创建第二份文档，也不追加流水账式"修改记录"。

## 4. 必读材料

1. `AGENTS.md`；
2. 用户原始请求和已确认的补充信息；
3. 来源 Issue 的标题、完整正文、附件或关联文档链接；
4. 用户指定或 Issue 关联的飞书周开发文档、模块说明；
5. `.specs/<KEY>/state.yaml`；
6. 与需求直接相关的入口文件、相邻模块、类型和测试；
7. 需要确定文件落点时，目标目录的现有组织方式和命名约定；
8. 涉及数据表变化时的现有 SQLAlchemy 模型、`apps/backend` 迁移目录和当前 revision 链；
9. [solution.template.md](solution.template.md)。

第二部分的每一处落点都必须基于真实文件。不要凭技术栈常识编造现有模块、接口、表、字段或目录结构。

## 5. 表达约束（可检查）

这些是硬规则，不是文风建议。每次生成或修订后逐条自检。

**第一部分禁止技术符号。** 文档 1–5 节中不得出现类名、方法名、表名、字段名、框架名和文件路径。要提某个东西时用业务名称。判断方法：把第一部分单独拿给不看代码的人读，他应该能完整复述业务逻辑。

**不解释通用术语，只解释自创说法。** 幂等、乐观锁、索引、外键这类行业通用词直接用，不要解释，也不要为它们单独列表。只有本项目自创的概念、内部代号或容易被误解的说法，才在首次出现处用一个括号或半句话就地说清，例如"顶替（生成新链接时把旧链接同时置为已撤销）"。就地解释一次即可，后文不再重复。

**选型必须有对比。** 文档 6.4 节每个决策点都要填"放弃的方案"和"代价与理由"，只写选定方案视为未完成。没有对比，用户就无法参与技术决策，这条规则的目的就是保住用户的决策权。

**落点必须可验证。** 文档第 9 节不许写"在服务层处理""由业务逻辑负责"这类没有落点的句子。每条实现路径都要能对着仓库核对。

**按内容选图，不为画而画。** 图只在能比文字说得更清楚时才画，一处只画一张：

- **流程图**（`flowchart`）：主体只有一个，重点是判断分支和走向。用于文档 4.1 业务主流程。
- **时序图**（`sequenceDiagram`）：参与者有多个，来回调用的先后顺序本身就是重点。用于文档 6.3 关键数据流；4.1 的主流程如果本质是多方往返而不是分支判断，也可以改用时序图代替流程图。9.3 的实现路径在调用链跨三个以上文件且存在回调或重试时可以补一张，否则用文字串起来就够。
- **状态图**（`stateDiagram-v2`）：用于文档 5.1 状态机，不用其他图代替。
- **实体关系图**（`erDiagram`）：用于文档 7.1，只画本次涉及的表及其直接关联，不画整库。

同一条链路不要既画流程图又画时序图。图中节点在第一部分用业务语言命名，在第二部分可以用真实的参与者或组件名。图后必须有一段文字补充图里看不出的信息（校验、转换、被刻意不返回的字段、失败中断点），不能只留一张图。

**分段展示。** 向用户展示时先只给第一部分请其确认业务，确认后再给第二部分请其确认技术取舍。不要一次性甩出全部 13 节。

## 6. 主动提问与确认

本阶段拥有提问权，业务规则和技术取舍都在这里定稿。发现不确定的地方不要猜测，也不要把两个选项都写进文档等下游澄清。

先分类，再决定是否提问：

1. **能从代码、Issue、飞书文档或配置核实的事实**：自己去查，不占用用户注意力。
2. **不影响外部行为、也不影响成本与风险的实现细节**：自己定稿，在文档 6.4 节说明理由即可。
3. **会改变范围、业务规则、数据归属、权限、状态流转、兼容策略或失败表现的选择**：必须提问。
4. **会改变架构走向、技术栈、外部依赖、运行成本、性能上限或后续扩展空间的技术选型**：必须提问。
5. **整个模块的目标或商业前提尚未成形**：不逐个提问，转 `module-planning`。

提问方式：

- 一次只处理一个问题，按依赖顺序排列，先问会影响后续问题的那个；
- 每个问题都给出已核实事实、可选方案、**推荐答案**和选择不同答案的具体影响；
- 技术选型问题必须翻译成用户能判断的语言，说清各方案在**体验、成本、风险、后续扩展**上的差别，而不是罗列技术特性；
- 不问用户已经在 Issue 或飞书文档中回答过的问题；
- 用户明确表示"你定"时，采用推荐答案并在决策记录中标注确认来源。

确认后立即把结论写入文档第 12 节"已确认决策"，并标注确认来源；尚未获得用户确认的推荐答案不得写成"用户确认"。同步修订受影响章节。文档正文只保留结论，不保留问答过程和未决选项。

需要用户在多个方案间做结构性取舍、且单个问题本身包含多层依赖时，可以调用 `decision-grilling` 处理该单个选择，返回 `confirmed` 后由本技能写入结论；`blocked` 时暂停并说明阻塞，`replan` 时转 `module-planning`。

上游已有经确认并读回的飞书详情文档，而本阶段的提问结论与之冲突时，停止并说明差异，交 `module-planning` 更新飞书后再修订本文档；不要在本地静默覆盖已确认的上游结论。

## 7. 需求部分的要求

### 需求描述

文档第 1 节要让人只读这一节就知道本次要做什么，其余章节是它的展开，不是它的补充说明。

- 1.1 需求正文必须是成段叙述，不是短语堆砌。至少覆盖：谁在什么场景下遇到什么问题、本次要做出什么、做出来之后整件事怎么运转、哪些明确不做；
- 需求正文中出现的每项能力，后面都要能在模块分解中找到承接；反过来，模块分解中不得出现需求正文没有提到的能力；
- 1.2 的"不做会怎样"要写具体损失，不写"影响体验""不够完善"这类无法判断的说法；
- 1.3 使用场景按真实使用者拆行，同一个人在不同时机使用算不同场景；
- 1.4 交付结果每条都必须可观察或可验证，是后续验收契约的直接来源；
- 1.5 本次不做要逐条说明排除理由，避免下游把它当成遗漏又补回来。

来源 Issue 正文不完整时，先按本文第 6 节提问补齐，再写需求正文；不要用模糊表述掩盖没问清楚的部分。

### 模块分解

先拆模块，再写流程和技术方案。拆分按业务能力，不按代码目录或技术分层；"前端改动""后端改动"不是模块。

判断一个候选模块是否成立：

- 能用一句业务语言说清它负责什么、不负责什么；
- 有独立的完成信号，可以单独描述验收；
- 与其他模块的关系是依赖，不是互相等待；
- 拆得再细就只剩实现细节，拆得再粗就无法单独验收。

处理依赖：按拓扑排序给出交付顺序。出现循环依赖时说明拆分理由或合并成一个模块。若某个模块可以独立上线且自身足以支撑一份独立方案文档，给出单独立项建议，由用户决定是否另起一个 KEY；本技能不自行拆分成多个 Spec 目录。

模块编号是贯穿全文的锚点：业务流程节点、接口清单、文件职责、实现方案和实施顺序都要引用它，使用户可以从"这个功能做什么"一路追到"它落在哪个文件"。

### 状态机

只要存在持久化的状态字段、审批或提交链路、任务生命周期、多步骤流程，或者同一对象在不同阶段有不同可用操作，文档第 5 节就必须完整填写。

- 穷举初始状态、终态和每一条流转；
- 每条流转写明起始状态、事件或条件、目标状态、触发者、副作用；
- 并发或重复触发的处理方式写明，不默认幂等；
- 明确列出不允许的流转，以及被拒绝时的系统行为和用户看到什么；
- 状态取值与文档 7.2 的枚举字段一一对应，不出现文档内两套命名；
- 流程图中出现的每个结果都能在状态机中找到落点，状态机中每个可达状态都能在流程或异常分支中找到来源。

## 8. 方案部分的要求

### 整体架构

文档第 6 节要让用户看懂系统怎么搭，也要让实现者知道边界在哪：

- 架构图节点用业务或角色语言命名，技术名词放括号里补充；
- 分层职责必须同时写"承担什么"和"不承担什么"，只写前者无法约束实现；
- 关键数据流至少覆盖一次完整的成功操作，说明数据从哪进、经过谁、落到哪；参与者之间存在往返调用时用时序图表达，并在图后补充图里看不出的校验、转换和中断点；
- 选型取舍表按本文第 5 节规则填写，四列都用白话。

架构走向本身就是需要用户拍板的事项，按本文第 6 节第 4 类提问，不要自行决定后只在文档里通知。

### 数据模型

只要新增或修改表、字段、约束、索引、枚举取值，或改变已有数据的写入、归属、清理规则，文档第 7 节就必须完整填写：

- 先读取现有 SQLAlchemy 模型和迁移链，确认真实起点，不凭表名猜测现状；
- 读取 `mysql-ddl-conventions` 并按其规范确定类型、主键策略、时间字段、字符集、约束和索引命名；
- 每个字段写明类型、可空、默认值和业务含义，不留"待定"；
- 索引必须对应文档中出现的具体查询，写不出查询就不要加索引；
- 外键、唯一约束和枚举取值全部穷举，删除与更新行为写明；
- 给出定稿 DDL，作为实现阶段的直接输入；
- 明确存量数据处理、兼容窗口和回滚时新数据的归宿；
- 7.4 的真值源核对必须分别说明模型定义、仓库当前迁移版本和目标环境当前迁移版本，不得合并成一句，也不得把仓库里存在某个版本描述成目标环境已经迁移到该版本；目标环境无法当场核实时明确写"尚未核实"；
- 7.4 的不可逆点必须写明哪一步执行之后数据就回不来了。定稿 DDL 只说明表长什么样，不说明上线时先加列还是先改代码，而这个顺序错了就是数据丢失，因此上线与回滚的先后关系在文档第 11 节实施顺序中按步骤给出。

本阶段只写文档。不执行 SQL，不创建 revision，不修改模型文件。字段语义、数据归属或旧数据处理仍有分歧时按本文第 6 节提问，不在 DDL 中替用户决定。

### 文件结构与实现方案

文档第 9 节是实现者的直接施工依据，也是这份文档区别于纯需求文档的地方：

- 目录树标注每个路径是新增、修改还是删除，并写一句话目的；
- 文件职责表写清修改后职责、所属模块和影响方，影响方漏写会导致调用方漏改；
- 每个模块一小节实现方案，只有"实现步骤"和"验证方式"两项必填，其余按需出现；
- **"实现步骤"按执行顺序编号，一步一句话**：先说这一步做什么，再用括号给出落点文件。不要把整条调用链挤成一段用箭头连起来的长句 —— 那种写法信息密度高但读不下去，实现者要反复回看才能理清顺序；
- 一步只做一件事。一步里塞进三个文件说明这步该拆成三步；
- "验证方式"指明落在哪个测试文件，这是后续 `test-authoring` 和 `acceptance-generator` 的接口，不能省；
- "实现要点"只写真正需要提醒实现者的点（算法、并发、幂等、事务、性能、易踩的坑），**没有就整节删掉**，不要写"无特殊处理"占位；
- "复用能力"必须先核实现有能力确实存在且适用，**没有可复用的就整节删掉**；
- 需要提醒的点或可复用能力超过一处时才用列表，只有一条就写成一句话。

新增文件的位置和命名必须先读目标目录的现有组织方式，跟随既有约定，不引入第二套结构。

### 外部服务与安全边界

涉及外部服务、密钥或敏感数据处理时，文档第 10 节必须完整填写。LinkCV 的默认底线是：不把真实简历正文、联系方式、密钥或供应商完整响应写入日志和测试；不为提高成功率无限重试；不静默切换会改变数据处理承诺的供应商。

## 9. 填写深度与后续路径

### 填写深度由内容触发

没有外部等级决定哪一节写多细。判断依据只有一条：**这一节实际涉及什么。**

- 文档第 9 节永远必填。没有文件落点的方案不算方案。
- 涉及新增或修改表、字段、约束、索引、枚举取值，或改变已有数据的写入与归属：文档第 7 节必须完整到定稿 DDL，不接受"实现时再定"。
- 涉及跨端共享契约、鉴权与权限边界、对象存储、部署配置或兼容窗口：相关章节必须写到可执行，包括兼容窗口、回滚顺序和不可逆点。
- 确实不涉及的章节，明确写"不涉及"并说明依据，不留空节，也不写"待定"。

写着写着发现必须设计跨模块迁移顺序、兼容窗口或回滚编排，说明影响面比分流时判断的更大：停下来告知用户，确认是否需要拆分或另起 KEY，不要在同一份文档里静默扩张范围。

### 冻结时选定后续路径

方案文档冻结时必须和用户一起确定下一步走哪条，这是本阶段最后一个提问，按本文第 6 节的方式问：一次一个，给推荐答案和影响。

| 路径 | 含义 | 适用信号 |
| --- | --- | --- |
| `契约验收` | 方案 → 验收契约 → 实现 | 存在状态机、权限边界或明确的失败路径；跨端契约需要两端对同一批规则达成一致；多个模块共享同一组业务规则；需要人工端到端验收且场景必须提前写清 |
| `直接施工` | 方案 → 实现 | 规则单一、可观察结果显而易见，写出来的验收场景只会是实现步骤的复述；改动局限在模块内部，且 9.3 的验证方式已经能直接落到具体测试文件 |

命中任一"契约验收"信号就推荐契约验收。用户选择直接施工时不再产出 `acceptance.feature`，9.3 的验证方式就是唯一的验证契约，因此这些内容必须写得足够具体，能直接交给 `test-authoring`。

路径不是终身的。实现过程中发现规则比预期复杂、需要一份共同契约时，运行 `npm run spec -- route <KEY> acceptance_first` 切换；切换会重置已有的验证与质量审查记录，需要重新验证。

## 10. 完整可执行的判据

需求"完整且可执行"不是感觉，按下面逐条核对，有一条不成立就继续补：

以下条目中的节号均指方案文档的章节：

- 1.4 的每个交付结果都有第 3 节的模块承接，没有无人负责的结果；
- 1.1 需求正文提到的每项能力都能在第 3 节找到对应模块，第 3 节也没有正文之外的多余模块；
- 第 3 节的每个模块都在第 4 节的流程中出现，没有孤立模块；
- 第 4 节流程中的每个结果都能在第 5 节状态机中找到落点；
- 第 5 节的每个持久化状态都能在 7.2 的枚举字段中找到对应取值，并给出中文状态名与取值的对应关系；派生状态写明推导来源和不落库的理由；
- 7.2 的每个字段都有明确的写入方和读取方，没有无人写入或无人读取的字段；
- 第 8 节的每个接口都能在第 9 节找到实现文件，每个消费方都在文件职责表的影响方中出现；
- 第 3 节的每个模块都在 9.3 有实现方案，且步骤中出现的文件都列在 9.2；
- 第 11 节的步骤顺序不违反第 3 节的模块依赖；
- 第 12 节覆盖本阶段所有提问结论，每行都标注了真实的确认来源，正文中没有残留的待决选项。

## 11. 工作步骤

1. 从来源 Issue 提取初始目标、范围、现状和显式验收要求，再用已确认飞书详情文档展开或修正。
2. 检查本地状态；缺失时按真实来源自动初始化，存在时核对当前阶段和记录来源。
3. 读取真实代码、目录结构、模型和迁移链，核对当前行为、影响模块和可复用能力。
4. 完成模块分解，确定模块边界、依赖和交付顺序。
5. 编写业务流程与状态机，收集需要用户确认的业务选择。
6. 按本文第 6 节逐个提问确认业务规则，把结论写入文档第 12 节并修订受影响章节。
7. 向用户展示第一部分，确认业务逻辑完整无误后再继续。
8. 设计整体架构与选型，编写数据模型、接口契约、文件结构和实现方案；收集需要用户确认的技术取舍。
9. 按本文第 6 节逐个提问确认技术选型，把结论写入文档第 12 节。
10. 补全外部服务与安全边界、实施顺序和风险依赖。
11. 运行本文第 10 节的完整可执行判据逐条自检，不通过就回到对应章节。
12. 向用户展示第二部分并确认技术取舍。
13. 按本文第 9 节提问确认后续路径，然后带上结论冻结：

```bash
# 方案 → 验收契约 → 实现
npm run spec -- freeze <KEY> solution --next acceptance_first

# 方案 → 实现
npm run spec -- freeze <KEY> solution --next direct_build
```

未经用户确认，不得自行冻结，也不得替用户选定 `--next`。冻结后按所选路径转 `acceptance-generator` 或 `implementation-execution`。

## 12. 冻结质量标准

冻结前必须满足：

- 需求正文成段完整，读完即知本次要做什么；正文、交付结果、使用场景与非目标互不冲突；
- 现状描述有仓库证据；
- 抬头基本信息完整，需求编号、来源 Issue、后续路径、时间和当前状态与实际一致；
- 第一部分没有类名、方法名、表名、字段名、框架名或文件路径；
- 没有为通用技术术语单独解释，自创说法已在首次出现处就地说清；
- 模块清单完整，每个模块有边界、依赖、交付顺序和完成信号，依赖关系无循环；
- 主流程可以从触发运行到可见结果，关键异常包含触发条件、反馈及失败后的状态或数据结果；
- 状态机要么明确写"不涉及"并说明依据，要么状态、流转、触发者、副作用和不允许的流转完整，且持久化状态与派生状态已区分；
- 架构图、分层职责和关键数据流成立，图的类型与内容匹配且图后有文字补充，选型取舍表每行都有放弃的方案和代价；
- 数据模型要么明确写"不涉及"并说明依据，要么字段、约束、索引、枚举和定稿 DDL 完整，且与现有模型和迁移链的起点一致；
- 文件结构和实现方案落到真实路径，每个模块的"实现步骤"是编号步骤且都有"验证方式"；没有内容的可选小节已删除而不是写"无"；
- 外部服务与安全边界要么完整，要么明确写"不涉及"并说明依据；
- 实施顺序不违反模块依赖，每步有完成判据；
- 本文第 10 节的完整可执行判据全部通过；
- 没有仍会改变范围或行为的未决问题，正文没有保存待决选项或问答过程；
- 已确认决策覆盖本阶段所有提问结论，且每行确认来源真实，没有把未确认的推荐答案写成用户确认；
- 文档与当前有效的来源 Issue 和飞书详情材料一致；
- 文件中不包含占位符、过程记录或未经确认的实现承诺。

- 后续路径已由用户选定，不是本技能自行填写。

冻结后按所选路径推进：选定契约验收时转 `acceptance-generator`，不要直接进入实现；选定直接施工时转 `implementation-execution`，此时 9.3 的验证方式就是唯一的验证契约。
