# 技术设计生成与收敛

## 1. 职责

把冻结的 L3 需求和验收规则转换为可以直接执行的技术方案。技术设计必须回答：

- 修改、新增或删除哪些真实文件；
- 每个模块承担什么职责，调用关系如何变化；
- API、共享类型、错误、权限和数据契约如何落地；
- 数据如何迁移，失败和回滚如何处理；
- Express 与 FastAPI 的兼容和切换边界是什么；
- 每个验收场景由哪里实现、由什么测试验证。

本阶段不编写业务代码，也不修改 Issue、提交或 PR。

## 2. 使用前提与机器门禁

本技能只用于 L3。进入前运行：

```bash
npm run spec -- check <KEY> technical_design
```

以下情况停止并返回上游：

- 需求简报或验收契约缺失、未冻结或哈希漂移；
- 设计过程中发现业务范围、权限规则或验收结果仍未确定；
- 任务实际只需要 L2，且不存在跨模块或高风险设计内容。

不能根据聊天记忆生成技术设计，也不能用通用框架惯例代替仓库事实。

## 3. 必读材料

1. `AGENTS.md`；
2. `.specs/<KEY>/state.yaml`；
3. `.specs/<KEY>/brief.md`；
4. `.specs/<KEY>/acceptance.feature`；
5. [technical_design.template.md](technical_design.template.md)；
6. 所有预计修改文件及其最近的调用方和测试；
7. 涉及时读取前端 API 客户端、共享类型、Vite 代理、环境变量和部署配置；
8. 涉及时读取 FastAPI 路由、临时 Express 路由、数据库模型、迁移和对象存储实现。
9. 涉及公共契约结构、语义或兼容变化时，读取 `contract-guard` 和共享契约治理映射；没有契约变化时不要为了流程完整额外调用。

只要方案声称“复用、修改或替换”某个能力，就必须先读取对应真实代码或文档。

## 4. 输出位置

固定输出到：

```text
.specs/<KEY>/technical_design.md
```

已有技术设计时先读取当前内容并在原章节修订。不要无说明地覆盖关键决策，也不要在末尾堆叠与正文冲突的补丁章节。

## 5. 设计内容要求

### 目标、范围与输入依据

- 引用冻结的需求简报和验收契约；
- 明确技术目标、非目标和关键约束；
- 如果修正了需求简报中的模块判断，说明差异和证据。

### 当前系统分析

- 指出真实入口、调用链、状态和数据流；
- 说明可复用能力、现有限制和过渡实现；
- 区分 FastAPI 现有能力与临时 Express 能力，不把规划当成已完成迁移。

### 文件与模块职责

列出本次涉及的文件树，每个文件标注新增、修改、删除、不改或待确认，并说明目的。修改已有文件时路径必须真实存在；新增文件的父目录必须符合当前项目结构。

### API、类型与错误契约

- 明确请求、响应、字段可空性、共享类型和错误语义；
- 指出前端调用方、后端路由和兼容旧调用的处理；
- 说明失败时 HTTP 状态、业务错误和用户可见反馈如何对应。

### 数据、迁移与完整性

- 明确物理字段、类型、约束、索引和关联关系；
- 说明迁移顺序、旧数据处理、事务边界和回滚；
- 说明重复请求、并发写入、部分失败和数据修复策略。

### 鉴权、归属与安全

- 明确身份从哪里获得；
- 每个资源由谁拥有，在哪里校验归属；
- 说明敏感字段、文件路径、下载访问和信任边界。

### Express、FastAPI 与部署兼容

- 明确请求当前由谁处理，改造后由谁处理；
- 同步检查前端 API 客户端、Vite 代理、环境变量和部署文件；
- 给出兼容窗口、切换顺序、监控信号和可执行回滚步骤；
- 未完成实现和回归前，不设计删除 `server`、SQLite 或旧拓扑。

### 验收、实现与测试映射

每个验收场景必须映射到具体实现位置和验证位置。不能只写“补充测试”，也不能留下无人承接的场景而不说明风险。

## 6. 设计步骤

1. 通过机器门禁并读取全部冻结输入。
2. 列出验收场景清单，作为设计覆盖基线。
3. 扫描真实代码，确认入口、依赖、调用方、现有测试和过渡边界。
4. 先确定模块职责和主链路，再设计接口、数据、权限和失败路径。
5. 命中公共契约时使用 `contract-guard` 形成影响清单，并把结论写入对应设计章节，不重复保留第二份分析报告。
6. 补充兼容、发布、回滚和监控方案。
7. 建立“验收场景 → 实现位置 → 测试位置”映射，检查覆盖缺口。
8. 使用模板生成或修订技术设计，替换全部占位内容；不适用章节明确写“不涉及”并说明原因。
9. 向用户展示关键决策、风险和待确认项，迭代修订直到确认。

## 7. 发现上游缺口时的回流

如果技术设计无法在不改变用户行为的前提下落地：

- 范围、用户结果或非目标有变化：返回 `brief-generator`；
- 验收断言、权限或边界规则有变化：返回 `acceptance-generator`；
- 修订对应产物并重新冻结后，重新运行技术设计门禁。

不得只在技术设计中悄悄改变需求或验收契约。

## 8. 技术决策盘问

技术设计初稿可能暴露新的实现分歧。先判断决策归属：

- 能由代码、现有架构和测试证据判断的局部实现选择，由本技能给出结论和理由；
- 会改变外部契约、数据处理、兼容窗口、权限边界、运行成本、发布或回滚方式的选择，属于阻塞性技术决策；
- 实际改变需求范围或验收行为的，不留在技术设计中，返回对应上游产物。

阻塞性技术决策使用 `decision-grilling` 一次询问一个。用户确认后把结论回写对应设计章节，删除草稿中的阻塞项，并重新检查受它影响的接口、数据、测试和发布方案。冻结前必须没有未解决的阻塞性技术决策。

## 9. 冻结质量标准

冻结前必须满足：

- 所有修改路径和现有方法均已通过代码核实；
- API、错误、权限、数据和部署契约没有遗漏；
- 数据迁移、兼容和回滚步骤可执行；
- Express 与 FastAPI 的过渡边界清晰；
- 每个验收场景都有实现和验证承接；
- 不确定内容明确标注，没有编造文件或方法；
- 没有模板占位内容或与上游产物冲突的结论。

只有用户明确确认技术方案后运行：

```bash
npm run spec -- freeze <KEY> technical_design
```

冻结后转 `implementation-execution`。
