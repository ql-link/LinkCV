# 代码审查与质量门禁

## 1. 职责与授权边界

以缺陷和交付风险为中心审查当前改动，判断是否可以进入提交和 PR 阶段。

审查请求默认是只读操作：

- 可以读取代码差异、规格、测试和命令结果；
- 不自动修改文件、提交、推送或创建 PR；
- 用户同时要求修复时，才进入实现并在修复后重新审查。

用户问的是“相对原始需求是否真正做完、还缺什么”时转 `feature-completion-audit`；本技能继续专注实现质量，不重复完成度对账。

## 2. 审查输入

至少读取：

1. `AGENTS.md`；
2. 当前分支、`git status`、提交范围和完整差异；
3. 新增或修改的测试；
4. 方案先行任务的 `.specs/<KEY>/state.yaml`、冻结产物和实施报告（如果存在）；
5. 适用的 `.specs/<KEY>/manual_acceptance.md`；
6. `state.yaml` 中由 `spec verify --run` 自动记录的命令、退出码和代码快照；
7. 与变更相关但未修改的调用方、公共类型和配置。

审查 PR 或分支时，先确认正确的目标分支和来源分支。不要只看工作区差异而遗漏已提交改动，也不要把无关历史差异归到当前任务。

## 3. 审查顺序

### 需求与范围

- 实现是否覆盖全部确认范围；
- 是否出现未确认的功能扩张或顺手重构；
- 每个验收场景是否有实现和验证承接；
- 实施报告中的偏差是否已经解释并重新确认，实际数据结构与状态流转是否与冻结方案文档一致。

### 正确性与失败路径

- 主流程、空值、边界、重复请求和并发是否正确；
- 错误是否在正确层处理，是否保留有用上下文；
- 部分失败时是否留下不一致状态；
- 前端状态、后端响应和持久化结果是否一致。

### API 与跨端契约

- 请求、响应、共享类型、可空性和错误语义是否同步；
- FastAPI、前端 API 客户端、Vite 代理、环境变量和部署入口是否兼容；
- 路由或契约切换是否有兼容窗口和回滚方案；
- 是否误删仍由当前调用方依赖的代码或配置。
- 是否已有适用的契约影响、配置核对和文档同步结果；已有证据时核实遗漏，不重新执行同一轮分析。
- 机器门禁通过不代表语义兼容，仍需检查权限、状态、错误和回滚行为。

### 权限与安全

- 鉴权是否在可信边界执行；
- 资源归属是否针对每次读取、修改和删除校验；
- 文件路径、下载、对象存储和本地资源是否可能越权暴露；
- 日志、错误、测试和配置是否泄露凭据或用户数据；
- 输入校验是否能阻止路径穿越、注入和非法类型。

### 数据与迁移

- 模型变更是否有迁移和旧数据处理；
- 约束、索引、事务和关联关系是否保持完整性；
- 升级、回滚和重复执行是否安全；
- 失败后是否可能产生孤立、重复或半完成数据。
- Alembic revision 是否接到预期 head、是否使用配对 up/down SQL、是否存在 Python DDL、改写已发布历史或伪 downgrade；需要深入迁移审查时使用 `alembic-migration` 的已有结论，不在本技能复制完整流程。

### 外部服务与 LLM（适用时）

- 发送数据是否最小化并符合已确认的隐私、保留与地域边界；
- 密钥是否只存在于后端受控配置，日志、错误、前端包和测试中是否泄露敏感内容；
- 成本、配额、限流、并发、超时、重试、幂等和取消是否存在失控或重复计费风险；
- 拒绝、超时、限流、异常响应和部分结果是否有明确降级及用户可见反馈；
- 日志和指标是否足以排查耗时、成本和错误，同时保持正文与凭据脱敏；
- 自动化测试是否使用受控替身覆盖主要异常路径，真实联调是否与普通测试隔离。

### 可维护性与性能

- 是否遵守当前模块边界，避免不必要耦合；
- 命名、控制流和注释是否能解释非显然意图；
- 是否存在无界查询、重复网络调用、明显的重复渲染或大对象复制；
- 新复杂度是否有实际需求支撑。

### 验证质量

- 测试是否真的能在行为错误时失败；
- 是否只覆盖主流程而遗漏高风险失败路径；
- 报告的命令是否真实执行并覆盖本次影响；
- 前端组件测试未覆盖的交互和跨端流程是否已明确人工核实方式。
- 适用的人工验收是否逐项记录真实结果，是否仍有未执行、失败或阻塞的必要项。

## 4. 问题分级

按影响分级，不按修改难度分级：

- 严重：可能造成安全漏洞、数据破坏、权限绕过、生产不可用或核心功能错误，必须阻断；
- 必须修复：明确需求偏差、兼容问题、迁移风险或关键测试缺失，修复前不得进入 PR；
- 一般：在特定条件下造成错误或维护风险，应在当前交付修复；
- 建议：不影响当前正确性，可作为后续优化。

每条问题必须包含：

- 精确文件和尽可能小的行范围；
- 可复现条件或触发场景；
- 实际影响；
- 为什么当前实现不足；
- 简短修复方向。

不要把纯格式偏好、没有行为影响的个人风格或无法由代码证明的猜测列为缺陷。

## 5. 输出要求

先列问题，再给总体结论。建议结构：

```text
问题：
1. [级别] <标题>
   位置：<文件和行>
   条件：<如何触发>
   影响：<错误、安全、数据或兼容后果>
   建议：<修复方向>

结论：可进入 PR | 修复后复审 | 阻断
审查范围：<已检查的规格、代码、测试和契约>
验证证据：<已执行命令>
残余风险：<未覆盖或依赖人工确认的区域>
```

没有发现问题时，明确写“未发现阻断问题”，同时说明残余风险和测试空白；不要只回复“看起来没问题”。

## 6. 阶段转交

- 存在严重、必须修复或影响当前交付的一般问题：返回 `implementation-execution`；
- 发现规格与实现冲突：返回 `solution-generator` 或 `acceptance-generator`；
- 活跃的方案先行任务处于 `quality_review`，且没有阻断问题时，记录与当前验证快照绑定的审查结论：

  ```bash
  npm run spec -- review <KEY> --pass --evidence "<简洁审查结论>"
  ```

  命令由 Agent 执行，不要求开发者维护状态字段；代码在验证后变化时会被门禁拒绝，修复并重新验证后再复审。
- 审查记录成功且用户要求发布：转 `branch-pr-workflow`；
- 用户没有要求提交或 PR：审查结束后停止，不推断发布授权。
- 用户要求判断功能完成度：转 `feature-completion-audit`，以原始需求重新取证。
