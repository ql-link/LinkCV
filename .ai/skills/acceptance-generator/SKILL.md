# 验收契约生成与收敛

## 1. 职责

把冻结的需求简报转换为 `.specs/<KEY>/acceptance.feature`。每个场景描述一条可以验证的业务规则，作为实现、技术设计和后续测试的共同契约。

本阶段回答“什么行为才算做对”，不回答“代码怎么实现”。不得在场景中写类名、方法名、表结构、框架选型或部署步骤。

## 2. 使用前提与停止条件

进入前运行：

```bash
npm run spec:source -- check <KEY> --gate acceptance # 仅 Multica 来源
npm run spec -- check <KEY> acceptance
```

出现以下任一情况立即停止：

- `brief.md` 缺失、未冻结或冻结后内容发生变化；
- 需求简报仍有会改变业务规则的阻塞问题；
- Multica 标题或描述自 Brief 冻结后发生变化，或者需求源当前无法核验；
- 用户尚未确认需求范围；
- 只能写出“正确处理”“适当提示”一类不可断言结果。

停止后返回 `brief-generator` 修订并重新冻结。若存在两个以上会改变用户行为的合理答案，先使用 `decision-grilling` 逐项确认；不得根据聊天记忆补齐规则后继续。

## 3. 必读材料

1. `.specs/<KEY>/state.yaml`；
2. `.specs/<KEY>/brief.md`；
3. 与用户可观察行为直接相关的当前实现、接口和测试；
4. [acceptance.template.feature](acceptance.template.feature)。

模板是 Gherkin 写法参考，不是业务内容。不得复制模板中的虚构事实代替真实需求。

## 4. 输出位置与语法

固定输出到：

```text
.specs/<KEY>/acceptance.feature
```

使用标准 Gherkin 关键字 `Feature`、`Background`、`Scenario`、`Scenario Outline`、`Given`、`When`、`Then`、`And`。这些关键字属于机器语法，场景名称、步骤和注释统一使用中文。

当前 LinkCV 已建立前端单元和组件测试基础，但尚无自动化端到端测试框架。本文件首先是可执行化的验收契约；只有存在真实映射且已经运行的自动化测试时，才能声称对应场景被自动验证。跨端流程仍需人工验收。

## 5. 场景写作规则

### 一条场景表达一条规则

- `Given`：可建立的前置状态；
- `When`：用户动作、接口调用或系统事件；
- `Then`：可观察、可断言的结果；
- `And`：补充同一阶段的条件或断言。

相同规则的多组输入使用 `Scenario Outline` 和 `Examples`，不要复制多份只有参数不同的场景。

### 结果必须可断言

合格示例：

- 返回明确的状态码和错误语义；
- 页面出现或不出现明确内容；
- 数据被创建、更新、保持不变或拒绝写入；
- 未授权用户无法读取或修改不属于自己的资源；
- 重复请求不产生第二份数据或重复副作用。

不合格示例：

- 系统正确处理；
- 用户体验良好；
- 返回适当错误；
- 数据正常保存。

## 6. 必须覆盖的场景类别

根据需求实际涉及面选择，但不能遗漏适用项：

1. 主流程：最常见成功路径和最终可见结果；
2. 权限与资源归属：未登录、越权、跨用户访问；
3. 输入校验：缺失、非法格式、超限和互斥条件；
4. 状态和持久化：状态转换、保存结果、失败时是否写入；
5. 异常路径：依赖失败、接口失败、存储失败和用户可见反馈；
6. 边界条件：空集合、最小值、最大值、重复操作和并发；
7. 重试与幂等：适用于上传、保存、异步任务和可重试调用；
8. 兼容与回归：旧数据、旧路由或未改动行为必须保持的结果。

非功能要求如性能目标、监控指标和部署约束，如果不能用当前验收层直接观察，应保留在需求简报或技术设计中，不强行写成虚假场景。

## 7. 生成步骤

1. 从需求简报逐条提取业务规则、参与者、状态、输入、输出和风险。
2. 建立规则清单，确保范围中的每项交付都有对应场景。
3. 把公共前置条件放入 `Background`，避免每个场景重复。
4. 先写主流程，再补权限、异常、边界、幂等和回归场景。
5. 逐条检查每个 `Then` 是否能由界面、接口、状态或数据断言。
6. 检查场景之间是否重复、矛盾或引入需求简报之外的新范围。
7. 发现事实缺口时探索代码；发现真实业务分歧时返回 `brief-generator` 并使用 `decision-grilling`，确认后重新冻结需求简报。
8. 向用户展示场景覆盖和仍待确认的业务规则。
9. 用户反馈后重新读取当前文件，在原场景中修订，不保留问答记录。

## 8. 冻结与质量门槛

只有用户明确确认验收规则后运行：

```bash
npm run spec -- freeze <KEY> acceptance
```

冻结前必须满足：

- 需求范围中的每个用户可见行为都有场景承接；
- 适用的权限、校验、失败、边界和幂等规则已覆盖；
- 每个结果都具体可断言；
- 没有实现细节、模糊措辞或模板占位内容；
- 场景之间没有相互冲突；
- 没有把尚未自动化的场景描述成已通过测试。

L2 冻结后转 `implementation-execution`；L3 冻结后转 `technical-design`。实现完成后，无法由自动化测试覆盖的跨端或视觉场景由 `manual-acceptance` 转换为人工执行清单；本技能不提前复制第二份清单。
