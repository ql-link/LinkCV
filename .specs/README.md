# LinkCV 本地 Spec 文档

`.specs/<KEY>/` 保存需要持久设计依据的本地开发文档，不保存机器阶段、文档哈希、验证快照或任务状态。纯后端与前后端混合任务以 `solution.md` 为业务和技术中心；纯前端标准或完整任务可以只以 `ui-design.md` 为中心；混合任务的 `ui-design.md` 只能作为 `solution.md` 的从属 UI 附件。

用户当前请求、可读取的 Issue、飞书文档及用户明确指定的其他材料都可以作为初始需求来源。Issue 存在时完整读取并关联；没有 Issue 不阻止方案、实现或 PR，本地任务可以使用 `LOCAL-YYYYMMDD-SHORT-SLUG` 作为目录名。飞书只提供方案形成前的初步设计；对纯前端则指 UI 设计形成前。后端与混合任务确认 `solution.md` 后以它作为当前实施和验收依据，纯前端持久设计确认 `ui-design.md` 后以它作为 UI 实施和验收依据。

## 文件组成

| 文件 | 什么时候存在 | 职责 |
| --- | --- | --- |
| `solution.md` | 纯后端或混合任务进入方案先行时 | 业务与技术中心，保存需求、流程、规则、数据与状态设计、契约、真实文件、实施步骤和验证映射 |
| `ui-design.md` | 纯前端标准或完整任务需要持久设计，或混合任务需要独立 UI 设计时 | 纯前端任务的 UI 中心；混合任务中从属于 `solution.md`，保存信息结构、交互呈现、布局、响应式、组件计划和 UI 验证映射 |
| `acceptance.feature` | 方案选择契约验收时 | 展开需要独立确认的可观察业务规则 |
| `manual_acceptance.md` | 自动化无法覆盖必要的跨端、浏览器、PDF 或视觉结果时 | 保存人工执行步骤和真实结果 |
| `implementation_report.md` | 存在已允许偏差、已接受限制或必须交接的遗留事项时 | 只补充方案之外的新事实 |

同一任务不得创建第二份 `solution.md`、第二份 `ui-design.md`、平级 Change、任务状态文件或验证报告。混合任务的业务、API、权限、数据与失败语义只写在 `solution.md`，不能在 `ui-design.md` 维护第二套结论。未命中的附件不创建。

## 领域与交付路径

- **直接实现**：不创建 Spec，根据当前请求和真实代码直接实现、验证和审查。
- **纯后端方案 → 实现**：确认 `solution.md` 后直接施工，方案中的“验证与验收”就是验证依据。
- **纯后端方案 → 验收契约 → 实现**：确认 `solution.md` 后生成并确认 `acceptance.feature`，再施工。
- **纯前端 UI 设计 → 实现**：标准或完整前端任务按 `frontend-delivery` 创建并确认适用的 `ui-design.md` 后施工；轻量任务不创建 Spec。
- **混合方案 → UI 设计 → 分域实现**：先确认 `solution.md`，再按需创建从属 `ui-design.md`；后端与前端分别消费同一个契约来源。

顺序是内容关系，不是机器状态机。AI 根据最新用户指令、Spec 文档、Git 差异、真实代码和本次实际验证自行判断下一步。缺少阶段字段、哈希或门禁命令本身不得构成阻塞。

## 创建和修订

后端或混合方案先行时由 `solution-generator` 直接创建 `.specs/<KEY>/solution.md`。纯前端持久设计由 `frontend-delivery` 创建 `.specs/<KEY>/ui-design.md`。已有文件就在原文档中修订，不生成“最终版”“第二版”或对话流水账。

`solution.md` 和 `ui-design.md` 都不保存全局的“当前阶段”或整份文档确认标记。具体业务决定和重要技术取舍只写入 `solution.md`；纯前端的布局、交互或视觉决定写入 `ui-design.md`。仍有会改变范围、用户行为、权限、数据、安全、兼容或不可逆结果的未决项时必须确认；普通实现细节由 AI 按仓库事实自行决定。

中心文档发生实质变化时更新原文档，只重新确认受影响的决定。若最新用户决定与飞书或 Issue 等初始来源不同，在对应中心文档中写清被替代结论、当前结论和确认来源；不反向同步飞书或 Issue 正文，也不另建平级变更文档。混合任务凡涉及范围、业务、API、权限、数据、状态、兼容或失败语义都先修改 `solution.md`，随后同步受影响的 `ui-design.md`。普通文件组织、命名、测试落点和其他不改变外部结果的实现调整不修改设计依据，按需在 PR 中解释。

只有原目标或核心验收已经失效、变化形成独立交付边界，或整个模块商业前提需要重建时，才停止沿用当前 Spec 并开启新一轮任务；同一目标内的重要决定变化继续修订适用的 `solution.md` 或 `ui-design.md`，不从飞书或 Issue 重新走一遍。混合任务的业务与契约变化仍只先进入 `solution.md`。

## 验证与收尾

任务完成时直接运行与改动范围和风险匹配的真实命令，不保存本地“已通过”状态。跨会话恢复后不继承以前会话的测试结论；准备创建 PR 时必须在当前可提交内容上重新运行完整 `npm run check`，共享 CI 继续运行完整入口。PR 负责说明实际交付及相对当前方案和初始来源的重要差异；存在来源 Issue 时，PR 创建后只追加一条交付评论，不把 Spec 正文复制回外部系统。

人工验收文件中的单项结果是实际证据，可以保留。相关代码、配置或环境发生变化时，由 AI 根据影响把对应项目恢复为未执行并重新验收。

## 跨会话与 worktree

新会话恢复任务时：

1. 读取当前请求和匹配的中心文档：后端或混合任务读取 `solution.md`，纯前端持久设计任务读取 `ui-design.md`；混合任务存在 `ui-design.md` 时一并读取；
2. 读取实际存在的 Acceptance、人工验收和实施报告；
3. 检查当前分支、Git 提交、工作区差异和真实代码；
4. 对照实施步骤与验证映射判断下一步；
5. 重新运行完成当前交付所需的检查。

多个 Spec 都可能匹配时由用户指定继续哪一个，不自动猜测。

`.specs/*/` 被 Git 忽略，不进入提交或远端；仓库中的 `.worktreeinclude` 只在 Codex 新建本地托管 worktree 时复制一次这些文档。它不是实时同步：两个已有 worktree、命令行 worktree、远程环境和不同设备不会自动保持一致，同一个 Spec 不应在多个 worktree 中并行编辑。

产物模板由对应的 `.ai/skills/<skill>/` 管理。仓库长期只跟踪本说明，不把本地任务内容复制进 `docs/`。
