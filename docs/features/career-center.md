# 求职中心功能

## 功能范围

求职中心覆盖岗位导入、一次求职尝试、阶段推进、面试排期、面试记录和素材。岗位资料可被多次求职尝试复用；一次 `JobApplication` 才是完整求职生命周期的聚合根。

字段、状态动作和错误语义见 [HTTP 接口契约](../api/http-contracts.md)，浏览器采集能力见 [浏览器插件架构](../internals/extension.md)。

周排期支持按住安排卡片在当天上下移动，保持原时长；拖动上、下边缘分别修改开始、结束时间，另一端保持不变。每步调整 30 分钟，最短时长为 30 分钟，不能拖出当天。松手后通过现有排期接口保存，时间冲突仍需确认，其他失败重新读取服务端数据。

## 用户入口

- `/career/applications`：默认展示阶段看板，并可切换到求职记录列表；同时提供岗位导入、采集插件入口、求职进程创建和详情。
- `/career/schedule`：面试排期。
- `/career/applications/:id`：一次求职进程的阶段、面试记录和岗位快照；从这里可下钻到完整岗位。
- `/career/jobs/:jobId`：复用原 JD 详情页展示并就地编辑完整岗位，不提供独立岗位列表入口。
- `/career/reviews`：面试记录和素材的内部入口。
- `/career/jobs`、`/jobs` 与旧 `/interviews` 只承担兼容跳转并回到求职记录；旧岗位新建入口打开求职记录内的岗位导入弹窗，旧岗位详情链接继续兼容。

## 核心对象与规则

- `job_descriptions` 保存用户私有的结构化岗位和来源身份；删除岗位会释放来源唯一键，但不会删除既有求职历史。
- `job_applications` 保存岗位快照、可选正式简历版本快照、投递事实、流程生命周期、Offer、归档状态与乐观锁；`applied_at` 为空就是待投递。
- `job_application_stages` 以追加记录保存稳定阶段类型、用户可见名称、可选面试轮次、顺序和当前标记；当前阶段和历史都以该表为准。
- `interview_sessions` 同时承载单场排期和复盘，并关联产生排期的具体求职阶段。
- `interview_assets` 保存面试录音、视频或文档的对象元数据，文件访问继续校验所属求职进程。
- 创建面试必须先存在岗位、求职进程和可排期阶段，不能产生孤立排期；阶段动作只能由后端应用服务执行。

## 依赖边界

该功能依赖身份、简历正式版本、统一 LLM、对象存储和审计。浏览器插件只负责提交用户确认后的岗位采集字段；AI 助手可把岗位、求职进程和复盘作为只读上下文，但不能代替求职中心写阶段状态。

## 关键流程

### 岗位进入系统

- 手工创建直接走统一创建服务；职位名称和公司名称必填，职位描述可以留空。
- 文字/图片智能导入只生成待确认草稿；用户确认后才创建岗位，原始输入和模型正文不落库。未识别出职位描述不阻止确认创建。
- 插件导入先清洗页面字段、规范化来源 URL 和站点身份，再复用相同创建与重复解决事务，不调用 LLM。

### 求职与面试

1. 用户导入或填写岗位 JD 后，后端在同一事务中创建或复用一条待投递求职记录；JD 是先行必需项，正常入口不再要求用户另建求职进程。
2. 待投递记录可一次进入筛选中、测评、笔试、AI 面试、普通面试或 Offer，也可以直接终止；这次操作同时建立第一条阶段历史并隐式完成“已投递”。用户可以补填实际投递时间，不填时以后端本次有效操作时间为准。简历可不选；选择简历时绑定本人最新正式版本。
3. 后续每次阶段变化只追加新阶段并保留历史，不覆盖旧阶段。筛选、测评、笔试、AI 面试和 Offer 使用稳定类型；普通面试名称由用户按公司流程填写，例如“一面”“二面”“技术终面”或“HR 面”，轮次由用户选填，不从名称推断。
4. “添加下一阶段”弹窗用同一条阶段轨道直接选择测评、笔试、AI 面试、普通面试或 Offer，并在原弹窗切换对应表单，不再先选阶段分类或勾选“现在添加日程”。测评填写可选链接、必填开始时间和完成期限；笔试填写固定开始/结束时间及可选链接或地点；AI 面试填写可选链接、开始时间和完成期限；普通面试填写自定义名称、可选轮次、时间、时长、方式及链接或地点；Offer 复用现有待遇字段。测评开始日期默认当天，日期通过日历修改，具体小时和分钟由用户在面板内点击选择，不使用手工时间输入；分钟支持 `00–59`。除测评开始时间外，没有明确排期时可以只保存阶段后再补充。排期必须关联当前阶段并校验时间范围和冲突，完成、取消与复盘共享同一场 `InterviewSession`。客户端提交 ISO 时间和 IANA 时区。若先成功添加阶段、后续排期创建失败，该阶段仍保留，用户可再次安排。
5. 音频素材先校验进程所有权，再保存对象与元数据；读取和删除继续通过 session→application→user 链路授权。后端继续兼容历史评价字段以及既有视频、文档素材，不因前端入口简化而清除存量数据。
6. Offer 阶段只在用户已经收到 Offer 后添加，不再区分 OC 与书面 Offer。进入阶段时可选填 Base、单值薪资、币种、计薪周期和福利待遇，也允许全部留空；填写薪资时要求同时选择币种和计薪周期，但保存的是这次投递的实际 Offer，不自动复制个人偏好。Web 的列表、看板、详情标题、求职信息和进度节点统一展示“已收到 Offer”；状态记录失败的异常记录显示“Offer 状态待确认”。历史 `accepted` 兼容展示为“已收到 Offer”，历史 `declined` 兼容展示为“已主动结束”，但前端不提供接受或婉拒 Offer 的录入动作。

### 求职进程看板

- 看板分为待投递、筛选中、测评/笔试/AI 面试、用户自定义普通面试、Offer 和已终止；普通面试按 `stage_label` 动态拆列。
- 待投递卡片可以直接选择任何业务阶段或终止；进行中的卡片可以在阶段轨道上直接选择下一阶段或终止，不再经过独立“标记已投递”动作。阶段节点切换会立即替换下方表单，已填写的其他阶段草稿只保留在当前弹窗会话中。拖放和表单最终都调用阶段追加或终止接口，冲突后重新读取服务端状态。
- 求职列表默认展示公司/岗位、求职分类、当前进度、最近安排、投递日期和更新时间；最近安排只展示进行中求职流程内尚未结束的有效排期，历史场次保留在详情中。列表按求职分类分组时隐藏重复的分类列，各分类使用带独立表头的表格区块，组间留白，分类标题显示记录数量。

- 右侧圆形“视图设置”图标按钮打开设置面板，顶部提供列表/阶段看板分段切换，下方提供分组与排序下拉框。开启求职分类分组后，实习、校招、正式和未分类分别展示一行带独立列框的阶段看板，各行阶段列保持对齐；跨分类行拖动不会修改分类或推进阶段，分类通过卡片菜单“修改分类”保存。
- 求职分类复用 `job_snapshot.employment_type`，空值归入未分类。修改仅作用于这次求职记录，不改原岗位和其他记录的快照；后台采用同一进程乐观锁处理冲突。岗位导入和编辑的 `employment_type` 使用同样三类枚举，详情继续展示当前快照。

- 看板以接口返回的稳定阶段类型和普通面试 `stage_label` 组合真实阶段列；普通面试名称不压缩回固定轮次。未归档、未终止且尚未进入 Offer 的进程可以发起拖动，合法落点复用阶段追加接口；同列、非法倒退和终态拖放不写入，冲突后重新读取服务端状态。
- 宽看板支持 Shift+滚轮、空白区域拖动和卡片靠近边缘时自动横向滚动；横向位置保存在当前标签页的 `sessionStorage` 中，重新进入看板时恢复，卡片按钮和其他交互控件不触发空白拖动。

## 一致性与失败边界

- 删除岗位只解除求职进程的来源外键，已保存的岗位和简历快照必须继续可读。
- 创建、阶段动作、排期移动和复盘更新使用 `lock_version` 或幂等请求边界，冲突时不覆盖较新的服务端状态。
- LLM、对象存储或插件采集失败不能生成部分岗位、孤立素材或虚假求职阶段。
- 新增阶段、结果、颜色或素材类型必须同步数据库 CHECK、应用服务、schema、前端映射和接口契约。

## 修改联动与验证

岗位来源契约变化还需同步插件 `contracts.ts`、Manifest 权限和导入测试；求职状态变化需同步看板、列表、排期、复盘和 Agent 上下文。兼容期内服务端继续维护旧扁平阶段字段，旧标签只用于历史投影，新 Web 以 `current_stage`、有序 `stages`、`phase` 和 `lifecycle_status` 为准。主要验证入口为后端 `test_job_descriptions.py`、`test_interviews.py`、`test_job_description_import.py`，以及 Web `JobSmartImportDialog` 和 `InterviewCenterPage` 测试。
