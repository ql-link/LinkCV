# 求职中心功能

## 功能范围

求职中心覆盖岗位导入、一次求职尝试、阶段推进、面试排期、面试记录和素材。岗位资料可被多次求职尝试复用；一次 `JobApplication` 才是完整求职生命周期的聚合根。

字段、状态动作和错误语义见 [HTTP 接口契约](../api/http-contracts.md)，浏览器采集能力见 [浏览器插件架构](../internals/extension.md)。

## 用户入口

- `/career/applications`：默认展示阶段看板，并可切换到求职记录列表；同时提供岗位导入、采集插件入口、求职进程创建和详情。
- `/career/schedule`：面试排期。
- `/career/applications/:id`：一次求职进程的阶段、面试记录和岗位快照；从这里可下钻到完整岗位。
- `/career/jobs/:jobId`：复用原 JD 详情页展示并就地编辑完整岗位，不提供独立岗位列表入口。
- `/career/reviews`：面试记录和素材的内部入口。
- `/career/jobs`、`/jobs` 与旧 `/interviews` 只承担兼容跳转并回到求职记录；旧岗位新建入口打开求职记录内的岗位导入弹窗，旧岗位详情链接继续兼容。

## 核心对象与规则

- `job_descriptions` 保存用户私有的结构化岗位和来源身份；删除岗位会释放来源唯一键，但不会删除既有求职历史。
- `job_applications` 保存岗位快照、可选正式简历版本快照、当前阶段、结果、归档状态与乐观锁。
- `interview_sessions` 同时承载单场排期和复盘，约束阶段、轮次、时间、状态和结果组合。
- `interview_assets` 保存面试录音、视频或文档的对象元数据，文件访问继续校验所属求职进程。
- 创建面试必须先存在岗位和求职进程，不能产生孤立排期；阶段动作只能由后端状态机执行。

## 依赖边界

该功能依赖身份、简历正式版本、统一 LLM、对象存储和审计。浏览器插件只负责提交用户确认后的岗位采集字段；AI 助手可把岗位、求职进程和复盘作为只读上下文，但不能代替求职中心写阶段状态。

## 关键流程

### 岗位进入系统

- 手工创建直接走统一创建服务。
- 文字/图片智能导入只生成待确认草稿；用户确认后才创建岗位，原始输入和模型正文不落库。
- 插件导入先清洗页面字段、规范化来源 URL 和站点身份，再复用相同创建与重复解决事务，不调用 LLM。

### 求职与面试

1. 用户在求职记录中导入或填写岗位并创建一次待投递的求职尝试；确认“已投递”时记录实际日期，简历可以不选，随后自动进入“筛选中”。如果选择简历，服务端校验归属后自动绑定该简历 `version_no` 最大的最新正式版本；所选简历没有正式版本时拒绝更新。旧调用方仍可显式提交 `resume_version_id`，但不能与 `resume_id` 同时提交。
2. “筛选中”不设用户自定义名称或轮次，并直接等待筛选结果；收到公司明确通知后，用户再添加已经确认的笔试/测评或面试阶段，同时填写日期时间、时长、方式以及链接或地点。手工填写的排期时间接受分钟 `00–59` 范围内的任意有效 `HH:mm`，不限制为整点或半点；排期视图中的拖动和键盘移动仍按 30 分钟吸附。客户端把本地日期时间转换为 ISO 时间，并随排期保存浏览器解析出的 IANA 时区，不能假定运行环境固定为 `Asia/Shanghai`。面试展示名称由用户按公司实际流程自由填写，例如“一面”“二面”或“HR 面”，后端不把名称收敛为固定枚举；内部数字轮次由客户端按当前面试轮次自动递增并继续用于状态机和排期关联，不要求用户填写。看板分类统一称为“笔试 / 测评”，阶段名称和进度状态分开展示；没有排期时显示“笔试 · 等待安排”或对应测评名称，不使用“笔试中”概括等待安排状态。阶段看板中的所有卡片都可以拿起拖动，但只有合法的后续列接受推进：待投递拖到筛选中时复用投递日期与简历绑定弹窗；笔试或面试必须先在详情页手动完成，完成后拖到目标阶段才打开统一的下一阶段弹窗。未完成、同列、倒退、Offer、已结束和已归档卡片不会改变状态；拖回原列静默取消，拖入其他不允许的状态栏时卡片回到原位并提示具体原因。拖入可用目标列时只在列头平滑让出卡位，不按指针纵向位置对列内卡片重新排序。目标为自定义面试列时自动预填该列名称。客户端只在用户确认相应弹窗后调用既有状态机与排期接口；若下一阶段排期创建失败，已推进的阶段保留为等待安排，用户可从安排时间入口重试。
3. 面试排期绑定求职进程并校验时间范围和冲突；完成、取消与面试记录共享同一场 `InterviewSession`。排期页的“安排面试”复用求职进程详情中的下一阶段表单和推进接口，先选择可推进的求职流程，再添加“笔试 / 测评”或“面试”并保存排期，不提供 Offer 入口，也不在此创建岗位或求职进程。候选流程必须仍在进行、未归档、已经投递且 `stage_state=awaiting_result`，待投递、当前阶段尚未完成和已进入 Offer 的流程不展示。Web 端新增记录只提供两种互斥方式：上传一个音频文件，或粘贴一段文字；不提供浏览器现场录音、面试评价或复盘编辑入口。
4. 音频素材先校验进程所有权，再保存对象与元数据；读取和删除继续通过 session→application→user 链路授权。后端继续兼容历史评价字段以及既有视频、文档素材，不因前端入口简化而清除存量数据。
5. Offer 阶段只在用户已经收到 Offer 后添加，不再区分 OC 与书面 Offer。进入阶段时可选填 Base、单值薪资、币种、计薪周期和福利待遇，也允许全部留空；填写薪资时要求同时选择币种和计薪周期，但保存的是这次投递的实际 Offer，不自动复制个人偏好。Web 的列表、看板、详情标题、求职信息和进度节点统一展示“已收到 Offer”；状态记录失败的异常记录显示“Offer 状态待确认”。历史 `accepted` 兼容展示为“已收到 Offer”，历史 `declined` 兼容展示为“已主动结束”，但前端不提供接受或婉拒 Offer 的录入动作。

### 求职进程看板

- 右侧圆形“视图设置”图标按钮打开设置面板，顶部提供列表/阶段看板分段切换，下方提供分组与排序下拉框。开启求职分类分组后，实习、校招、正式和未分类分别展示一行带独立列框的阶段看板，各行阶段列保持对齐；跨分类行拖动不会修改分类或推进阶段，分类通过卡片菜单“修改分类”保存。
- 求职分类复用 `job_snapshot.employment_type`，空值归入未分类。修改仅作用于这次求职记录，不改原岗位和其他记录的快照；后台采用同一进程乐观锁处理冲突。岗位导入和编辑的 `employment_type` 使用同样三类枚举，详情继续展示当前快照。

- 看板以接口返回的 `current_stage_type`、`current_round_no` 和 `current_stage_label` 组合真实阶段列；筛选中、等待沟通、一面、二面、HR 面、Offer 与已结束是基础列，接口返回的其他轮次或阶段标签按流程顺序成为独立列，不能压缩回固定五列。
- 所有进程卡片都能发起拖动；只有未归档、未结束、尚未进入 Offer 且满足当前阶段完成条件的进程允许推进。拖放只允许进入顺序更后的非结束阶段，并向既有推进接口提交目标阶段类型、轮次、标签和 `base_lock_version`；同列、逆向、当前阶段未完成或终态拖放不写入，其中跨栏失败会显示具体阻止原因，冲突后重新读取服务端状态。
- 宽看板支持 Shift+滚轮、空白区域拖动和卡片靠近边缘时自动横向滚动；横向位置保存在当前标签页的 `sessionStorage` 中，重新进入看板时恢复，卡片按钮和其他交互控件不触发空白拖动。

## 一致性与失败边界

- 删除岗位只解除求职进程的来源外键，已保存的岗位和简历快照必须继续可读。
- 创建、阶段动作、排期移动和复盘更新使用 `lock_version` 或幂等请求边界，冲突时不覆盖较新的服务端状态。
- LLM、对象存储或插件采集失败不能生成部分岗位、孤立素材或虚假求职阶段。
- 新增阶段、结果、颜色或素材类型必须同步数据库 CHECK、应用状态机、schema、前端映射和接口契约。

## 修改联动与验证

岗位来源契约变化还需同步插件 `contracts.ts`、Manifest 权限和导入测试；求职状态变化需同步看板、列表、排期、复盘和 Agent 上下文。阶段看板按待投递、筛选中、笔试中、面试、Offer 和已结束的顺序投射真实进程状态，其中面试位置会按用户填写的 `current_stage_label` 动态拆列并合并同名记录，例如分别展示“一面”“二面”和“HR 面”；没有面试记录时保留空的“面试中”列，空白旧标签也归入该兜底列。存量“等待后续通知”、初筛和复筛标签统一兼容展示为“筛选中”。主要验证入口为后端 `test_job_descriptions.py`、`test_interviews.py`、`test_job_description_import.py`、`test_interview_state.py`，以及 Web `JobDetailPage`、`JobSmartImportDialog` 和 `InterviewCenterPage` 测试。
