## 2. 起始仓库的真实工作流（历史基线）

### 2.1 已经完成的简化

详细来源文档把旧流程描述为 Brief、Acceptance、Technical Design、Implementation、Quality Review 和 Release Ready 的固定链条，但当前仓库已经不是这个版本。

2026-07-31 的 `ff74665` 已经完成以下调整：

- 删除独立 `brief-generator` 和 `technical-design`；
- 把需求分析与技术方案合并为 `solution.md`；
- 把入口改成直接实现、方案后直接施工、方案后先写验收契约三条路径；
- 让 `acceptance.feature` 变为按需产物；
- 把本地状态升级到 schema v7。

因此，本次不能按来源文档中的旧阶段数量直接重写；必须从当前三条路径继续演进。

### 2.2 当前入口仍然偏重

当前项目允许用户明确关闭工作流或指定直接实现，但默认代码改动仍先经过 `flow-router`。普通团队任务默认要求来源 Issue；没有 Issue 的用户直达请求主要被当作关闭工作流、自举或本地维护例外。

直接实现还必须同时满足多项条件。一旦涉及跨端联动、HTTP 契约、鉴权、数据库、对象存储、环境变量或部署，通常会进入完整方案路径。风险高低和需要多少规划仍然没有真正分开。

相关事实源：

- `.ai/prompts/project.md` 的“交付流程入口”；
- `.ai/skills/flow-router/SKILL.md` 的“直接实现”和“方案先行”判据；
- `.ai/skills/solution-generator/SKILL.md` 与 `solution.template.md`。

### 2.3 方案路径仍有较高固定成本

`solution-generator` 同时要求业务叙述、模块分解、流程、状态机、架构、数据模型、接口、文件结构、实施顺序、决定和风险。完整任务需要这些内容是合理的，但中等规模改动也可能因为入口判据进入同一份 13 节模板。

当前已经减少了文件数量，但还没有做到“目标明确的小任务只保留必要内容，复杂或高风险任务再逐步加严”。

### 2.4 本地恢复范围有限

方案先行任务的关键上下文位于 `.specs/<KEY>/`，而 `.gitignore` 默认忽略具体任务目录。它能支持同一 worktree 中换会话恢复。当前仓库还没有把 `.specs/*/` 写入 `.worktreeinclude`，所以新建的 Codex 托管 worktree 默认拿不到这些本地文件。

这里不必直接推导出“必须把记录提交到 Git”。Codex 支持在仓库根目录的 `.worktreeinclude` 中列出被忽略的路径，在创建本地托管 worktree 时复制匹配文件。因此，本机不同 Codex worktree 之间的初始化恢复可以继续使用被忽略的 `.specs`，不需要为了这个问题新建受 Git 管理的 Change 系统。

但 `.worktreeinclude` 是一次复制，不是持续同步；它不覆盖已经创建的 worktree、命令行自行建立的 Git worktree、远程 worktree、换设备或交给其他开发者。跨设备和正式协作仍需 Issue、PR、提交或经确认的长期文档。

直接实现路径不创建 Spec，其目标、决定和局部验证主要依赖当前会话以及最后的用户回复，跨会话恢复更弱。

### 2.5 状态仍然以单一阶段为中心

`scripts/spec/flow_guard.py` 目前保存一个 `phase`，可能取值为：

```text
solution
acceptance
implementation
quality_review
release_ready
```

脚本会根据冻结产物和验证事实计算期望阶段并检查一致性，已经不是完全靠人工切换。但“是否有未决问题”“是否需要同步文档”“哪些证据过期”等不同事实仍被压缩到一条主阶段链中。

`release_ready` 后可以再次运行 `spec verify`，所以它不是绝对不可重入；但当前没有明确的续改命令，不保留上一个已验证检查点历史，修改代码后先查询状态还会得到“不可信”的错误提示。这是“技术上能继续、使用上不自然”。

### 2.6 验证可靠但失效范围过大

当前验证有几项应保留的优点：

- `spec verify` 亲自执行命令，不接受手填的通过结论；
- 记录命令、退出码、耗时、时间和代码内容快照；
- 验证命令若改变可提交内容，则拒绝记录成功；
- 质量审查必须绑定同一代码快照；
- 人工验收文件变化后会使对应记录失效。

主要问题是 `repository_snapshot()` 对整个仓库所有可提交文件计算内容指纹。任何跟踪文件变化，即使和当前任务无关，也会使整份验证和质量审查失效。当前证据只能回答“这个仓库快照通过了什么命令”，不能回答“哪条结论由哪些文件和检查证明”。

### 2.7 共享质量底线已经存在

`.github/workflows/quality.yml` 会在面向 `dev`、`master` 的 PR 以及对应分支 push 时运行完整 `npm run check`。本次应保留“本地按影响范围提高速度、共享 CI 运行最终完整检查”的分工。

仓库文件只能证明 CI 工作流存在，不能证明远端分支保护已经把它设置成不可绕过的必需检查；这一点需要在准备发布时单独核实。

## 7. Change 与 Spec 的复杂度复核

2026-08-01 在拟定第一批 `change.md + state.yaml + init/status` 后重新核对，发现该方案会在迁移期增加第二套任务系统，与“先减轻复杂度和约束”的目标冲突。

### 7.1 当前 Spec 已经承担的职责

当前 Spec 不是一份普通方案文档，而是一组产物和状态机：

- schema v7；
- 5 个阶段；
- 2 条方案后续路线；
- `init`、`status`、`check`、`freeze`、`route`、`verify`、`review` 共 7 个命令；
- `solution.md`、按需 `acceptance.feature`、实施报告、人工验收和验证证据；
- 相关概念分布在 17 个项目文件约 119 处；
- `solution.template.md` 有 303 行、13 个章节；
- `flow_guard.py` 约 898 行，相关工具测试文件约 965 行。

候选 Change 又准备保存目标、非目标、完成标准、来源、风险、决定、进度、下一步、分支、基线和机器状态。这些内容与 Spec 大量重叠。

### 7.2 如果长期并存，会新增什么

| 重叠点 | Spec 已有内容 | 候选 Change 再增加的内容 |
| --- | --- | --- |
| 任务身份与来源 | KEY、`source_issue` | Change ID、source |
| 目标、范围、验收 | `solution.md` | `change.md` |
| 决定与风险 | `solution.md` 决策和风险章节 | `change.md` 决定和风险 |
| 进度与下一步 | phase、`spec status` | Change 状态、`change status` |
| 机器状态 | `.specs/<KEY>/state.yaml` | `changes/<ID>/state.yaml` |
| 验证与完成 | verification、quality review、`release_ready` | 后续 checkpoint、amend、close |

这会带来两套初始化和恢复入口、两套 schema、tracked 与 ignored 两种存储语义，以及目标、决定、进度、验证、收尾和外部来源至少六类同步问题。它不是合理终态。

### 7.3 四种关系的判断

| 关系 | 长期复杂度 | 判断 |
| --- | --- | --- |
| Change 与 Spec 长期并存 | 最高 | 不采用 |
| Change 只做 Spec 的索引或摘要 | 较高 | 仍需双写，不推荐 |
| Change 完全取代 Spec 顶层身份，Design 和 Acceptance 成为按需附件 | 较低 | 可以作为长期方向，但迁移成本较高 |
| 先直接简化现有 Spec，再判断是否值得演化或改名为 Change | 最低 | 在四种 Change／Spec 关系中成本最低；具体施工顺序后来由第 8 节修正 |

### 7.4 七维确认前的阶段性建议

这一阶段已经否决新增 `change.md`、第二个状态文件和第二套命令，但当时仍把“是否直接实现”和“是否需要记录”绑在一起，并考虑过普通临时便笺。D-023 确认七维判断后，这部分不再作为施工依据：记录需要由“持续性与协作”单独决定；会话内任务不建持久文件，需要持久记录的任务在 Spec 精简前暂用现有 Spec；不再增加临时便笺这一中间载体。

仍然有效的结论只有两点：同一任务不能长期维护 Change 与 Spec 两套平级状态；只有真实出现恢复或证据问题后，才按问题增加最小能力。

因此，原“第一批新增最小 Change 工具”的候选计划暂停，先确定如何对现有 Spec 做减法。

### 7.5 `.worktreeinclude` 对结论的影响

仓库已经在受 Git 管理的 `.worktreeinclude` 中列出 `.specs/*/`。它会在 Codex 创建本地托管 worktree 时，把匹配的 Git 忽略文件从本地检出目录复制进去；不会持续同步，也不会覆盖新 worktree 中已经存在的文件。

这意味着跨会话问题应拆开判断：

| 场景 | `.specs` 加入 `.worktreeinclude` 是否解决 | 说明 |
| --- | --- | --- |
| 同一 worktree 换会话 | 是 | 原本就可直接读取本地 Spec |
| 从本地检出目录创建新的 Codex 托管 worktree | 是 | 创建时复制，之后各自独立 |
| 已存在的两个 worktree 持续互相更新 | 否 | 没有自动双向同步 |
| 命令行创建的 Git worktree 或远程 worktree | 否 | 官方明确不适用 |
| 换设备或交给其他开发者 | 否 | Spec 内容仍被 Git 忽略 |

当前已经采用的方案是：

- 继续让 `.specs/*/` 被 Git 忽略；
- 在 `.worktreeinclude` 中使用与忽略范围一致的窄模式，让新建的本地 Codex 托管 worktree取得本机 Spec；
- 把这个行为称为“创建时复制”，不承诺同步或多人共享；
- 同一个 Spec 同一时间只由一个 worktree 作为写入方，复制后先核对 `solution.md`、实际附件、Git 差异和真实代码，不能直接复用旧验证结论；
- 不为本机恢复新增 `change.md`、状态文件或阶段命令。

还有一个容易混淆的边界：`.specs` 内容继续不会进入远端，但当前 `.worktreeinclude` 本身是已跟踪文件。若把规则提交，它会随分支进入远端；远端只看到“允许复制哪些本地路径”的规则，看不到本地 Spec 内容。若连规则也不能推送，只能把这行长期保留为本机未提交修改，维护成本和丢失风险反而更高，不是当前推荐。

依据：[Codex Worktrees 官方说明](https://learn.chatgpt.com/docs/environments/git-worktrees)。

## 8. 分流维度复核与第一步结论

进一步讨论发现，把任务只分成直接实施、计划实施、调查先行，再叠加常规或严格风险，仍然会把不同问题混在一起。旧 `flow-router` 也存在同类问题：只要五个直接实现条件有一项不满足就整套升级，导致跨文件、用户可见、普通契约变化和严格风险容易共同触发完整方案。

用户已经确认使用七个判断维度：

1. 准备程度；
2. 影响面与相互牵连；
3. 规则与状态关系；
4. 实现确定程度；
5. 验证难度；
6. 风险与可回退性；
7. 持续性与协作。

只有第 2 至第 5 项决定简单、中等或复杂，不使用数字总分。第 1 项只决定能否开工；第 6 项只决定常规或严格检查；第 7 项只决定会话内或持久记录。工作量、文件数、优先级和交付阶段都不属于复杂度。

这一拆分解决几个典型误判：

- 一行权限修复可以是简单但严格，不自动生成大型方案；
- 大量机械改名可以工作量大但规则简单，只展开影响和验证；
- 根因未知的低风险 Bug 先调查，不因未知就称为复杂开发；
- 状态很多但能完整单测时展开规则和测试矩阵，不创建无关人工验收；
- 行为简单但必须在真实浏览器验证时，只增加验证内容。

第一小步因此调整为先替换正式入口判断：保持现有三条端到端路径、Spec schema、`direct_build` 和 `acceptance_first` 不变，只让 `flow-router` 输出准备、复杂度、风险和记录，并按当前能力映射路径。复杂任务进入方案先行；符合条件的简单和中等任务可以直接实现；严格风险本身不升级路径；需要持久记录的任务在 Spec 精简前暂时保守走方案先行，但保持真实复杂度标签。
