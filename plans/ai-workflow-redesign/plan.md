# AI 工作流改造计划

## 1. 目标

把当前“一条直接实现条件不满足就进入整套方案”的工作流，逐步改成：

- 准备程度、任务复杂度、风险和记录需要分开判断；
- 简单和中等任务在信息充分、当前会话可完成时可以直接实施；
- 复杂任务只有一个 Spec，并且只展开实际命中的内容；
- 严格风险只增加对应确认、回退、验证和审阅，不自动制造大型方案；
- 跨会话和协作只决定是否需要记录，不改变复杂度；
- 本地日常验证尽量聚焦受影响范围，最终共享 CI 保持完整兜底；
- 开发者看到目标、主导复杂度、具体风险、记录方式、证据和下一步，不操作内部状态机。

七维模型见 [workflow-model.md](workflow-model.md)，确认决定见 `decisions.md` 的 D-023 和 D-024。

## 2. 本次明确不做

- 不修改 LinkCV 业务功能、数据库结构或产品行为。
- 不用简化流程削弱权限、数据、安全、迁移、不可逆操作和 Git 授权底线。
- 第一批不自动写 Issue、飞书或其他外部系统。
- 不新增 Change 目录、第二个 `state.yaml` 或另一套 init/status。
- 不一次性重写分流、Spec 模板、状态机、证据范围和外部同步。
- 不用数字总分决定任务规模。

## 3. 实施原则

1. 每个小步只改变一项可独立验证的能力。
2. 七个维度只保存必要事实和主导原因，不组合成几十种模式。
3. 文件数、代码行数、工时、优先级和风险不能单独代表复杂度。
4. 旧规则在对应新能力落地前继续有效；正式规则、消费 Skill 和测试在同一步同步。
5. 新产物必须对应真实需要，没有触发就不创建。
6. 局部证据无法可靠判断影响范围时扩大验证；PR 前仍运行完整质量入口。
7. 用户可以覆盖规划形式，但不能绕过权限、数据、安全、迁移和破坏性操作检查。

## 4. 分阶段计划

### 阶段 0：建立基线和改造护栏

目标：让整个改造可恢复、可审查，不让聊天成为唯一依据。

已完成：

- 建立独立改造分支和本临时施工目录；
- 核对当前三条路径、Spec 状态机、文档产物和 CI；
- 建立决定、进度、候选模型和验证记录；
- 识别 Change 与 Spec 双系统风险并暂停旧第一批计划。

### 阶段 1：替换一票升级的分流判断

状态：已于 2026-08-01 完成。

目标：先改“什么时候需要方案”，不同时改“方案内部怎么运行”。

实施内容：

- `flow-router` 改用七维判断；
- 只有影响面、规则关系、实现确定程度和验证难度决定简单、中等或复杂；
- 准备程度作为开工门，风险和记录独立输出；
- 简单和符合条件的中等任务允许直接实现；
- 复杂任务进入方案先行；严格风险本身不自动升级方案；
- 当前需要持久记录的任务，在 Spec 精简前保守进入方案先行，但复杂度标签保持真实；
- 保留直接实现、方案后直接施工、方案后契约验收三条端到端路径；
- 保留 schema v7、`direct_build`、`acceptance_first`、冻结、验证和审查行为；
- 增加最小契约检查，防止旧“一项不满足就方案先行”规则返回。

完成条件：

- 正式入口、`flow-router`、直接实施消费规则和 Skill 索引一致；
- 一行权限修复可以表达为“简单 + 严格”，不因风险标签自动生成完整方案；
- 已知模式下的前后端联动可以是中等并直接实现；
- 多角色状态机、在线迁移和分阶段兼容仍进入方案先行；
- 目标不清和根因未知分别进入澄清或调查，不伪装成复杂任务；
- 目标测试、`npm run check:ai` 和完整工作流工具测试通过；
- 独立审查没有发现新旧规则并存或下游记录缺口。

### 阶段 2：按七维结果给现有 Spec 做减法

目标：一个任务只有一个 Spec，主文档只展开实际命中的内容。

状态：进行中。第一小步已经完成 `solution.md` 完整章节库、按需选择和生成规则改造，并通过独立复核与完整质量检查；尚未处理实施报告、状态简化和验证证据范围。

已完成：

- 保留 `solution.md` 原有 13 个章节作为完整章节库，并保留独立的“验证与验收”；实际方案按需求挑选章节，不恢复逐章必填；
- 在精简主文档中保留一张表达核心链路的主要流程图，按任务选择业务流程、交互时序或迁移发布流程，不强制多图重复表达；
- 把业务流程作为主图的简短文字解释保留在核心章节，只写触发、关键步骤、成功结果和关键失败结果；
- 把状态机和数据模型设为高优先条件章节：命中状态关系时完整状态边界，读写持久数据时保留数据模型，改 schema 或迁移时写完整模型、字段级变更、DDL、兼容和回退；
- 在“文件结构与实现方案”中保留目录树和文件职责作为按需子块，并固定使用一张代码施工表承接真实路径和步骤；
- 用可观察结果和业务规则编号贯通真实文件、实施步骤与验证证据；
- 把项目入口、Spec 说明、Acceptance、实施、测试、人工验收、审查和完成度审计改为按语义内容读取，不再依赖 `1.4`、`9.3` 等固定节号；
- 把模板检查改为同时保护完整章节库、需求描述、状态机、数据模型、代码施工契约和按需选择能力，并增加回归测试。

后续方向：

- 影响面复杂时展开消费方、兼容和实施顺序；
- 规则关系复杂时才展开 Acceptance 或测试矩阵；
- 实现存在关键未知时才展开技术取舍、试验、迁移和回退；
- 验证复杂且自动化不足时才创建人工验收；
- 严格风险写入同一主文档的对应章节，不新增风险文件；
- Tasks、Design 和 Decisions 优先作为主文档章节，确需独立执行或评审时才拆文件；
- 重新评估 `implementation_report.md`，能由主 Spec、最终摘要或 PR 承担的内容不再重复生成。

完成条件：

- 小型常规任务为零任务文档；
- 中等任务可以是零或一份精简主文档；
- 大型任务默认只有一份主文档，Acceptance 和人工验收按需增加；
- 小型严格任务不填写与风险无关的大型模板；
- 当前文档内容、模板、Skill 和检查脚本保持一致。

### 阶段 3：简化状态、恢复和续改

目标：在唯一 Spec 内减少阶段和机器状态负担，并支持自然恢复。

计划方向：

- 实测 `.specs/*/` 加入 `.worktreeinclude` 的本机创建时复制；
- 决定 `state.yaml` 最终只保留哪些机器事实；
- 评估删除或降级 5 个 phase、freeze/refreeze、文档哈希、历史 schema 迁移、本地 `quality_review` 和 `release_ready`；
- 验证与审查继续真实执行，但不一定保存为用户要操作的阶段；
- 只有真实出现续改证据覆盖问题后才引入最小 checkpoint 或 amend；
- 不建设 Change 与 Spec 双轨，不建立后台 worktree 同步。

完成条件：

- 新会话能恢复目标、有效决定、真实差异和下一步；
- 同一个任务只有一个有效状态源；
- `.specs` 内容仍被 Git 忽略，复制行为明确标注为一次快照而非同步；
- 旧 Spec 有明确读取、转换或退出方式；
- 开发者不需要手填哈希、阶段或退出码。

### 阶段 4：按影响范围保存和刷新证据

目标：减少无关重跑，同时避免错误复用旧结果。

计划方向：

- 每条关键证据说明结论、覆盖范围、代码版本、命令、结果和未覆盖区域；
- 第一版使用保守的目录、模块和契约规则，不建设完整依赖图；
- 前端、后端、扩展、公共契约、迁移、构建和纯文档分别定义默认刷新范围；
- 无法判断时扩大检查；PR、合入和发布前继续运行完整 `npm run check`；
- 审查支持检查点差异，最终仍检查完整交付范围。

### 阶段 5：检查点收敛和可选外部同步

目标：内部模型稳定后，再处理 Issue、飞书和正式设计之间的同步。

计划方向：

- 定义交接、评审、PR 和高风险决定生效时的收敛；
- 先生成待同步差异给人审阅，不直接自动写远端；
- 只有授权、稳定 ID、重复执行安全和失败恢复明确时才启用外部写入；
- 外部系统不可用时不丢失本地确认结果，也不伪装同步成功。

### 阶段 6：正式收口和删除临时记录

目标：最终仓库只保留已经生效且互相一致的规则和工具。

工作项：

- 删除废弃 Skill、模板、字段、命令和重复说明；
- 同步项目入口、Skill 索引、Spec 说明和真实脚本帮助；
- 运行完整检查并完成独立质量审查；
- 删除项目入口临时指针和本目录；
- 在 PR 中说明自举例外、迁移方式、验证结果和遗留风险。

## 5. 衡量改造是否有效

试点记录：

1. 接收任务到第一次有效代码修改所需时间；
2. 新会话恢复到可以继续实施所需时间；
3. 每项任务实际生成和维护的文档数量；
4. 同一个决定要求用户重复确认的次数；
5. 局部修改触发的无关测试和重复审查数量；
6. 分流到直接实现后又因遗漏影响面返工的次数；
7. 误实现、漏验证和交付缺陷是否增加。

步骤减少但缺陷或误判增加时，应调整具体维度信号和验证规则，而不是继续追求更少步骤。
