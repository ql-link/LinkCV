# AI 工作流改造计划

## 1. 目标

把当前“一条直接实现条件不满足就进入整套方案”的工作流，逐步改成：

- 准备程度、任务复杂度、风险和记录需要分开判断；
- 简单和中等任务在信息充分、影响有界时可以直接实施；
- 复杂任务只有一个 Spec，并且只展开实际命中的内容；
- 严格风险只增加对应确认、回退、验证和审阅，不自动制造大型方案；
- 跨会话和协作只决定如何保留必要内容，不改变复杂度或交付路径；
- 方案任务以 `solution.md` 为中心，AI 根据当前 Spec、Git、代码和实际验证判断下一步，不操作机器阶段；
- 本地日常验证尽量聚焦受影响范围，最终共享 CI 保持完整兜底；
- 开发者看到目标、主导复杂度、具体风险、记录方式、证据和下一步，不操作内部状态机。

七维模型见 [workflow-model.md](workflow-model.md)，确认决定见 `decisions.md` 的 D-023、D-034～D-036。

## 2. 本次明确不做

- 不修改 LinkCV 业务功能、数据库结构或产品行为。
- 不用简化流程削弱权限、数据、安全、迁移、不可逆操作和 Git 授权底线。
- 第一批不自动写 Issue、飞书或其他外部系统。
- 不新增 Change 目录、状态文件、确认总开关、检查点或另一套 init/status。
- 不建设验证缓存、证据失效图或工作树持续同步。
- 不用数字总分决定任务规模。

## 3. 实施原则

1. 每个小步只改变一项可独立验证的能力。
2. 七个维度只保存必要事实和主导原因，不组合成几十种模式。
3. 文件数、代码行数、工时、优先级和风险不能单独代表复杂度。
4. 正式规则、消费 Skill 和测试在同一步同步；已经删除的状态层不保留兼容分支。
5. 新产物必须对应真实需要，没有触发就不创建。
6. 局部证据无法可靠判断影响范围时扩大验证；PR 前仍运行完整质量入口。
7. 用户可以覆盖规划形式，但不能绕过权限、数据、安全、迁移和破坏性操作检查。

## 4. 分阶段计划

### 阶段 0：建立基线和改造护栏

目标：让整个改造可恢复、可审查，不让聊天成为唯一依据。

已完成：

- 建立独立改造分支和本临时施工目录；
- 核对当前三条路径、Spec 状态机、文档产物和 CI；
- 建立决定、进度、候选模型和验证记录；
- 识别 Change 与 Spec 双系统风险并暂停旧第一批计划。

### 阶段 1：替换一票升级的分流判断

状态：已于 2026-08-01 完成。

目标：先改“什么时候需要方案”，不同时改“方案内部怎么运行”。

实施内容：

- `flow-router` 改用七维判断；
- 只有影响面、规则关系、实现确定程度和验证难度决定简单、中等或复杂；
- 准备程度作为开工门，风险和记录独立输出；
- 简单和符合条件的中等任务允许直接实现；
- 复杂任务进入方案先行；严格风险本身不自动升级方案；
- 当前需要持久记录的任务，在 Spec 精简前保守进入方案先行，但复杂度标签保持真实；
- 保留直接实现、方案后直接施工、方案后契约验收三条端到端路径；
- 保留 schema v7、`direct_build`、`acceptance_first`、冻结、验证和审查行为；
- 增加最小契约检查，防止旧“一项不满足就方案先行”规则返回。

完成条件：

- 正式入口、`flow-router`、直接实施消费规则和 Skill 索引一致；
- 一行权限修复可以表达为“简单 + 严格”，不因风险标签自动生成完整方案；
- 已知模式下的前后端联动可以是中等并直接实现；
- 多角色状态机、在线迁移和分阶段兼容仍进入方案先行；
- 目标不清和根因未知分别进入澄清或调查，不伪装成复杂任务；
- 目标测试、`npm run check:ai` 和完整工作流工具测试通过；
- 独立审查没有发现新旧规则并存或下游记录缺口。

### 阶段 2：按七维结果给现有 Spec 做减法

目标：一个任务只有一个 Spec，主文档只展开实际命中的内容。

状态：已完成。第一小步完成 `solution.md` 完整章节库和按需选择；第二小步完成来源、分流展示、确认次数、实施报告和任务验证五项减法。

已完成：

- 保留 `solution.md` 原有 13 个章节作为完整章节库，并保留独立的“验证与验收”；实际方案按需求挑选章节，不恢复逐章必填；
- 在精简主文档中保留一张表达核心链路的主要流程图，按任务选择业务流程、交互时序或迁移发布流程，不强制多图重复表达；
- 把业务流程作为主图的简短文字解释保留在核心章节，只写触发、关键步骤、成功结果和关键失败结果；
- 把状态机和数据模型设为高优先条件章节：命中状态关系时完整状态边界，读写持久数据时保留数据模型，改 schema 或迁移时写完整模型、字段级变更、DDL、兼容和回退；
- 在“文件结构与实现方案”中保留目录树和文件职责作为按需子块，并固定使用一张代码施工表承接真实路径和步骤；
- 用可观察结果和业务规则编号贯通真实文件、实施步骤与验证证据；
- 把项目入口、Spec 说明、Acceptance、实施、测试、人工验收、审查和完成度审计改为按语义内容读取，不再依赖 `1.4`、`9.3` 等固定节号；
- 把模板检查改为同时保护完整章节库、需求描述、状态机、数据模型、代码施工契约和按需选择能力，并增加回归测试。
- 把 Issue 从开工许可证降为可选追踪信息；当前请求、飞书和用户指定材料都可以作为有效来源，无 Issue 使用本地任务标识；
- 七维始终在内部完整判断，普通任务对外只展示路径、一个主导原因和额外检查，只有准备不足、严格风险、持久记录或用户主动询问时展开；
- 没有真实待决选择的短方案整份只确认一次，已选后续路径和模块规划后的继续授权直接复用；
- 把 `implementation_report.md` 缩成三类增量信息：已允许偏差、已接受限制、跨会话遗留风险或下一步；任务类型和严格风险本身不触发；
- 任务完成运行范围与风险匹配的检查，Spec 可记录多条选定命令；PR 前才固定运行完整 `npm run check`，共享 CI 保持完整，迁移保留专项检查。

持续适用的按需规则：

- 影响面复杂时展开消费方、兼容和实施顺序；
- 规则关系复杂时才展开 Acceptance 或测试矩阵；
- 实现存在关键未知时才展开技术取舍、试验、迁移和回退；
- 验证复杂且自动化不足时才创建人工验收；
- 严格风险写入同一主文档的对应章节，不新增风险文件；
- Tasks、Design 和 Decisions 优先作为主文档章节，确需独立执行或评审时才拆文件；
- 实施报告不承担主 Spec、正常实现摘要、验证记录、人工验收或 PR 已经承担的内容。

完成条件：

- 小型常规任务为零任务文档；
- 中等任务可以是零或一份精简主文档；
- 大型任务默认只有一份主文档，Acceptance 和人工验收按需增加；
- 小型严格任务不填写与风险无关的大型模板；
- 当前文档内容、模板、Skill 和检查脚本保持一致。

### 阶段 3：删除机器状态，改为自然恢复

状态：已完成实施和完整验证，独立复核发现的问题已经修正。

目标：彻底移除需要 AI 和开发者维护的阶段状态，同时让方案任务仍能从唯一 Spec 自然恢复。

已实施：

- 删除 `state.yaml` 的创建、读取、迁移和校验工具，并删除 `npm run spec` 入口；
- 删除 phase、freeze/refreeze、文档哈希、验证快照、本地质量阶段和完成状态；
- 不迁移旧任务，不保留兼容读取，也不创建替代状态文件；
- 方案任务把 `solution.md` 作为唯一中心，按需读取 Acceptance、人工验收和实施报告；
- AI 根据当前请求、Spec、Git 差异、真实代码和当前验证判断继续确认、实现、验证、审查或收尾；
- `.worktreeinclude` 加入 `.specs/*/`，明确它只是新建本地 Codex 工作树时的一次快照；
- 验证和审查仍真实执行，需要当前结论时重新运行，不继承旧会话缓存结果；
- 增加无状态契约和删除变异测试，防止重新引入阶段脚本或换皮状态字段。

完成条件：

- 新会话能恢复目标、有效决定、真实差异和下一步；
- 方案任务只有一个中心文档 `solution.md`，不出现平级进度或状态文档；
- `.specs` 内容仍被 Git 忽略，复制行为明确标注为一次快照而非同步；
- 当前 Spec 可直接读取；没有旧任务迁移路径；
- 开发者不需要手填哈希、阶段或退出码。

### 阶段 4：直接验证当前代码

状态：已并入阶段 3，不再建设独立证据系统。

已确认边界：

- 任务完成时运行与当前改动范围和风险匹配的检查；
- 无法可靠判断影响范围时扩大检查；
- 旧会话的测试描述只作历史信息，不能直接成为当前通过结论；
- 准备 PR 时对当前可提交内容运行完整 `npm run check`；
- 数据库迁移、权限、契约和真实浏览器等专项验证继续按实际风险触发；
- 不保存机器证据快照，不计算局部失效，不建立检查点差异状态。

### 阶段 5：确定外部文档边界

状态：已完成；不建设持续外部同步，只保留一次性交付收尾。

已确认边界：

- 飞书只用于方案形成前的初步模块设计和协作输入；
- Issue 正文只用于任务入口、边界和追踪，不随 Spec 与代码反复改写；
- `solution.md` 确认后成为方案任务的当前实施与验收依据；
- 后续设计变化修订原 `solution.md`，记录被替代的来源结论并重新确认受影响决定；
- 不把方案差异回写飞书或 Issue 正文，也不让它们成为第二个实施真相源；
- PR 基于最终差异说明实际交付和重要来源差异；创建 PR 后向主要来源 Issue 只发布一条交付评论，不发送过程同步；
- 只有用户以后明确要求开展新的初步模块规划时，才按 `module-planning` 单独写入飞书。

### 阶段 6：正式收口和删除临时记录

目标：最终仓库只保留已经生效且互相一致的规则和工具。

工作项：

- 删除废弃模板、字段、命令和重复说明；
- 同步项目入口、Skill 索引、Spec 说明和真实脚本帮助；
- 运行完整检查并完成独立质量审查；
- 删除项目入口临时指针和本目录；
- 在 PR 中说明自举例外、无旧任务迁移、验证结果和遗留风险。

## 5. 衡量改造是否有效

试点记录：

1. 接收任务到第一次有效代码修改所需时间；
2. 新会话恢复到可以继续实施所需时间；
3. 每项任务实际生成和维护的文档数量；
4. 同一个决定要求用户重复确认的次数；
5. 局部修改触发的无关测试和重复审查数量；
6. 分流到直接实现后又因遗漏影响面返工的次数；
7. 误实现、漏验证和交付缺陷是否增加。

步骤减少但缺陷或误判增加时，应调整具体维度信号和验证规则，而不是继续追求更少步骤。
