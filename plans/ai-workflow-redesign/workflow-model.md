# 目标工作流模型

> 状态：阶段 1 的七维判断和阶段 2 的 Spec 减法已经落地：Issue 可选、分流默认三行、确认按真实决策量、实施报告只留三类增量、任务验证与 PR 全量检查分离。状态简化、跨 worktree 恢复、证据局部失效、续改和外部收尾状态仍是候选，只有对应代码、测试和正式规则落地后才算生效。

## 1. 核心结论

任务不能只用“直接实施、计划实施、调查先行”或“风险高低”概括。目标模型先做七个互相分开的判断：

| 编号 | 维度 | 回答的问题 | 是否决定复杂度 |
| --- | --- | --- | --- |
| 1 | 准备程度 | 现在是否已经知道要做什么、不能做什么、什么算完成 | 否，是开工门槛 |
| 2 | 影响面与相互牵连 | 涉及多少职责边界、消费方和实施顺序 | 是 |
| 3 | 规则与状态关系 | 角色、状态、失败和副作用是否相互影响 | 是 |
| 4 | 实现确定程度 | 仓库是否已有可靠做法，是否存在关键技术未知 | 是 |
| 5 | 验证难度 | 需要什么环境和证据才能证明正确 | 是 |
| 6 | 风险与可回退性 | 做错后的损失多大，能否安全恢复 | 否，独立决定检查强度 |
| 7 | 持续性与协作 | 是否需要跨会话、交接、并行或多个检查点 | 否，独立决定记录需要 |

七个维度始终在内部完整判断。普通任务默认只向用户表达：

```text
路径：直接实现 | 方案先行 | 模块规划 | 暂不进入开发路径
原因：一个决定当前路径的主导事实
额外检查：无，或本次真实增加的检查
```

准备不足、风险严格、需要持久记录或用户主动要求解释时，才展开准备、复杂度、风险、记录及四项复杂度依据。展示变短不改变内部判断；路径仍只是七维结论在当前仓库能力下的后续动作，不反过来定义任务本身。

需求来源也不再绑定 Issue。用户当前请求、可读取的 Issue、飞书文档和用户明确指定的其他材料都可以定义任务；有 Issue 时完整读取并作为可选追踪信息，没有 Issue 时使用本地任务标识，不阻止分流、Spec、实现或 PR。

## 2. 七个维度的边界

### 2.1 准备程度

- `可实施`：已经能确认这是一个边界清楚的开发任务并选择下一条路径；直接实现还要求目标、明确不做、修改授权和可观察完成结果足够清楚，方案先行可以保留已识别的内容问题到方案阶段确认；
- `需澄清`：缺少的选择使任务目标本身无法成立，或会改变是否进入开发、进入哪条路径；
- `需调查`：目标清楚，但根因、真实影响面或可行性需要先取得只读证据。

目标含糊不等于复杂。准备不足时先澄清或调查，暂不为实现定级。整个模块目标或商业前提尚未成形时转模块规划；单个具体选择不需要升级成模块规划。任务已经明确属于方案先行时，方案内部的业务规则和技术取舍直接列入未确认项并交给 `solution-generator`，不由分流器提前主持讨论。

### 2.2 影响面与相互牵连

看职责边界、真实消费方、兼容和先后顺序，不看文件数量：

- 局部边界、单一消费方、一次修改和直接回退：简单信号；
- 多个已知模块同步、消费方已找全、可以一次实施和验证：中等信号；
- 多个独立应用或外部消费方、兼容窗口、分步迁移、部署顺序或依赖交付单元：复杂信号。

五百个文件的机械改名可以只是中等；前后端同时改一个已知字段也不再自动等于复杂。

### 2.3 规则与状态关系

看规则是否相互作用，不机械计算场景数量：

- 一个主要结果、少量独立校验：简单信号；
- 几条明确分支，可用短清单表达，失败结果相互独立：中等信号；
- 多角色、多状态、并发、重试、恢复、跨端一致性或失败副作用相互影响：复杂信号。

这一维决定是否需要展开 Acceptance 或测试矩阵。

### 2.4 实现确定程度

看仓库内是否已有可靠路径：

- 沿用已核实的实现和测试模式：简单信号；
- 一个有界、可逆的选择，不引入新架构或长期兼容负担：中等信号；
- 新架构、新依赖、外部服务、技术试验、数据迁移或复杂回退仍有关键未知：复杂信号。

“技术难”不靠主观感觉；必须指出缺少的成熟模式、未知事实或真实取舍。

### 2.5 验证难度

看如何证明，而不是看是否需要测试：

- 邻近自动化或一次明确观察即可覆盖：简单信号；
- 多个测试层或一次稳定的浏览器、设备检查：中等信号；
- 多个真实服务、生产式数据、长期观察、难复现并发或外部系统协作：复杂信号。

行为复杂但能完整单测时，不因此创建人工验收；行为简单但必须真实浏览器确认时，只增加对应人工步骤。

### 2.6 风险与可回退性

风险只分两档：

- `常规`：局部、可逆，不涉及关键权限、数据和外部承诺；
- `严格`：权限、安全、隐私、凭据、数据迁移或丢失、公开接口已有消费者、生产切换、计费或不可逆操作。

严格只增加命中的确认、失败结果、回退或不可逆说明、验证和责任审阅，不自动生成完整方案。一行权限修复可以是“简单 + 严格”；在线数据迁移可以是“复杂 + 严格”。

### 2.7 持续性与协作

- `会话内`：预计当前会话完成，一个协调者推进，来源、Git 差异和最终摘要足以恢复；
- `持久记录`：预计跨会话、正式交接、并行协作、多个检查点，或用户明确要求保留当前计划。

它不改变任务复杂度。简单任务也可能因为要交接而需要记录，复杂任务也不能因此再创建第二套 Change。

## 3. 复杂度与当前路径映射

### 3.1 不做总分

只使用第 2 至第 5 维：

- `简单`：四项全部符合简单信号；
- `复杂`：任一项命中明确复杂信号；
- `中等`：不满足全部简单，但没有复杂信号。

每次只写一个主导原因。不能把同一个“跨模块”事实在影响面、实现和验证三处重复累计。

### 3.2 当前过渡映射

现有三条端到端路径保持不变：直接实现、方案后直接施工、方案后契约验收。

当前 `flow-router` 按以下顺序处理：

1. 整个模块目标或商业前提未成形，或用户明确要求形成多人协作文档：模块规划；
2. 其他准备不足：先澄清或调查，不进入开发路径；
3. 复杂任务：方案先行；
4. 当前确需持久记录：Spec 精简完成前保守走方案先行，但不改变复杂度标签；
5. 其他简单或中等任务：允许直接实现，风险可以是常规或严格；
6. 方案冻结时仍由 `solution-generator` 决定是否额外产出 Acceptance。

中等任务直接实施必须满足：目标与完成结果已收敛；消费方已找全；实现有界可逆；无需分阶段兼容或迁移；验收可用短清单表达；当前会话能完成。

数据库 schema 或数据迁移自动分流时仍默认方案先行，因为通常会同时命中存量数据、兼容、顺序和回退，而不是因为“数据库”标签本身代表复杂。

## 4. 维度如何触发产物

以下关系中，`solution.md` 的完整章节库与按需选择规则已经落地；Acceptance、人工验收和后续状态简化仍按各阶段推进：

| 判断结果 | 需要表达的内容 | 是否必须拆文件 |
| --- | --- | --- |
| 准备不足 | 一个阻塞问题或调查结论 | 否 |
| 影响面复杂 | 消费方、兼容和实施顺序 | 优先放主 Spec |
| 规则关系复杂 | 可观察业务规则和测试矩阵 | 需要独立确认时才拆 Acceptance |
| 实现存在关键未知 | 技术取舍、试验结论、迁移和回退 | 优先放主 Spec |
| 验证复杂 | 验证环境、证据和未覆盖区域 | 需要人工执行时才拆人工验收 |
| 风险严格 | 风险原因、关键确认、失败结果、回退或不可逆点 | 不单独创建风险文件 |
| 持久记录 | 当前目标、进度、有效决定和下一步 | 沿用唯一 Spec，不创建 Change |

直接实现的会话级任务不创建 Spec。复杂或需要持久记录的任务只有一个 Spec；Tasks、Design 和 Decisions 优先作为 `solution.md` 的按需章节，只有确实需要独立执行或评审时才拆文件。

验证证据和收尾摘要是必须存在的结果，不等于必须新增 Markdown 文件。长期 `docs/` 只由已经实现的架构、接口、数据、配置或部署事实触发；PR、CI 和发布状态属于交付生命周期，也不参与复杂度判断。

### 4.1 已落地的完整章节库与重点章节边界

用户审阅模拟方案后已经确认：精简 `solution.md` 仍须保留一张表达本次核心链路的主要流程图。这里的“主要”不是固定画用户操作图，而是按任务选择最能说明先后和分支的一种图：有用户行为时画业务流程，多个参与方往返时画时序，迁移或发布任务则画迁移发布流程。默认只保留一张主图；只有另一张图表达的是不同关系并且会影响实施决定时才增加，避免业务流程图、时序图和架构图重复描述同一条链路。

用户随后确认并已经落地以下边界：

- **模板保留完整章节库**：原有 13 个章名继续存在，并保留独立的“验证与验收”；实际方案按触发条件挑选章节，未命中的整章删除，下游不依赖节号。
- **业务流程作为核心内容保留**：主图下面只补充触发条件、关键步骤、成功结果和关键失败结果。图与文字合在同一节，不恢复当前模板中逐节点重复转述的固定写法；纯技术任务把这一节改成“变更流程”，不虚构用户故事。
- **状态机和数据模型是高优先条件章节**：命中生命周期、状态关系、并发、重试或恢复时必须完整保留状态机；只要读写持久数据就保留数据模型，只使用现有实体时简写，新增或修改 schema、回填或迁移数据时完整展开关系、字段级变更、约束、定稿 DDL、存量处理、发布顺序和回退。
- **架构图继续按需**：主流程图不能替代职责边界说明，但只有新增服务、改变模块职责、引入外部系统或出现分阶段兼容时才需要单独架构图。

这样完整保留模板能力，同时不让未命中状态、数据或架构的任务填写空章节，也不为同一条流程维护多份图。

### 4.2 已落地的交互、报告和验证减法

- 没有真实待决选择的短方案整份只确认一次；长方案或存在独立决定时才分段。用户已经选择直接施工或契约验收时，冻结阶段直接复用。
- 模块规划完成并读回一致后，原请求已经授权继续时直接进入已指定路径；没有指定路径时才重新分流，不要求用户再发一次“继续”。
- `implementation_report.md` 只在存在已允许的实际方案偏差、已接受限制或必须跨会话交接的遗留风险或下一步时创建，只保留相应增量章节。数据库、跨端、权限、部署、多模块和严格风险本身都不触发。
- 任务完成运行与改动范围和风险匹配的一条或多条命令，Spec 记录真实命令和代码快照；准备创建 PR 时才固定执行完整 `npm run check`，共享 CI 仍执行完整入口。数据库迁移另外保留空库、升级、降级、往返和目标 MySQL 等专项检查。
- Spec 的 `release_ready` 只表示当前代码快照完成任务范围验证和质量审查，不代表 PR 全量检查、远端 CI、审核或发布已经完成。

## 5. 典型情况

| 情况 | 准备 | 复杂度 | 风险 | 记录 | 当前动作 |
| --- | --- | --- | --- | --- | --- |
| 清楚的局部样式修正 | 可实施 | 简单 | 常规 | 会话内 | 直接实现 |
| 一行资源归属修复，语义已有测试约束 | 可实施 | 简单 | 严格 | 会话内 | 直接实现并增加权限验证 |
| 已知模式下的前后端字段联动 | 可实施 | 中等 | 常规 | 会话内 | 可以直接实现 |
| 大量机械改名 | 可实施 | 中等，主因是影响面 | 常规 | 视持续时间 | 影响清单和范围验证，不写大型设计 |
| 多角色状态机 | 可实施 | 复杂，主因是规则关系 | 按真实后果 | 持久记录 | 方案先行，通常需要 Acceptance |
| 在线数据迁移和兼容发布 | 可实施 | 复杂，主因是实施顺序 | 严格 | 持久记录 | 方案先行，展开迁移和回退 |
| 低风险 Bug 但根因未知 | 需调查 | 暂不判定 | 暂按常规 | 会话内 | 只读调查后重新分流 |

## 6. 人的职责

### 开始时

人负责说明问题、明确不能触碰的边界、提供可观察结果，并授权外部写入、破坏性操作和真实环境操作。清楚的指令本身可以构成共识，不为了流程重复确认。

AI 在分流阶段负责核实仓库事实、完成七维判断，并只提出会改变任务成立、路径或严格检查的关键问题；进入方案阶段后，`solution-generator` 只确认真实存在的业务和技术选择，短且无待决选择时整份确认一次，不按章节制造重复确认。

### 实施中

人只处理无法由事实决定、且会改变目标、用户行为、权限、数据、安全、兼容、成本或不可逆结果的选择。普通代码组织、测试落点和内部记录由 AI 处理。

### 收尾时

人审阅实现摘要、风险和未覆盖区域；完成确实需要人的业务、视觉或设备验收；审核 PR 并决定是否合入或发布。人不手填哈希、退出码、阶段或证据新鲜度。

## 7. 新建、继续与续改

| 动作 | 判断标准 | 系统行为 |
| --- | --- | --- |
| 新建 | 新的独立目标或交付边界 | 建立新的工作对象和来源基线 |
| 继续 | 目标未变，仍有未完成内容 | 恢复有效决定、差异和证据，不重做全部材料 |
| 续改 | 同一分支或 PR 中，已验证版本继续调整同一目标 | 只让受影响证据失效，形成新检查点 |
| 新一轮变更 | 已合入、发布，或形成独立验收和发布时间 | 建立关联的新任务，不混用旧状态 |

这部分仍是候选，尚未实现 `amend` 或检查点历史。

## 8. 统一收尾骨架

所有实际改动都执行以下逻辑步骤，维度只决定哪些内容要展开：

1. 核对目标和完成结果；
2. 核对差异范围和无关修改；
3. 收敛当前有效决定；
4. 同步已经实现的长期事实；
5. 运行影响范围和风险对应的任务验证；
6. 审查正确性、契约、权限、数据、回退和测试质量；
7. 形成与确定代码版本对应的验证结论；
8. 根据用户授权决定本地交付、交接、PR 或发布；准备 PR 时另跑完整本地检查；
9. 删除实验、重复记录和无效临时材料。

只读任务和调查不伪造代码验证结果，以事实、剩余未知和下一步收尾。

## 9. 不混淆四种完成

| 结果 | 真正表示什么 |
| --- | --- |
| 当前代码已验证 | 当前代码版本有范围匹配的验证和必要审查 |
| 可以提 PR | 提交范围正确，完整本地检查和必要验收完成 |
| 远端检查和审核完成 | PR 对应提交的 CI 与要求的审核实际通过 |
| 已发布 | 确定构件进入目标环境，迁移、健康检查、观察和回退有结果 |

前一步不能自动代表后一步。任务范围验证与“可以提 PR”的边界已经落地；`release_ready` 仍沿用旧名称，但正式规则已明确它只代表前者。远端检查、审核和发布是否进入本地状态模型，留到阶段 3 决定。

## 10. 尚需确认

- 持久记录是否正式采用 `.specs + .worktreeinclude`，以及完成后的删除或归档规则；
- 当前五阶段、冻结、文档哈希、质量审查和 `release_ready` 哪些保留；
- 已记录的验证证据如何按影响范围局部失效和复用；
- 续改检查点的最小结构；
- 外部 Issue、飞书是否以及何时允许自动写入；
- 远端 CI、审核和发布是否需要进入本地工具状态。
