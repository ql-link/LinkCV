# 跨会话与跨工作树记录（当前建议）

> 状态：候选方案，尚未成为现行项目规则。当前优先利用现有 `.specs` 和 `.worktreeinclude`，不再为本机恢复新增 Change 目录、第二个状态文件或新命令。

## 1. 先说结论

“跨会话”不是一个问题，而是四种不同范围：

| 场景 | 当前最小做法 |
| --- | --- |
| 同一 worktree 换聊天会话 | 直接读取本地 Spec、Git 差异和当前代码 |
| 从本地检出目录创建新的 Codex 托管 worktree | 用 `.worktreeinclude` 在创建时复制被忽略的 `.specs` |
| 已存在的多个 worktree 之间持续更新 | 不自动同步；同一个 Spec 只保留一个写入方 |
| 换设备、交给其他人或远端协作 | 依赖 Issue、提交、PR 和必要的长期文档，不靠本地 Spec |

当前首要目标是降低本地开发工作流复杂度。是否需要记录由七维判断中的“持续性与协作”单独决定，不由任务大小、风险或直接／方案路径代替。第一批只解决前两种高频场景，不为了低频的跨设备共享建设第二套任务系统。

## 2. `.worktreeinclude` 能做什么

当前仓库事实：

- `.gitignore` 已忽略 `.specs/*/`；
- `.specs/README.md` 仍是正常跟踪的项目说明；
- 仓库根目录已有受 Git 管理的 `.worktreeinclude`，目前只列出本地环境文件和 IDE 运行配置；
- `.specs/*/` 尚未列入其中。

Codex 官方说明：在仓库根目录的 `.worktreeinclude` 中列出被 Git 忽略的路径或 `.gitignore` 风格模式后，Codex 创建本地托管 worktree 时会复制匹配的本地文件。它只处理匹配的忽略文件，跳过源符号链接，也不覆盖新检出中已经存在的文件。

对本项目，候选规则应与现有忽略范围保持一致：

```text
# Local Spec snapshots copied into new Codex-managed worktrees.
.specs/*/
```

这是一条待实测的候选配置，不在方案确认前直接写入正式文件。

依据：[Codex Worktrees 官方说明](https://learn.chatgpt.com/docs/environments/git-worktrees)。

## 3. 它不能做什么

`.worktreeinclude` 不是同步工具：

- 只在 Codex 创建本地托管 worktree 时复制；
- 不会把之后的修改自动同步回本地检出目录；
- 不会让两个已经存在的 worktree 实时保持一致；
- 不适用于命令行自行创建的 Git worktree；
- 不适用于远程 worktree；
- 不解决换设备或其他开发者读取本地 Spec 的问题。

因此不能把它描述成“Spec 全局继承”或“跨环境同步”。准确说法是“新建本地 Codex 托管 worktree 时取得一份本机快照”。

## 4. 推荐的最小规则

1. 判断为 `持久记录` 的任务只维护一份现有 Spec，不再建立 `change.md`；任务可以简单、中等或复杂。
2. 判断为 `会话内` 的任务不为了规模或风险标签单独创建恢复文档；严格风险仍须在当前交付摘要和适用的 PR 中说明。
3. 跨会话、正式交接、并行协作、多个检查点或用户明确要求保留时使用 Spec；Spec 自身应先做减法，而不是再套一层记录。
4. `.specs/*/` 继续被 Git 忽略，本地任务内容不进入提交和远端。
5. `.worktreeinclude` 只负责新建 Codex 托管 worktree 的初始复制。
6. 同一个 Spec 不在多个 worktree 中并行编辑；若复制后两边都改了，没有 Git 冲突保护，只能人工判断哪份有效。
7. 复制到新 worktree 后，先检查分支、`git status`、真实代码和 `npm run spec -- status <KEY>`。旧验证如果不匹配当前代码，就必须失效，不能因为文件被复制就继续宣称通过。
8. 已存在的 worktree 需要继续同一任务时，优先回到原 worktree；确实要迁移再做一次明确的人工交接，不建设后台同步器。

## 5. “不推送远端”的准确边界

`.specs/*/` 已被 Git 忽略，所以里面的方案、状态和验收文件不会因为加入 `.worktreeinclude` 而进入提交。

但 `.worktreeinclude` 当前是受 Git 管理的文件。若提交新增规则，远端会看到这条配置，但不会看到任何本地 Spec 内容。这通常是合理的：团队共享同一条本地工作树准备规则，任务数据仍留在本机。

如果要求连这条规则也绝不进入远端，只能长期保留一个本机未提交修改，或者另找 Codex 支持的本机配置入口。前者容易在切分支、更新文件或清理工作区时丢失，也会让工作区长期不干净，当前不推荐。

## 6. 什么时候才需要 Git 管理的 Change

只有出现以下真实需求，才重新讨论统一 Change：

- 同一任务必须跨设备继续；
- 多名开发者需要共同维护当前计划；
- 本地 Spec 经常因工作树清理而丢失；
- Issue、PR 和代码仍不足以完成正式交接；
- 团队明确需要审计开发过程，而不只是最终代码和 PR。

即使到那时，也不能让 Change 与 Spec 作为两套平级状态长期并存。合理终态仍然是只有一个任务身份，方案、验收和人工验收只是按需附件。

## 7. 当前改造任务的例外

本次 `plans/ai-workflow-redesign/` 受 Git 管理，是因为它正在改造工作流本身、周期长，并且需要保留分支内的设计与施工依据。它不是普通任务模板。

改造完成后：

- 已生效事实进入正式规则、脚本、测试和长期文档；
- 结果与验证进入提交和 PR；
- 本目录和项目入口中的临时指针一起删除。
