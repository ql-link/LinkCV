# 跨会话与跨工作树记录

> 已确认：不再维护 `state.yaml`、阶段字段、哈希快照或另一份状态文档。方案任务以 `solution.md` 为中心恢复，直接任务以当前请求和 Git 事实恢复。

## 1. 记录边界

| 场景 | 恢复依据 | 边界 |
| --- | --- | --- |
| 同一工作树的新会话 | 当前请求、`.specs/<KEY>/`、Git 差异、真实代码 | 直接读取当前文件，不继承聊天里的阶段结论 |
| 新建 Codex 托管工作树 | `.worktreeinclude` 创建时复制的 `.specs/*/` 快照，再结合新工作树的 Git 事实 | 只复制一次，不持续同步 |
| 已经存在的多个工作树 | 各自本地文件和 Git 差异 | 不自动合并；同一 Spec 原则上只在一个工作树继续写 |
| 跨设备或多人协作 | 来源材料、提交、PR 和已经提交的长期文档 | 本地 `.specs` 不承担远端同步职责 |

## 2. 唯一中心

- 直接实现任务不为恢复额外创建 Spec；新会话重新读取用户请求、分支、提交、差异和相关代码。
- 方案先行任务以当前 `solution.md` 为唯一中心文档。Acceptance、人工验收和实施报告只在真实需要时作为附件存在。
- 不创建 `change.md`、`status.md`、检查点文件、确认标志或其他替代状态源。
- 方案中的具体决定写入“已确认决策”；不增加表示整份文档阶段的“当前状态”或“已确认”总开关。
- 多个本地 Spec 都可能相关且无法从分支和内容确定唯一对象时，AI 直接询问用户，不猜测活跃任务。

## 3. 新会话恢复步骤

1. 读取当前请求和可用的来源材料。
2. 查看当前分支、最近提交、工作区状态和完整差异。
3. 方案任务读取 `solution.md`，再按引用和真实需要读取 Acceptance、人工验收或实施报告。
4. 对照方案中的目标、边界、已确认决策、实施步骤和验证要求，检查真实代码已经做到哪里。
5. 根据当前事实判断下一步是继续确认、实现、补测试、运行验证、质量审查还是收尾。
6. 不沿用旧会话口头声称的测试结果；需要作为当前结论时重新运行与现有代码匹配的命令。

恢复动作是重新核实事实，不是重建阶段机。缺少哈希、退出码、阶段字段或历史检查点都不构成阻塞。

## 4. `.worktreeinclude` 的作用

仓库跟踪 `.worktreeinclude` 中的 `.specs/*/` 规则，使 Codex 新建本地托管工作树时能够把被 Git 忽略的 Spec 目录作为一次快照带入。这个机制只解决本机新工作树缺少本地方案的问题：

- `.specs` 内容仍被 Git 忽略，不会随普通提交推送到远端；
- 复制发生在新工作树创建时，不是双向或持续同步；
- 后续在两个工作树分别修改同一份 Spec 不会自动产生冲突提示；
- 跨设备和多人协作仍依赖 Issue、提交、PR 或正式长期文档。

## 5. 明确接受的取舍

删除状态层后，不再提供以下自动能力：

- 用文档哈希自动发现方案是否漂移；
- 用缓存快照证明旧测试仍对应当前代码；
- 由工具给出唯一的下一阶段或活跃任务列表；
- 保存每次冻结、验证和审查的机器历史。

这些能力不通过另一份状态文件补回。对应做法是让 AI 阅读当前 Spec 和差异、检查真实实现，并在需要形成当前交付结论时重新验证。这样会增加少量语义判断，但能显著减少维护状态和处理状态不一致的成本。

## 6. 收尾

- 方案中的长期结论在实现后同步到 `docs/` 或代码附近的正式说明；未实现设想不进入长期文档。
- `implementation_report.md` 只保留已经允许的偏差、已接受限制和确需交接的遗留事项，不重复方案或正常测试结果。
- 本地 Spec 是否保留由实际后续需要决定；删除它不影响已经提交的代码和长期文档。
- 本改造临时目录在工作流收口后整体删除，不成为新工作流运行时依赖。
